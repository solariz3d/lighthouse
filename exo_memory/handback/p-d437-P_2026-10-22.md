## 6. The fix plan (no build; tier prove it, export)

1. **Tests first**, in `test/geom_bvh.test.js` and `test/geom-pitlane.test.js`: (a) `soup(mesh)` returns typed arrays whose lengths equal the counted vertices × 3, vertices, and indices of the mesh, and whose values equal the current implementation's on the test meshes (keep the current `soup` as a reference inside the test for the comparison, or compare hashes taken before the change); (b) `laneCheck(mainMesh, laneMesh, lane, { main: { soup, bvh } })` returns findings identical to `laneCheck(mainMesh, laneMesh, lane)`; (c) a bound: across `soup()` of a synthetic mesh of N vertices, `process.memoryUsage().heapUsed` grows by less than 64 B per vertex (today about 250 B); (d) the full suite and the mutants over bvh.js and geom/pitlane.js at landing.
2. **`soup()` counts, then fills typed arrays** (bvh.js:36-69): one pass over `mesh.scene.root.children` summing `positions.length` and `indices.length`, then `pos = new Float64Array(3n)`, `nrm`, `s`, `u` likewise, `vCell = new Int32Array(n)`, `tris = new Uint32Array(m)`, `triCell = new Int32Array(m / 3)`, filled by index in `add`. Expected cost at this mesh: 156 + 52 + 13 + 39 + 13 = 273 MB of ArrayBuffers, outside the V8 cage, instead of 806 + 236 MB inside it; the lane-check stage then peaks below the mesh stage. The output shape is unchanged (`vCell` and `triCell` become typed; their only readers index them, bvh.js:155-165 and pitlane.js:156-165).
3. **Build the main mesh's soup and BVH once**: `selfCheck` returns them on its result (`out.selfCheck.main = { soup: S, bvh: B }` at bvh.js:210, next to `trace.soup`), `laneForExport` passes `mainMesh.selfCheck && mainMesh.selfCheck.main` into `laneCheck`, and `laneCheck` uses them when given (pitlane.js:139). This removes the second build and its 10 s; the BVH's 2 M node objects are then built once per export.
4. **Measure, same instruments**: `exp437.js` on the ELYSIUM copy (expected: the `laneCheck` lines no longer rise above `after buildMesh`), and `run-export-437.js` in headless Chrome (expected: the export finishes or is refused by the validator, never a crash). Both scripts are in the evidence folder; the save copy is in my scratchpad by digest.
5. **Then, a separate lap (check it):** an export that runs out of memory should not take the page with it. The export is synchronous on the main thread (coreshell.js:1147, export.js:108); moving `runSegments` into a worker (the close runner's pattern, app/core/closejob.js) gives it its own isolate, so an OOM there ends the export with a message ("the export ran out of memory building the pit-lane check") and the page stays. That is the keeper's "screen turned white" as a symptom, distinct from the cause above.

What I would not do: raise V8's heap limit (the cage is 4 GB, fixed), turn the lane check off, or split the kn5; none of them is the cause.
