## 2 · TWO CORRECTIONS TO THE PACKET'S MODEL, both load-bearing

### 2.1 "The target's LAST CAPTURED screen is READY" cannot work — it is vacuous

The capture watcher writes **only when the screen is already ready**
(`main.rs`: `if !capture::screen_ready(&lines) { continue; }`). So the last captured screen is ready
**by construction**, and a gate reading it says yes always.

**The gate reads the LIVE emulator instead.** `PaneEmus` holds a vt100 parser per pane fed by the
reader thread on every PTY byte — the only thing that knows whether the keeper is typing *now*.

**This also collapses most of the bar you flagged as most likely to bite.** A dead capture WATCHER
does not blind this gate; only a dead READER does, and a dead reader is a dead pane. Tonight's
four-hour silent watcher death would NOT have muted the room through this path.

### 2.2 The naive version fails for a different reason than the packet gives — and the real one is worse

The packet says a naive `screen_ready` check misses the keeper typing. On a **clean** screen it does
not: he types, the box becomes `❯ we need to get that solid`, `is_empty_box` is false, and
`screen_ready` already holds.

**It fails when ANY OTHER ROW is a bare `❯`** — because `screen_ready` asks whether *any* row is an
empty box. And one routinely is: **a warm-started pane renders its own restored capture into the
scrollback, and that text contains bare `❯` rows as content.** This pane's own shell has several.
Then `screen_ready` is TRUE while he is mid-word.

So the gate keys on the **input box** — the *bottom-most* `❯` row — not on "some row somewhere".
`input_box_empty` uses `rposition`. The test
`screen_ready_alone_is_the_naive_version_and_this_is_the_screen_that_proves_it` asserts the premise
(`screen_ready` IS fooled by that screen) and then that the real gate is not. **If the reason had
been the packet's, bar 3's mutant would have been green and I would have shipped the naive version
believing it guarded.**

## 3 · THE STALE-SCREEN FALLBACK — the answer you asked for explicitly

**The hold is BOUNDED. `MAX_HOLD_MS = 240_000` (4 min), then the message is delivered anyway and the
board row says `(FORCED after the bounded hold — the pane never went idle)`.**

Unknown always **holds**, never "ready": a poisoned emulator mutex, a missing pane, or a screen with
no `❯` row at all. That is right, and unbounded it would be **a mute room with no error** — the exact
failure the watcher demonstrated tonight for four hours. A late message that says it was late is
recoverable. Silence is not. The number is a judgement, not a measurement: longer than any observed
pane turn, short enough that a wedged gate is a delay rather than an outage.

## 4 · REFUSAL — `deliver_only_when_idle` DOES NOT GO IN `brief/room-settings.json`

That file is a **Claude permissions file**. It is written verbatim into each pane's
`.claude/settings.json` (`room_brief("room-settings.json")`, `main.rs:2865`); today it holds only a
`permissions.allow` block. A `deliver_only_when_idle` key there would be **an unknown key in another
program's schema**, would never be read by this binary, and would reach a seat only after a build.
Putting it there would have looked done and been inert.

**Shipped instead:** `fn deliver_only_when_idle()` in `main.rs`, default **on**, overridden by
`CONSONANCE_DELIVER_ONLY_WHEN_IDLE=0|false|off`. Both states tested (bar 5) and mutated.

*(Also: the packet's path is `consonance/brief/room-settings.json`; the file is at
`consonance/src-tauri/brief/room-settings.json`.)*

**Owed, not mine:** if the flag should be operator-visible rather than env-only, its home is
Consonance's own config (`~/.consonance.json`, the surface `fromConfig` already reads) — a small
change, and it is a decision about a config surface, not a tool edit.

## 6 · THE BOARD ROWS — and the ~29% class

`QUEUED -> <pane> (N waiting, prompt not idle): <preview>` and
`DELIVERED -> <pane>[ (FORCED…)][ [WRITE FAILED]]: <preview>`.

Two facts, two rows. Today the board says delivered when the text *rendered*, so **"not yet sent"
and "sent and unacknowledged" produce the same line** — the conflation behind the unconfirmed class.
A queue that records both transitions can now tell them apart.

**What this does NOT do, and I will not claim it does:** it does not *reduce* the unconfirmed
percentage. It makes one previously invisible state expressible. **Whether the ~29% is mostly
never-sent or mostly sent-unacknowledged is now measurable and is not yet measured** — that reading
needs rows written after this ships, and quoting a number today would be inventing one.

## 8 · WHAT THIS DOES NOT ESTABLISH

- **No live-pane test.** Every screen is a fixture, as the packet required. The predicate is proven
  against the shapes the emulator produces; it is **not** proven against a shape nobody has thought
  of yet. A pane rendering something exotic at the bottom is the residual risk, and it fails
  **closed** (holds, bounded), not open.
- **The drain thread is not itself guarded.** It is one thread with no liveness stamp — the same
  class as the watcher that died silently tonight. It does not `break` on a poisoned lock (it holds
  no lock across the tick), so it is better placed than the watcher was, but B's liveness stamp is
  still the real answer and is still parked.
- **The 4-minute bound is unmeasured.** No distribution of real turn lengths was collected; it is a
  judgement stated as one.
- **A pane that is never idle still delays by up to 4 minutes.** That is the deliberate trade.
