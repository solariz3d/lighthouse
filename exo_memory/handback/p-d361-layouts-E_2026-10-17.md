## 0. What it does

- **File ▸ Export layouts…** is a new button in the File menu, beside Export…:
  - It lists the saved tracks. You tick 2 or more, give each a layout name (a–z, 0–9, _) and the name Content Manager shows ("Elysium Long"), mark one as main, and name the track.
  - Then you pick a folder.
  - It writes one `t180b_<name>` folder in Aurora's shape (§1 of D360):
    - per layout: `<folder>_<L>.kn5` (a whole road), `models_<L>.ini`, `<L>/data/{surfaces,map}.ini`, `<L>/map.png`, `<L>/ai/fast_lane.ai` and `ui/<L>/{ui_track.json,preview.png,outline.png}`;
    - at the root: nothing else but the marker.
  - No layout gets an `extension/` of its own.
- **G1, the boundary.** checked: a saved track is a `src/core/document.js` document (`eq-<name>.t180track`, `app/README.md:153`). `src/doc/project.js` holds `src/doc` documents (`project.js:14`, `require('./serial.js')`). So **the two don't fit, and project.js is not used by the app.**
  - At the boundary (`app/menubar/layoutsexport.js`), each saved track opens in a core shell of its own and is built by that shell's own `buildExport`, which is the Export button's route: placed spawns or the start layout, the pit lane, the road surface.
  - That shell's exporter only catches the segments and options it's handed. They then go through `buildFromSegments`, the function `exportSegments` calls.
  - That shell's storage can only open and list tracks, so it never autosaves or writes.
  - **Each layout's kn5 is byte-identical to the Export button's kn5 for that track** (test row A1).
- **G3.** On re-export, the folder's previous marker list, minus this export's files, is removed: plain files only, never through a link or a junction. Then any folder they leave empty goes too, but never the track folder itself.
  - Anything else in the folder is left alone: a CSP `extension/` config, a note, or a path in the marker that points outside.
  - An unreadable marker removes nothing, with a warning.
  - The webview builds in memory and can't see the old folder, so **the native side does it**: a new command, `write_layouts_export` (`src-tauri/src/lib.rs`), which first writes under `write_export_to`'s own guards. `src/export/layouts.js` has the same rule for node (`staleFiles` and `removeStale`).
- **G4.** Each `ui_track.json` carries `priority`: main 1, the others 0. CM adds priority × 1e8 to its name scoring (TrackObject.cs `:210`), so the main layout wins. The test proves it with a control: without `priority`, CM's name rule picks "gp"; with it, the marked main wins.
- **One root `extension/`:** this exporter writes no `extension/` at all today, so the rule holds as "none per layout". It is pinned in two places: the folder-shape row checks there's no `<L>/extension`, and the app row checks the exact file list.
  - The narrow reading, stated: I didn't add an empty root `extension/`, since we have no CSP config to put in it.
- **The folder pick** goes through the Export button's own guard (`resolveTarget`: the AC-install rule, and an empty folder made in content\tracks), and through its empty-folder note.
