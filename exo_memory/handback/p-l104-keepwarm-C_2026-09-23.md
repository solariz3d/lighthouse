## 1 · First, the finding: the recorded collision was not a shared crossing

The librarian's note (`db76263`) says A and E were pinged in the same minute at 01:07 "because their last requests
started together". **The board says otherwise.** It holds 5 keep-warm rows (earliest 2026-09-22T07:47Z), and exactly
one minute with two seats pinged:

    2026-09-23T07:07:25.779Z keep-warm -> a2122153 (committee) · 151 min since its last request started
    2026-09-23T07:07:25.967Z keep-warm -> 6fe15f0a (committee) · 123 min since its last request started

(command: read `board.jsonl`, keep rows matching `^keep-warm -> (\S+) .*?(\d+) min since`, group by minute; read-only)

- **Their last requests started 28 minutes apart, and both were far past 50 minutes.** They were not crossing a
  threshold together. Both were **overdue** and were released in the same tick by something else: a composer reading
  empty, or activation, arriving at once.
- **A threshold offset of 0 to 6 minutes cannot separate two seats that are 123 and 151 minutes idle.** This fix would
  not have changed 07:07.
- **What would cover the observed case is a per-tick stagger** in `keep_warm_tick`: at most one ping per tick, with the
  rest carried to the next minute. That function is outside my files, so I propose it and did not build it.
- **I did not trace what released both at 07:07.**

The offset still fixes the case the note describes: seats whose last requests started together, such as one dispatch
ringing several panes, would cross 50 together. **Zero such collisions are on the board,** so it is a guard against a
case that hasn't happened here yet. It's cheap and correct, so I built it as asked.

## 2 · What was built (`consonance/src-tauri/src/main.rs`, sha256 `2332046174352db2`)

- **`keep_warm_after(seat)` = `KEEP_WARM_AFTER` (50 min) + (FNV-1a-64(pane id) mod 7) whole minutes.**
  - **The hash is this file's existing `fnv1a` (`main.rs:1763`, the transcript fingerprint's hash), not a copy.** I
    wrote my own `fnv1a64` first; a mutant anchor that matched 4 times showed the duplicate, and I deleted it.
  - FNV-1a is deterministic by definition, unlike Rust's per-process-keyed `DefaultHasher`, so the value is the same
    across calls, restarts and machines.
  - A test pins it to the published vectors: `""` gives `cbf29ce484222325`, `"a"` gives `af63dc4c8601ec8c`.
  - The key is the full pane id (the session id), which a resumed seat keeps.
- **`keep_warm_decision` takes the seat and uses its own threshold for BOTH bars**: idle since the request started, and
  "pinged and not yet answered". The one caller (`keep_warm_tick`) passes `&pane`.
- **Every reader of `KEEP_WARM_AFTER`** (`grep -n KEEP_WARM_AFTER main.rs`): only the two bars in `keep_warm_decision`
  read it, and both now go through `keep_warm_after`.
  - The two Skip reasons said "under 50 min" and now say "its keep-warm threshold (50 min + its fixed seat offset)".
  - The "pinged" rows (`keep_warm_row`) print the seat's measured idle minutes, not a threshold, so they needed no
    change.
  - Two doc comments still describe the base 50; they are the base and remain true.
- **Why 7 slots, and what it costs.** The cache lives one hour from the request start: 50 + 6 = 56 minutes, plus a
  60-second tick, is 57. The old ten-minute margin for a slow delivery is now three minutes for the +6 seats. More slots
  would use it up. A test pins `50 + 6 + tick < 60`.
- **The limit that comes with 7 slots:** seats sharing an offset still share a crossing. Tonight's live ids by the same
  hash: chair `0c0c0c0a` +0, librarian `0c0c0c0b` +4, **C `0845a868` +4, `12fb81f6` +4**, E `a2122153` +3, A
  `6fe15f0a` +6, Third Place `3d000000` +2. Three of them share +4.

## Step 2 — AT MOST ONE PING PER TICK, most overdue first (2026-09-23 ~05:0x local). Step 1 above is kept (blob `03f872de`).

`main.rs` sha256 is now `699fafab5fc758a3`; all hunks are in the keep-warm code and its tests. There was no rebuild or
restart. **Live at the next rebuild.**

**What changed in `keep_warm_tick`.**
- The per-pane loop is unchanged in everything except the ping. When a seat's decision is `Ping`, the loop no longer
  sends; it adds the seat to `due` (pane, idle since its last request started).
- **After the loop, the new pure function `keep_warm_pick(&due)` chooses ONE, the MOST OVERDUE.**
  - Overdue = idle minus **that seat's own threshold**, `keep_warm_after`, offset included.
  - A tie goes to the smaller pane id, so the order is stable.
- That one seat is sent through the existing `keep_warm_send`.
- Every other due seat has its `KeepWarmLastSkip` set to `"deferred: due, but another seat more overdue was pinged
  this tick (one ping per tick)"`. The missed-window report prints that reason if a window passes while the seat
  waits.

**Nothing else is rationed.** For every pane, every tick, as before:
- the transcript read;
- activation, which is sticky;
- the Skip reason;
- the **missed-window report**.

There is no `break` and no early `return` in the loop. A source-sweep test pins this: no send and no `break` inside the
loop, exactly one `keep_warm_send` in the tick, and the pick and the deferred-reason write after the loop.

**Many overdue seats, and starvation.**
- **N seats due at once clear in N ticks, one per minute.**
- **Nobody is starved.** A deferred seat is not queued: it is decided afresh next tick, still `Ping` and a minute more
  overdue, so it only climbs the order. A seat just pinged drops out for its own threshold.
- The test `no_seat_is_starved_n_overdue_seats_clear_in_n_ticks` runs seven seats all overdue together through
  seven ticks, and all seven are pinged.
- **The keeper's rule still holds.** Every activated seat is kept warm; rationing only delays a ping, by at most N−1
  minutes.
- **The cost, stated:** the Nth seat waits N−1 extra minutes. A room of about 7 released together pings its last seat
  up to 6 minutes late. If that seat was crossing fresh at +6 (56 minutes), it is pinged past the one-hour cache life
  and pays a re-write it otherwise wouldn't. That only happens when many seats fall due in the same minute, which is
  exactly the burst this step spreads out.
- **A seat active between ticks is not pinged,** because nothing is carried over: its new request resets its idle time
  and the next tick decides `Skip`.
- **A send the gate withdraws** (`keep_warm_send`'s "NOT SENT") uses up that tick's one ping. The others wait one more
  minute, and nothing is lost.

**Tests: 6 new, 39/0 for the keep-warm set.** They use the real decision plus `keep_warm_pick` for each seat, which is
the pass without the app.
- **Two overdue seats on one tick are pinged on two DIFFERENT ticks, most overdue first.** This is tonight's pair:
  E (151 min, 98 over its 53) on tick 1, A (123 min, 67 over its 56) on tick 2.
- One overdue seat is pinged on the first tick, and not before its own threshold.
- **A seat that becomes active between ticks is not pinged.**
- The pick measures overdue against each seat's own threshold, and a tie goes to the smaller id.
- No starvation: 7 seats in 7 ticks.
- The source sweep that only the ping is rationed.

**RED** (stub `keep_warm_pick` = first candidate, and the send still inside the loop): 4 failed. The one-seat and
no-starvation tests pass on that stub: a first-candidate pick satisfies them, so they are guards, not the red.
