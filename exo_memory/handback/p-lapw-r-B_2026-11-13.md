## 1. W5, the launcher's pull (`consonance/launch.ps1`)

- **F1, the receipt.** Every return of `Update-FromOrigin` names an outcome, and a `finally` writes `launch-pull.json` (in a receipt dir
  that is a PARAMETER, default `Get-FuseReceiptDir`) with the spec's eleven fields: `at, machine, launch_id, outcome, head_before,
  head_after, behind, fetch_ms, bytes_received, last_progress, why`. Outcomes are the spec's ten. The fetch's stderr is redirected and drained
  asynchronously, `--progress` is added for `last_progress`, and `why` is git's first `fatal|error|warning` line.
- **The launch id.** `$env:CONSONANCE_LAUNCH_ID` = a fresh GUID before the pull; the app inherits it. **Critic E3:** the app takes it ONCE
  in `main()` before anything is spawned and REMOVES it from its environment (`launch_id`, `take_env_var`), so `stick-apply.js`'s relaunch
  cannot inherit an old id.
- **F1b, the wait** (`Wait-FetchChild`, `Get-NewTmpPackBytes`): the 20 s ceiling holds until a NEW `tmp_*` file opens in
  `git rev-parse --git-path objects/pack` (files there before the fetch are excluded, e.g. today's `tmp_pack_Hl1ze7`). After that it waits
  while those bytes grow, kills after 15 s of silence and never waits past 120 s. `-c fetch.unpackLimit=1` (the second reader's fix) makes
  every fetch keep a pack. A stop for silence or cap gets its own dialog; the 20 s one is unchanged.
- **A FINDING THE SPEC DID NOT HAVE:** on Windows, the directory listing's size of a file another process holds open for writing does not
  grow. index-pack holds its tmp_pack open. A listing-only reader read **0 B** and cut a live, throttled 24 MB fetch for silence at
  **16.3 s**. The size is now read through a handle of our own, opened for read and shared for read, write and delete, so git still renames
  the file at the end. The recorded `2,138,111 B` of `tmp_pack_Hl1ze7` was readable only because the kill had closed the handle.
- **F3:** the comment's stale pointers now read `dev\ARRIVING.ps1:146`, `main.rs:15387-15389` (stick-apply) and `sync_at_launch()` at `main.rs:16403`.
- **Critic E2 stands and is written in the code's comment:** at the 08:41 rate (113.7 KB/s) the 120 s cap carries about 13.6 MB of the
  90.5 MB, so the wait is not shown to fix the recorded case. The receipt's `bytes_received`, `fetch_ms` and `last_progress` at the next
  large catch-up answer it (Q4).
