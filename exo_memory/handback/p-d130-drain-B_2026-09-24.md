## 2 · WHAT HELD THE 06:20 PAIR — the drain thread

**The observation, from D's board, which carries L's pane rows for that morning.** The librarian's own composer rows (`role: user`, pane `0c0c0c0b`, 12:05–13:45Z = 06:05–07:45 local; `<scratch>/d130/librarian_rows.js`):
- Rings kept arriving at the librarian **throughout** the "hold": `[pane:C] L110` at 12:30:22Z, `[pane:A] L111` at **12:37:16Z** (the stall trace's "ready file current by 06:37:16" is this delivery), `[pane:E] L112` at 12:50, then L113 ×3, L114 ×3, the keeper's own prompts and a `/compact`.
- **Neither queued ring appears, ever.** A's L109 ring and the chair's "premise that fails" note occur nowhere in the librarian's rows through 16:00Z. A itself wrote at 12:32:39Z: *"My L109 ring still shows as queued at the librarian (QUEUED librarian 11m)"*. The librarian collated L109 from disk at 12:31.

**Why that can't come from `drain_decision`.** Every later ring was delivered **at the door**: `gate_or_queue` (`:10180`) computed `pane_state` for the librarian, got Deliver, and wrote directly. On any tick where the librarian's state said Deliver, a running drain would have popped the queued head too. Deliverable moments came again and again for 3+ hours, and the head never moved.

**So the drain was not running, and the code has an unguarded way to stop it.**
- The thread (then `:13364-13374`) was `loop { sleep(250 ms); drain_inboxes(&h); }` with **no `catch_unwind`**. The keep-warm thread directly below it *does* have one, with the L034 lesson written beside it: *"a thread that can die without a word is a feature that stops without a word."*
- One panic inside one tick ended queued delivery **for every pane, silently, until the next launch**, while door deliveries (which never touch the queue) went on working. That is exactly the observed pattern.
- **Why the door survives what kills the drain:** the door computes `pane_state` for its ONE receiver; `drain_inboxes` computes it for **every pane that has a queue**. So it meets every pane's worst screen: a vt100 read (`screen.rows`, `typed_only`), `composer_state`, or a `Panes`-lock `unwrap()` in `inject_to_pane`.

**What this does NOT establish: which panic.** The panic text went to stderr, which a windowed Tauri app does not keep. The mechanism is named from the code and the observation; the specific line is not.

**Evidence that would confirm it — all on L, none reachable from D:**
1. L's board, chair audit rows (`pane: chair`) from the last DELIVERED or WITHDRAWN row written by the drain before 12:20Z. **After the death point, every QUEUED row to ANY receiver has no drain row**, until L's next launch.

## 3 · THE FIX (main.rs, live after a rebuild)

- **`guarded(step) -> Option<String>`**: runs one step under `catch_unwind` and returns the panic's text (`&str` or `String` payload) instead of unwinding. It **returns** the text rather than logging it, so tests never write into the real data dir (the D129 lesson).
- **`drain_inboxes`: each pane's work runs under `guarded`.** The body is unchanged and kept at its old indent, so the diff is the guard alone, and the neighbouring source-shape tests still find their strings. A panic on one pane no longer stops the others in that tick. The message being handled **stays queued** (a panic before the take leaves it) and is retried next tick.
- **`report_drain_panic`:** `plog` plus a board row `DRAIN PANICKED -> <id8> (caught; …): <why>`. Rate-limited to **once a minute per pane** (`drain_panic_due`), so a panic that repeats every 250 ms doesn't write four rows a second.
- **The thread loop is guarded too:** `if let Some(why) = guarded(|| drain_inboxes(&h)) { plog(…) }`, for anything outside the per-pane guard.

**New tests (6), all in `inbox_tests`:**
- the Stale-through-the-queue test (§1);
- two rings behind Stale;
- `guarded` catches and names a panic;
- **one panicking pane doesn't stop the others** (panes a, b, c with b panicking: a and c done, b reported);
- the once-a-minute rule;
- **the wiring by source shape:** each pane's step, including the sweep and the take, sits under `guarded`; a caught panic is reported; the thread loop is guarded; and the bare `drain_inboxes(&h);` statement is gone.

## 4 · A SEPARATE DEFECT FOUND ON THE WAY — `chain-status.js` can't pair a forced delivery (NOT mine; for routing)

`queueRow` (`consonance/tools/chain-status.js:738-750`) takes the label after the **first** `": "` that follows the `]`. Since **D074 (`96f62a6`, 2026-09-19)**, every forced delivery's note carries a `": "` before the label: `"; composer: read as text on N … of M readings)"` or `"; at the bound: text)"`. So `queuedWaiting` **never pairs a forced delivery**, and the pulse prints it as waiting forever.

**Measured, not argued** — the rows below are rebuilt from the format strings at `main.rs:10239-10249` and `:10292`, not taken from a real board:

| row | parsed label | |
|---|---|---|
| `QUEUED -> 0c0c0c0b (1 waiting, stamp=STALE (…)): L109 ring label` | `L109 ring label` | pairs |
| `DELIVERED -> 0c0c0c0b [stamp=ready]: …` | `L109 ring label` | pairs |
| forced Stale, with readings | `read as text on 3 of 3 readings): L109 ring label` | **does not pair** |
| forced outranked, with readings | `text): L109 ring label` | **does not pair** |

`queuedWaiting` over the queued row plus the forced Stale row, 99 minutes later → `[{"seat":"librarian","age_min":99,"waiting":1}]`: **a delivered ring reported as waiting 99 minutes.**
- **D's board can't show it:** its 235 forced rows are all pre-D074 format and all pair (`<scratch>/d130/pairing.js`: 235 of 235, and 138 of 138 plain). D's app hadn't forced a delivery since that format landed; the newest forced row is 09-19 02:42, the old format.
- **This did not cause the 06:20 pair.** L109 was genuinely never delivered (§2). But it makes a forced delivery look exactly like that stall, so the next "QUEUED 99m" alert can't be trusted until it's fixed.
- **The fix belongs in `chain-status.js`:** pair a drain row to an open QUEUED row when the row ENDS with `": " + label`, not by the first `": "`. Plus a test built on today's forced-row format. It's the chain-status owner's file, so it is not done here.

## 5 · ALSO SEEN, NOT CHANGED — the door skips the queue

`gate_or_queue` delivers at once whenever the door says Deliver, **without checking whether that pane already has messages queued**. So on L, L110, L111 and the rest overtook the queued L109: FIFO broken at the door, which `Inbox`'s own doc says matters.
- A one-line fix (queue when `depth(pane) > 0`) has a real trade-off: with a dead drain it would stop door deliveries too, turning a partial stall into a total one.
- With the drain now guarded, it's probably right, but **it's a design call**, so it is named, not made.
