## 1 · THE THING THE CHAIR AND A NEED FIRST — JEV HAS BEEN JUDGING WITH THE STRUCK LINE, UNDER A STAMP THAT SAYS OTHERWISE

The harness's first dry-run plan failed its own baseline proof: **0 of 3** stored prompts rebuilt byte-identical through
the current builder. The first differing byte is in the builder's fixed text. **The stored prompts carry the pre-L083
line** (the struck "can't lose" test), and the current builder carries BOOT's repaired wording.

**Measured over every capture on L** (`%LOCALAPPDATA%\consonance\jev-shadow\judge-captures`, 384 with an `l2` prompt):

    stamp 93608b0f (older builder)      text OLD   138   2026-09-22 09:01Z → 13:53Z
    stamp e18b0546                      text OLD    22   2026-09-23 06:57Z → 07:16Z
    stamp = CURRENT builder (d1a1ace4)  text OLD   224   2026-09-23 07:17:51Z → 12:38Z   ← stamped as repaired, and not repaired

**All 384 carry the old line.** The first capture stamped "current" is 47 seconds after my L083 edit (07:17:04Z).

**The cause, in A's file** (`jev-judge.js:100–111`, `loadJudgeInputs`):
- `sourcesSha` hashes the worker **file on disk** (`readText(w2)`).
- `buildOverseerPrompt` comes from `require(w2)`, and **Node caches that module for the life of the process.**
- So a runner started before an edit keeps building with the old code, while stamping the new file's hash.

**This is the caveat I recorded in L083** ("the live Jev runner loaded its prompt before the edit, so the fix reaches
Jev at the next app launch"). What is new is that **the stamp makes the gap invisible.** The field meant to say which
builder built a prompt says the wrong one.

**Two consequences:**
1. **The L083 repair has never reached Jev on L**, and nothing in the store says so.
2. **Any Jev result read today was produced under the struck wording.** If the discipline is a suspect, the version
   Jev actually read was not the current file.

**For A, not changed by me** (A owns `jev-judge.js`): stamp the builder from the function actually used, for example a
hash of `buildOverseerPrompt.toString()`, or re-load it per pass. And the runner restart is owed before any further Jev
reading counts as current-discipline.

**How the harness handles it:** it never trusts the stamp. It tries the working-tree builder, then each committed
revision of the worker, newest first (`git log -n5`), and uses **the first one that reproduces the stored prompt byte
for byte**. It records that revision. All 3 dry-run units reproduced under **`1a5891a`**, the pre-L083 worker.
- **Every variant of a unit is built with that same builder**, so a variant differs from what Jev actually saw by
  exactly one part.
- Old revisions are loaded by extracting the one function with jev-shadow's own `extractFunction`, never by
  `require()`. The `58b94f9` revision has no `require.main` guard, and requiring it RAN the overseer: exit 1, silent.
  I hit that before switching.
