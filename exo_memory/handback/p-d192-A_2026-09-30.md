## Root cause
- **CHECKED in the Tauri source** (tauri 2.12.0, the version in `src-tauri/Cargo.lock`): `manager/window.rs` (`CloseRequested`): `if window.has_js_listener(WINDOW_CLOSE_REQUESTED_EVENT) { api.prevent_close(); }` — ANY script close listener makes Tauri prevent the close and wait for the script to call `destroy()`. The script wrapper (`scripts/bundle.global.js`, `onCloseRequested`) is `listen(close-requested, async (e) => { const ev = …; await handler(ev); ev.isPreventDefault() || await this.destroy(); })`: a handler that THROWS leaves the window open. `event/listener.rs`: script listeners are removed by `remove_webview_listeners`, called only when the webview/window is destroyed (`manager/mod.rs:648, :662`), NOT when the page reloads.
- **CHECKED in the real window (the reproducer, unmodified app at e9f3127, `old.exe` sha256 `3c6ad6c2dec6ec72…`):** WM_CLOSE (`Process.CloseMainWindow`) to an off-screen instance, 8 s wait, then kill:
  | scenario (each a fresh process, its own WebView2 profile, the mode switched through the page's own select) | old |
  |---|---|
  | A core, fresh start | closed (6 ms) |
  | B pieces (core → pieces) | closed (15 ms) |
  | **C pieces → core** | **STAYED OPEN (killed after 8 s)** |
  | D core → pieces → core → pieces | closed (16 ms) — the last pieces page registers a working handler |
  | E pieces with a failing autosave | closed — **see below: the plant did not work** |
  | **F core after a pieces page (plant attempted)** | **STAYED OPEN** — the stale listener, same as C |
- **So, of the two candidates the librarian named: the STALE LISTENER is the cause, checked** (source + real window, C and F). The core page registers no listener, but the previous pieces page's registration is still in the webview's registry, so Tauri prevents the close and emits `close-requested` to a callback that no longer exists: nothing ever calls `destroy()`. A fresh core start does close (A), so the keeper's window had been switched pieces → core earlier in its session (**inferred**: I cannot see his session; the stored mode `core` is what a switch leaves behind).
- **The other candidate, "the handler throws", is REAL BY SOURCE but NOT reproduced in the real window.** `shell.cleanExit()` → `clearAutosave()` awaits `storage.clearAutosave()` with no catch (`app/shell.js:78-82`), so a failing `clear_autosave` would reject the pieces handler and, by the wrapper above, leave the window open. I could not plant a failure from the page: `window.__TAURI_INTERNALS__.invoke` is non-writable and non-configurable and `window.__TAURI__.core` is frozen (measured, scenario Z; my replacement of `__TAURI_INTERNALS__` was silently ineffective: the plant self-check printed `PLANT INEFFECTIVE`), so scenario E/F's "failing autosave" was NOT actually failing. That case is covered by the model tests below, not by the real window. I did not make the native call fail (it would need a hostile file in the keeper's app-data folder).

## The fix (FEEL tier; no src-tauri change: Rust needed nothing, the handler belongs to the page)
- `app/closer.js` (new, 49 lines): `makeCloseHandler` / `installCloseHandler`. The handler `preventDefault()`s the wrapper's own destroy, runs the mode's cleanup in `try` raced against a 3 s timeout, swallows and logs any error or timeout, and calls `win.destroy()` in `finally` — exactly once, itself.
- `app/index.html`: the close handler is registered **before the mode branch** (`let closeCleanup = null;` + `installCloseHandler(win, () => closeCleanup)`), so both builders have it; if `closer.js` cannot load, a bare handler that only destroys is registered instead (a stale listener can still not trap the window). The pieces builder's old `win.onCloseRequested(async …)` is gone; the pieces mode now only SETS `closeCleanup` (the same cleanExit-or-flushAutosave), so the autosave/cleanExit stays, inside the try. Core sets nothing.
- `app/test/shell-dist.test.js`: `app/closer.js` added to the modules the page loads (it must sit in a folder `build.rs` copies).
- `CHANGELOG.md`: one line under Fixed.

## Tests (heavy-run lock, `--max-old-space-size=4096`; targeted only; no mutation, no full suite, no AC)
- `app/test/closer.test.js` (new, 24 tests): a Tauri model built from the source above (registry survives reload; any listener prevents the close; only a live page's callback answers; a throwing handler never destroys). Seven cases, each run against the page AS IT WAS (`REPRODUCER`, asserting the fault) and as it is now (asserting the window closes, `destroy()` at most once): core fresh; pieces; pieces → core; core → pieces; core → pieces → core → pieces → core; pieces with a failing autosave; core after a pieces page whose autosave fails. The reproducers give TRAPPED for pieces → core, the 5-step switch, the failing autosave, and core-after-failing-pieces, and CLOSED for the other three, matching the real window's C and D. Plus: the pieces cleanup runs BEFORE destroy; core has none; a cleanup that throws is logged and the window closes; a HANGING cleanup closes after the timeout (40 ms in the test); a failing `destroy()` never throws out of the handler; the wrapper's destroy is prevented (once only); off-Tauri registers nothing; the cleanup is read at close time; and two structure tests on `app/index.html` (registration before the mode branch; one `onCloseRequested(` left, the fallback). At e9f3127 `index.html` has no `installCloseHandler` and no `closeCleanup` (checked), so the two structure tests are red there by construction.
