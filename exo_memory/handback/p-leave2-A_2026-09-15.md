## 1 · WHAT IS BUILT

### (a) D-8, pid reuse: the app's half

- **One start time per session.** `main.rs`: `static APP_STARTED_AT: OnceLock<String>`, read through
  `app_started_at()`. It is recorded by `let _ = app_started_at();` at the top of `main`, right after
  `claim_single_instance`, before `tauri::Builder`. The format is ISO UTC to the millisecond
  (`to_rfc3339_opts(Millis, true)`, the same clock `leave_run`'s `now` already uses).
- **The waiter's argv.** `sync_launch::waiter_args(data_dir, app_pid, app_started_at)` now ends
  `… --app-image consonance.exe --app-started-at <ISO>`. `start_exit_waiter` passes `app_started_at()`.
- **Both LEAVE files.** `run_leave(…, find, app_started_at, now, export)` writes `"appStartedAt"` into
  `stick-leave.started.json` and into `stick-leave.result.json`, on both branches that write a result (one folder, and
  several folders). `leave_run` passes `app_started_at()`.
  - The parameter goes after `find`, so E's pin `&data, std::process::id(), &alive, in_flight, find,` still holds.
  - **Named `appStartedAt`, never `startedAt`.** The result already has a `startedAt`, meaning when the Leave began.
    A test asserts the two are not the same value.

### (a) D-8: the waiter's half (`dev/stick-waiter.js`)

- **Parsing.** `--app-started-at <ISO>` is parsed into `app.startedAt`. With the flag and no value it is refused (code
  2), like every other argument. **The flag is optional:** see §2.1.
- **`leaveFor` matches on four things:** the pid, then the image (D-7), then `appStartedAt`, which must be a string on
  BOTH sides and equal. A legacy file with no field, a file with `null`, or a waiter given no start time matches
  nothing. So each of these is stale and never case b or case c.
- **`removeLeave`** re-reads the file and removes it only when the pid AND `appStartedAt` still equal this session's.
  A reused-pid session's file written during the export is kept, alongside D-4's newer-pid guard.
- **Adoption** sets `app.startedAt = null` when it takes the relaunched pid. This waiter was only ever told the first
  session's start time (§2.2).
- The doc header, the usage line and case d's comment now say this.

### (b) 1: a spawn that fails after its child runs kills the child

- `sync_launch::or_kill(r, kill)` is pure. It calls `kill()` on `Err` only, then returns the error as a `String`.
- In `spawn_claude_pane`, `try_clone_reader()` and `take_writer()` both go through it, each with a closure that runs
  `let _ = child.kill();`.
  - This is the `Child` itself, still here at those lines; it moves into the wait thread later.
  - Its result is not read, because portable-pty 0.8.1 reports it backwards (§2.7 D-1).
- These were the only two `?` between `spawn_command` and `Ok(PtySession …)`. The P1b `return Err(row)` runs only
  after the child has exited.

### (b) 2: `insert_pane` kills a live session it replaces

- `sync_launch::kill_replaced(replaced, kill)` is pure. On `Some` it calls `kill` on the replaced value; on `None` it
  does nothing.
- `insert_pane` now reads `sync_launch::kill_replaced(map.insert(id, session), &mut |old: &mut PtySession| { let _ = old.killer.kill(); });`.
- It still has the literal `map.insert(`, and the order take < insert < `drop(flight)`, so E's pin
  `every_spawned_session_reaches_panes_through_the_helper_that_releases_its_flight` holds unchanged.

## 2 · WHAT BUILDING IT AS WRITTEN LEAVES OPEN (rulings for B and the chair)

### 2.1 The mixed-build window: `--app-started-at` is OPTIONAL, and that is my choice, not the packet's

The packet says the waiter learns the start time from argv. It does not say what happens when an app does not pass it.

- **Required** (BAD_ARGUMENTS without it): an exe that does not pass the flag gets NO waiter at all. A hard kill of
  that exe then exports nothing.
- **Optional** (built): such an exe still gets a waiter. Its LEAVE files match nothing (the app's start time is
  unknown), so the waiter always takes case d, the fallback.

**Who is in the window.** An exe that writes LEAVE files but does not pass the flag, launched against this script: that
is, any build from 99649d8 ("P-LEAVE lands") up to this landing.

- The release exe on D has mtime `2026-09-14 23:40:04 -0600`. 99649d8 is `2026-09-15 01:58:14 -0600`, so that exe
  predates P-LEAVE. It writes no LEAVE files, and its waiter already took case d on every exit. Nothing changes for it.
- An exe built inside the window, once it has done a DONE Leave, gets a second, fallback export from its waiter.
  - The notice will say *"Consonance closed without saving to the stick itself (it was stopped before its close window
    could run)"*. That is false in this case.
  - Whether the second export carries anything was NOT measured. I expect nothing, since the seats have ended and the
    Leave already carried them.
- **Named for L:** I have not looked at what is built on L.

### 2.2 The adoption regression: an adopted session's DONE is no longer recognised

**Before this lap:** a close and reopen inside one poll (D-9) adopted the new pid. At that session's exit, its own
LEAVE_RESULT matched by pid, and the waiter stood down (case b).

**Now:** the waiter was told only the FIRST session's start time. The adopted session's start time is unknown to it,
and guessing would bring D-8 straight back. So `app.startedAt = null`, and the adopted session's LEAVE files are stale.

- At its exit the fallback runs: a second export after its own Leave, and the false notice from §2.1.
- The test says this outright:
  `an ADOPTED session's start time is unknown to this waiter, so its LEAVE files are stale — named, not guessed`
  (exports === 2).
- Its case c is lost too: an adopted session killed mid-Leave is exported at once, instead of waiting on the
  ledger.lock holder.

This is not data loss that I can find: the export is serialised by the ledger lock. But it is a behaviour the P-LEAVE
lap had, and this lap removes it. **Options, none of them built:**
- (i) The app writes its start time to a file keyed by pid at launch (for example beside the waiter lock), and
  adoption reads it.
- (ii) Adoption reads the new pid's OS creation time, and the app records that same OS time instead of its own clock.
  Not the same string today.
- (iii) Accept it as ruled: adoption is rare (a reopen inside a 2 s poll), and the cost is a redundant export plus a
  wrong notice.

### 2.3 Not changed, and named

- **`leave_cleanup` does not read `appStartedAt`.** The packet does not rule it. A file naming this launch's own pid is
  still kept at launch as a "live Consonance", although a reused pid wrote it. The waiter that owns it reads it as
  stale. Only the doc comment and the test comment changed; the stale "D-8 is HELD" wording is gone from both.
- **`insert_pane` kills AFTER the new session is spawned.**
  - `pty_reopen` spawns the new `claude --resume` before `insert_pane` sees the old one. If the old session is still
    live, two processes resume the same conversation for the length of a spawn (`RESUME_CONFIRM` is 1 s, plus startup).
  - The packet puts the kill in `insert_pane`. Killing before the spawn would be a change to `pty_reopen`, which I did
    not make.
  - The kill runs under the Panes lock.
- **A killed replaced session is not waited on.** It has left Panes, so the close's D-1 pid wait does not see it. The
  same is true for an `or_kill`ed child. Both are killed, not awaited.
- **`child.kill()` ending the process is not measured** in either path (§5).
