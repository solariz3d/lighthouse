## 2 · THE COMMAND

**JS, not PowerShell**, and the reason is measurable rather than stylistic: `js-suite.js` DISCOVERS
tests by walking the tree, so `dev/place-conversations.test.js` is run by the room's instrument from
the moment it exists, and a `.ps1` is run by nobody. The mutation discipline is JS too. It is still
one command the keeper types, in the shape `dev/acceptance-p1.ps1` established:

    node dev/place-conversations.js --dry-run                    # rehearse; writes nothing
    node dev/place-conversations.js                             # do it, app closed
    node dev/place-conversations.js --pane <sid> --pane <sid>    # only these

Every path is derived — the roster gives sid and cwd, `encodeCwd` gives the slug, the home slug is
`encodeCwd(os.homedir())`. **No path is typed anywhere in the file.**

**The ordering is the design, and it is the whole safety argument:** copy to a temp name → verify
the temp against the source's sha → *only then* retire whatever holds the destination name → rename
into place → read the placed file back → re-sha the original. **A bad copy cannot cost a seat the
transcript it already had**, because the retirement happens after the copy has been proved.

**The retirement is stamped** (`<sid>.jsonl.retired-20260912T081500Z`, with a counter if that exists)
and keeps the app's `.jsonl.<suffix>` shape rather than ending in `.jsonl`, so a retired transcript
stays out of the vendor's session list in that same directory. E's slug **already holds** a
`.jsonl.orphaned` from 06:29 tonight; a retirement under that fixed name would have destroyed it.
That is `main.rs:835-836` — a fixed archive name overwriting a seat's history — as a live near-miss
rather than a remembered one.

**The unit is the sid.** Nothing in the file lists a directory to decide what to move, retire or
count. C's slug holds two 525 KB scratch sessions that are not C's, and a test asserts their size,
mtime and sha are identical after a run.

### The one deliberate departure from §5

**§5 step 0 says REFUSE unless the app is closed. A LIVE run does. A DRY RUN does not.** A dry run
writes nothing, so a running app costs it accuracy, not safety — the "retire" column and the launch
table are read off a disk that live panes are still changing. Refusing there would force the keeper
to close the app merely to *look*, which prices the rehearsal step high enough to skip. So it runs
and says out loud that its reading is going stale. **The room's recurring failure is a reading
reported as a state; the fix is to label it, not to withhold it.** Both behaviours are mutation-
tested: removing the live refusal is killed, and so is removing the staleness note.

### What the mutation pass actually bought, because the first run is the finding

Run one: **14 killed, 4 SURVIVED.** The survivors were the read-back verification itself — the
placed file's sha, its byte count, its timespan, and the run-level failure on a bad placement could
each be replaced with `true`/`false` and the suite stayed green. The cause is structural and worth
naming: **`apply` verifies the copy before it commits, so by construction it never produces a bad
placed file, so no test could reach that code with one.** A verification nothing can exercise is a
printed reassurance — which is precisely what §5 step 5 was written against (*"verify by reading
back, not by reporting the copy"*), and I had shipped the reporting version.

Fixed by pulling the read-back out as `verifyPlaced(destPath, row)` and pointing it at files that
are deliberately wrong (same byte count / different content; truncated; a different conversation
entirely), plus one named injection seam so a test can make a placement fail and watch the run
refuse. Run two: **20 killed, 0 survived.** Also caught: an anchor that matched two sites and
reported `MUTATION DID NOT APPLY` rather than a false kill — the harness refusing to score itself
green, which is the only reason the first count was trustworthy enough to act on.

**Red-first, honestly:** the command existed before its tests, so there is no red-then-green
transition to show. The mutation pass is that evidence with the arrow reversed, and the four
survivors are what it was for.

**Two checks are redundant and are kept anyway, said rather than implied:** `okBytes` and `okSpan`
are subsumed by `okSha` — a differing byte count or timespan implies a differing hash. §5 asks for
all three to be printed, and they say *how* a mismatch failed. They are reports beside a gate, not
three independent gates.

## 4 · WHAT I DID NOT VERIFY

- **I never ran the placement for real.** The live path's writes are exercised only against
  fixtures. Against the real machine I ran `--dry-run` (twice) and read-only measurement — stat,
  sha256, first/last timestamps — over the four sources and the pane slugs. **No real pane's
  transcript was written, moved, retired or deleted by me.**
- **The retire path has never run against a 3.29 MB real transcript**, only fixture-sized ones. It
  is a same-directory `rename`, so size should be irrelevant — *should be* is the honest word.
- **Whether a placed conversation actually resumes IN THE APP is not tested.** §1 proves the vendor
  accepts a foreign-cwd transcript through `ptyprobe`; it does not prove `resume_pane` reaches that
  point for these four panes. E's registered launch falsifier covers that and **it has now been
  scored, and did not fire**: at 02:03 `persist.log` shows A, B and C `jsonl_existed=false -> fresh`
  (correctly — nothing was in their slugs) and E `jsonl_existed=true -> RESUMED`. `plan_resume`'s
  predicate matches the disk.
- **The app-running check is `tasklist`.** It cannot see an app that has just been closed but whose
  file handles are not yet released. A failure to *run* `tasklist` refuses a live run; a stale
  answer from it would not.
- **I did not touch `main.rs`** (E's this lap) or the 09-06 lap-row set. I did not commit.
- **`dev/` has no CHANGELOG entry**; nothing in `dev/` carries one, so I followed the surrounding
  practice rather than starting a convention in a hand-back.
