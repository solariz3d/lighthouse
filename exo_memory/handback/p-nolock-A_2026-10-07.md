## Step 1 — is there a setting? NO (cited)
- Chromium's mouse-lock design document (https://new.chromium.org/developers/design-documents/mouse-lock): exit instructions are shown after a lock; they are not shown only on a re-entry with no user gesture. It names no embedder flag, policy or permission that suppresses them. (Fetched 2026-10-07.)
- I found no WebView2 setting or `additionalBrowserArgs` switch that hides it, and the page lock is what raises it, so none of the route-1 options exist as a supported setting. I did NOT fetch the WebView2 settings reference page itself; "none found" is a negative from a search plus the Chromium document, not a read of the full WebView2 API list. A flag would likely be a security/feature switch anyway, which the packet excludes.
- Tauri v2 permissions (https://v2.tauri.app/reference/acl/core-permissions/): `core:window:allow-set-cursor-grab`, `-set-cursor-visible`, `-set-cursor-position`, `-set-cursor-icon`, `-cursor-position` exist; `core:default` does not include the setters.

## Route taken: 2, drop the lock — and why
No lock means no banner (the lock is the only cause). Kept the feel with:
- `setPointerCapture` on the press (it was already there) — a captured pointer keeps reporting its position outside the stage;
- `stage.style.cursor = 'none'` for the drag, restored on release;
- the value from the pointer's OWN position, not `movementX/Y`. Why: it is the same pixels D251 measured its rates in, so the per-px scales are unchanged by construction, and there is no first-move spike to drop. (The packet said "still reading movementX/Y"; I judged position the safer read of "feel unchanged". Say if you wanted movement.)
- Native, ONE call only: on release, `win.__TAURI__.window.getCurrentWindow().setCursorPosition(new LogicalPosition(pressX, pressY))` puts the cursor back at the grabbed handle. Permission added: `core:window:allow-set-cursor-position` only (no grab, no visible: CSS hides the cursor). No browser/test host has `__TAURI__`: then the cursor stays where the drag ended. A refused/failed call is a `console.warn`, not a throw (cosmetic, the drag is over).
- Esc: a `keydown` on the document ends the drag where it is (same as D251's Esc and as a release). It does not roll back.

## What this does NOT establish
- **No real window.** I did not run the app (rule: no real-window pointer test while the keeper may be at the PC; none was asked). So: that the banner is actually gone, that `cursor: none` hides it over the WebView, that `setCursorPosition` lands on the handle (client coords = window-inner coords is my reading of winit; with a title bar or a DPI scale the cursor could land off), and that the permission is accepted at runtime are all UNWITNESSED. The cargo build checks the permission id exists, not that the call works.
- **A cost the keeper should know:** a very long scrub now stops at the screen edge again (the lock existed to prevent that). At length 0.42 m/px a ~900 px sweep is ~380 m, so most scrubs fit; if he hits the edge, the next lever is native `setCursorGrab` + recentring, not built (it would fight the captured pointer's events and I could not witness it).
