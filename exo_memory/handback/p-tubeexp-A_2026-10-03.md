## (a) The folder
- `app/export/export.js`: `directChild(dir)` (exactly `…\content\tracks\<name>`, nothing deeper, the user's own path spelling kept for the parent), `exporter.resolveTarget(dir, storage)`, `removeEmptyNote`. A picked folder that is directly in `content\tracks`, not `t180b_*`, and reported EMPTY by `storage.folderIsEmpty` (must answer exactly `true`) exports into `content\tracks` as the normal `t180b_<track name>`; the parent must pass `checkTarget` too. Anything else (non-empty, deeper, a nested path whose parent is itself inside another track) is refused with the original message.
- `app/shell.js`, `app/core/coreshell.js`: both `exportTo` use `resolveTarget`; after the files are written the empty folder is removed (a failure to remove does not fail the export). **Removal happens only after a successful write**: a refused or failed export (an open track, a red) leaves the picked empty folder where it was (tested). That leaves a bug-shaped outcome the keeper can still hit: an export that fails on a red leaves his empty folder, which Content Manager lists. I chose not to delete a folder he made for an export that did not happen; the chair may overrule.
- `src-tauri/src/lib.rs`: two new commands, `folder_is_empty` and `remove_empty_folder`, registered in the handler. Native checks, again: `direct_foreign_track` (the same path rule), a real folder (not a link), `read_dir` empty; removal is `fs::remove_dir`, which the OS refuses on a folder with anything in it, so contents are never deleted. `app/index.html` adds the two storage entries.
