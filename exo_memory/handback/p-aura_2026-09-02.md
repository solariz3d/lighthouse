## 2 · WHY BAR 0 IS NOT EXECUTABLE FROM A PANE — the mechanism, four parts, each checkable

    consonance/src-tauri/tauri.conf.json:7      "frontendDist": "../ui"

The UI is bundled into the exe at compile time (brotli-compressed — see §8), so an edit to `ui/` changes
nothing a running window can see.

    consonance/launch.ps1:107-127   $sources includes (Join-Path $root 'ui')
    consonance/launch.ps1:148-159   if ($running) { ... exit 0 }   # "Windows locks a running exe"

A `ui/` edit makes the exe stale; the stale exe can only be replaced by a build; the build cannot run while
Consonance is up. **So the only way to get an instrument into the WebView is: keeper closes the app → rebuild →
relaunch.** That relaunch also restarts every pane, including this one.

No devtools in the release build, no console sink in `main.rs`, and no control-plane verb reaches the WebView
(`post_board` / `read_board` / `raise_pull` / `call_*` are all Rust-side). **There is no path from this seat to
the rendered DOM.** That is a fact about the harness, not a refusal.

**The packet's premise — *"A lap is open now (L029), so it is testable immediately"* — is true of the LAP and
false of the SEAT.** The lap being open is necessary and not sufficient; what Bar 0 needs is an eye on the
screen.
