## 4. The hashed segment key: can two different docs collide so the ghost is stale?

- **In practice, no.** On a pool of **2,471 real segments** (a 4-piece tube track, the same after a brush and after an undo, a bowl
  track, a half-pipe track), **1,069 distinct by JSON = 1,069 distinct by key**: no collision and no split (S5). A's row 6 also shows,
  on a real brush, that exactly the segments whose JSON changed got a new key.
- **In principle:** the key is two non-cryptographic 32-bit mixes over the same input (FNV-style and a multiply-xor), so it is
  not a true independent 64 bits. A stale mesh needs a CHANGED segment to hash to its own old key. Even at 32 effective bits, that is
  about 2^-32 per changed segment per update, too rare to plan for. An adversary is not part of the threat model.
- **A test gap (owner A, not blocking):** my plant **P6, the key ignoring each number's HIGH 32 bits** (sign, exponent, top of the
  mantissa), **survived both A's row 6 and my pool.** The real code mixes both words, so this is a missing assertion, not a
  defect. But under P6, `1` and `2` (or `0.5` and `−1`) hash alike, because their low words are all zero, and nothing would notice.
  The fix is one line in row 6: `assert.notEqual(keyOf({ a: 1 }), keyOf({ a: 2 }))`, and the same for a sign flip. Also: P8 (h2
  dropped, a 32-bit key) is caught only by row 6's FORMAT regex (`/^[0-9a-z]+\.[0-9a-z]+$/`), not by any collision. That's fair, since
  no test could find a 2^-32 collision.
