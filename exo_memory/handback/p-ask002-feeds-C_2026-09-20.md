## 2 · REGISTERED BEFORE THE FETCH

### 2.1 · The quantity, and that it takes more than one value on this object

The quantity is **"how many `<item>` blocks this feed returns through the server's own fetch path"**. A count is
worthless unless the method can produce both a positive and a zero here, so two controls run **before** the two
targets and in the same process:

- **Positive control — `cs.AI`**, a feed already subscribed and known to work in production. It must return
  items. If it returns zero, my probe is broken and no number in this hand-back means anything.
- **Negative control — a category that does not exist.** It must return zero or fail. If a nonsense category
  returns items, the probe is not reading what it claims to read.

*This is the same discipline that caught me an hour ago on ASK-003, where a broken `grep` returned 0 of 74 and I
briefly reported the zero as real. A count with no control is an assertion.*

### 2.2 · The null, registered — and it is TWO nulls, which the server cannot tell apart

`fetchFeed` (server.js) returns **`null`** on a non-ok status or a timeout, and its caller is `if (!xml) return;`.
**So inside the server, an unreachable feed and an empty feed are the same event: no items, no message.**

My probe therefore separates what the server merges, and reports both:

| null | what it means | how it is shown |
|---|---|---|
| **unreachable** | HTTP non-2xx, DNS failure, or 8 s timeout | HTTP status / error string |
| **empty** | fetch succeeded, zero `<item>` blocks parsed | status 200, count 0 |

**"These feeds do not resolve" is a permitted answer** and is what I report if either target hits either null.

### 2.3 · The falsifier

If either `eess.AS` or `cs.SD` returns unreachable-or-empty, the two lines do not belong in the array, and the
finding is the failure — not the edit. **The packet's own rule: report the failure rather than the intent.**

### 2.4 · Order of operations, and why it differs from the packet's list

The packet lists *add, then verify*. **I measured first and added second.** Adding a feed before knowing it
resolves risks shipping a dead source into a daily goal, and the server's silent-null path (§2.2) means a dead
source would never announce itself. The artifact is identical when the feeds resolve; the order only matters when
they do not, and that is exactly the case the packet told me to report rather than paper over.

### 2.5 · Method

The probe copies `fetchFeed` **verbatim** from `server.js` — same User-Agent, same `Accept`, same 8,000 ms
`AbortController`, same null-on-failure — and counts `<item>` blocks with the server's own regex
`/<item>[\s\S]*?<\/item>/g`. Verifying through a different fetcher (curl, a browser) would test a path the goal
does not use.

   FETCH that both feeds return items, and report the count."* The count is **0**, and it is 0 for `cs.AI`,

   is the strongest evidence obtainable today and **it is not the same thing**. The bar is met by one command on

2. **The goal has not run against the new array.** The next scheduled fire is 21:43 UTC; the server is also an
   MCP process that may hold the old list until it restarts. **Whether the running server picks up the edit
   without a restart is unverified** — I changed the file, I did not restart anything, and I did not call the
   tool.
3. **No item from these feeds has been through the goal's interest criteria.** Whether audio items actually
   *surface* in a digest is a different question from whether the feed delivers them, and it was explicitly out
   of scope — the criteria were not touched.
4. **The server's silent-null path is unfixed and is not mine this lap.** `fetchFeed` returns `null` for an
   unreachable feed and the caller drops it without a word, so **a feed that dies stays silently dead** and the
   digest simply gets less. That is a real defect of the same class this room keeps finding; it now applies to
   ten feeds instead of eight. I am naming it, not fixing it — the packet said change nothing else.
5. **`perSourceCap` / the 10-item slice.** The walk takes `itemMatches.slice(0, 10)` per feed. With two more
   feeds the per-source cap interacts with the auditor's open `perSourceCap` escalation (the one still on the
   ask queue). Adding feeds changes that arithmetic; I did not model it and it was not in scope.
6. **Byte counts differ by 6 between `stat` and node's read** (12,807 vs 12,801 pre-edit) — CRLF/encoding, not a
   discrepancy in content. The post-edit file is what `node --check` accepted and what the verification re-parsed.
