## 2. The shared interface: where I fixed an ambiguity, and where the docs disagree (no silent divergence)

1. **UV convention was unstated.** I fixed it, and the fix is written in `scene.js`'s header: the scene holds the
   usual image convention (v = 0 at the image's bottom), and the writer stores `1 − v`.
   - Why: kn5 stores DirectX-style UVs. blackbox uploads textures with no Y flip (`grep FLIP_Y` over blackbox → 0 hits)
     and reads kn5 UVs raw.
   - Not settled: `−v` against `1 − v`. The two measured tracks do not settle it. Their V ranges are
     [−19.34, 1.26] and [−0.99, 410.08], opposite signs, so they come from different exporters (inferred).
   - The two forms differ by exactly 1, which is invisible under wrap addressing and not under clamp (inferred).
   - C's platform UVs are tiled, so either form renders the same there.
2. **Transpose: there is none to do.** The interface gives matrices "in kn5's stored order (translation at [12..14],
   as tools/kn5.cjs reads it)", so the writer writes them as given.
   - The "transposed matrices" of ARCHITECTURE §6 and research 01 is the step from Blender's column convention into
     this order. It belongs to whoever builds the scene.
   - So the packet's "drop the transpose" mutant is **NOT APPLIED**. Its inverse (M2b, "add a transpose") is applied
     and caught.
3. **Winding: kept as given, and measured.**
   - Research 01's "use triangle winding (1, 2, 0)" is a cyclic rotation of (0, 1, 2). **It does not reverse a
     triangle.** So Blender's CCW-outside order reaches kn5 unchanged.
   - Measured, read-only, with `scratchpad/d165/measure_kn5.js <kn5>`, which tests each triangle's (p1−p0)×(p2−p0)
     against its stored normals in local coordinates:
     - `ohyeah2389_t180testtrack.kn5`: **938,068 CCW / 4 CW**;
     - `t180_bowltrack.kn5`: **94,283 CCW / 41 CW / 51 degenerate**.
   - This matches the interface's "CCW seen from outside".
   - C's generated platform scene: **394,304 CCW / 0 CW** (inline `node -e` walk over `buildPlatformTest()`).
4. **The vertex cap is 65,535, per ARCHITECTURE §3** ("under 65,536 vertices each") and the packet. Research 01 §1 says
   "at most 65,536", which is also what 16-bit indices can address. ARCHITECTURE is the master, so I followed it; the
   research line is looser by one.
5. **0-triangle meshes are REFUSED** (`EMPTY_MESH`). The byte format could encode one, since the counts are simply 0.
   I refuse it anyway: there is no vertex to make a bounding sphere from, and nothing says AC loads one. **C and E
   must not emit empty cells.** This is my choice, and the librarian or ARCHITECTURE can overrule it.
6. **Refusals beyond (c):**
   - a duplicate texture name;
   - a sampler naming a texture not in `textures`;
   - a mesh node with children (research 01: "Mesh nodes cannot have children");
   - a prop whose value is not 1–4 floats;
   - non-finite vertex or matrix values;
   - a root that is not a dummy;
   - bad flags and bad array types.
7. **A prop of n floats fills slot n.** kn5 stores 10 floats per prop: A (1), B (2), C (3), D (4). Measured: 34 of the
   52 props on the first track use A only and 18 use none; the second track has one B.
8. **The writer computes what the scene does not carry:**
   - **tangents:** per-vertex sums of d(position)/du, orthogonalised against the normal, as real tracks store them
     (median |t·n| = 8.8e-9 on the first track);
   - **the bounding sphere:** the box centre, and the farthest vertex with the radius rounded up to the next float32;
   - **layer 0, lodIn 0, lodOut 0, every node active 1, texture active 1:** the values the measured tracks use (the
     second has lodOut 1000 or 10000 on 4 of 25 meshes).
9. **Two findings from the real files that the interface does not model:**
   - **Both reference tracks are version 6** (with the extra int = 0). We write 5, per ARCHITECTURE §6.
   - **Every `AC_` marker in both tracks has exactly one child**: a 24-vertex, 12-triangle box mesh with the marker's
     own name (77/77 on the first, 19/19 on the second), most likely an exporter's display gizmo (inferred).
   - Our markers are childless dummies, as the interface says. **Whether AC accepts childless markers is unverified.**
     T1's install and T2's launch will show it.
10. **Strings** are an int32 byte length and then UTF-8 bytes, as `tools/kn5.cjs` reads them. blackbox reads them one
    byte per char (latin1), so the two readers disagree on non-ASCII names. Whether AC reads names as UTF-8 is
    unverified. **Keep names ASCII** for anything that must work in AC. The test uses one non-ASCII material name only
    so that the length mutant can bite.

## 3. Tolerance, stated before the first run (it is also in the test file's header)

- **Local positions and normals: exact.** They are written verbatim as float32.
- **World positions and marker pos/fwd through `tools/kn5.cjs`: exact (tolerance 0).** The expectation composes the
  float32 matrices in float64, in kn5.cjs's order.
- **u: exact.**
- **v: not exact**, because 1 − v is stored as float32. The bound is |Δv| ≤ 2⁻²³·max(1, |v|).
- **Float32 positions are exact, and the reason is simple:** the writer never does arithmetic on them. It copies the
  scene's float32s into the file.
