## 1. The bug, as found (L122 land hand-back §3)

- `<data>/heavy-run.lock` held pid 27836, a `js-suite` from 06:42:17Z.
- Windows had given that pid to another program's crash handler, which started 06:42:22Z.
- `pidAlive` (`process.kill(pid, 0)`) read it as alive. The next runner would have waited 30 minutes and failed, so
  the lock was moved aside by hand.

## 2. The design

**The identity is recorded at acquire, with no spawn:**
- `image` = `path.parse(process.execPath).name`, i.e. `node`;
- `holder_start` = `Date.now() − process.uptime()·1000`.
- **Seen on the real lock** during this lap's suite run: `"image":"node","holder_start":"2026-09-27T11:52:48.415Z"`,
  39 ms before its `started`.

**The identity is asked of the OS only when needed:** when a lock HAS identity fields AND its pid reads alive.
- **The query:** `processIdentity(pid)` runs `powershell -NoProfile -NonInteractive -Command "$p = Get-Process -Id <pid> … $p.ProcessName + '|' + $p.StartTime.ToUniversalTime().ToString('o')"`.
- **Why this source:** it is the query the codebase already uses for the same question (`whats-live.js:50-52`, `Get-Process … StartTime`).
  `wmic` is deprecated on current Windows, and Node's standard library has no start time for another pid.
- **Windows only.** Elsewhere, or on any failure, it returns `null`.
- **The pid is validated as a positive integer before it reaches the shell.** The lock is a file, so it is input.

**The decision** (`sameHolder(h, id)`), for a live pid:

| the OS reports | verdict |
|---|---|
| a **different image** (case-insensitive) | **STALE** — `took_over.reason = "pid_reused"`, plus `took_over.now_running = {image, start}` |
| the same image, **start more than `START_TOLERANCE_MS` (10 s) from `holder_start`** | **STALE**, `pid_reused` (a later process of the same kind took the pid) |
| the same image, start within 10 s | **HELD**, as today |
| nothing (`null`: the query failed, not Windows, or no such process) | **HELD**: failing to look is never a reason to take a live lock |

**Unchanged:**
- **A dead pid** is STALE as before, and the OS is never asked (`took_over.reason = "dead"`).
- **An unreadable lock** is handled as before (`reason = "unreadable"`).
- **An OLD-FORMAT lock** (no `image`, no `holder_start`) is **never probed and behaves exactly as today**: a live pid is
  held, then there is the 30-minute loud failure. Tested (§3).

**Cost:** one PowerShell call, about 262 ms measured. A waiter re-asks about the same holder at most once per
`IDENTITY_RECHECK_MS` (60 s), not on every 2 s poll. Tested.

**The takeover path is the existing one**, logged and recorded in `took_over`. The log line for this case:
`heavy-run: took over a stale lock — <holder>: pid N is now <image>, started <t> — the pid was reused (the lock recorded node, started <t>); it was Nm old`.

- **On "never deleted", named:** the existing path renames the stale file aside, records its holder in the new lock's
  `took_over`, logs it, and then **unlinks the renamed file**.
  - An existing test pins exactly that: "the stale lock set aside is not left behind", `readdirSync(d)` → `[]`.
  - The header gives the reason: a new file in the data dir is UNPLACED at close until the manifest names it.
  - **I kept that path unchanged, as the packet also says.** The holder's details survive in `took_over` and the log,
    not as a file. If a kept file is wanted, it needs a manifest row too, which is a separate change.
- **The header's old sentence** ("a REUSED pid reads alive — the waiter waits … fails loudly") is corrected: it is now
  true only for old-format locks.

**Measured tolerance headroom:** the OS start minus the recorded start for this process was **−57 ms**, three times
(`node -e` with `H.processIdentity(process.pid)`). The 10 s tolerance is about 175× that.

**Not caught, named:** a pid reused by the **same image** within 10 s of the original holder's start (the holder would
have had to die inside those 10 s).

  1. a live pid, **different image** → stale, logged as reused, `took_over.reason` and `now_running` recorded;
  2. a live pid, **same image, start outside the tolerance** → stale;
  3. the **same process** (image matched case-insensitively, start inside the tolerance) → held, times out, lock
     untouched;
  4. a **dead pid** with an identity lock → stale, and the OS is not asked;
  5. an **old-format lock** with a live pid → held, times out, **OS asked 0 times**, lock untouched;
  6. an **unknown identity** (`null`) → held;
  7. the OS is asked **at most once per recheck interval** (3–4 times over three intervals of 2 s polls);
  8. **REAL:** `processIdentity(this pid)` agrees with the identity this process records (same image, start within the
     tolerance), and `sameHolder` says true;
  9. **REAL:** `processIdentity` of a non-existent pid → `null`; of a non-integer → `null`; of **a PowerShell
     injection payload that would print a parseable identity if it ran** → `null`; of pid 0 → `null`.
- **The one existing test changed, named:** "the lock holds {pid, seat, cmd, started} (and the token)". Its exact key
  list gains `holder_start` and `image`, and its title says so. **It was verifiably out of date by the packet's own
  requirement** (the lock must record identity). No other existing assertion was touched: the diff's `-` lines are that

- **End to end, real OS, no fakes:** a temp lock naming the pid of a live `explorer.exe`, recorded as `node` → acquire
