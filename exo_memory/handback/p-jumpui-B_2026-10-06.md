- `JUMP_UNSOLVABLE`

`jumpplan.js jumpWords` has a case for each. The PAST_VERTICAL split keys on "the road before the jump", which is in `resolve.js:64`'s text, so both variants route correctly. The BAD_JUMP split re-tests the same bounds the core uses: gap > 0, drop finite, |land| < 90° against the core's < π/2.

`addJump` catches a `CoreError` and only calls `set({ message })`. It never calls `commit`, so there is no history change and no undo step.

The fields parse consistently. An empty drop or landing field is 0, written into `jumpFor`. An empty gap is `Number('') = 0`, which gives the gap words.

## The dashed arc against the validator's landing check
**The arc lands where the check says it lands.**

Probe: `jumplook/arcprobe.js` (output `arcprobe.json`), under the lock. On the merged tree:
- five builds, each read right after Add jump and again after the next Extend (10 cases × 2 falls);
- the arc comes from `jumpplan.flightsOfPath`;
- the check is `V.validate(path, segments, { designSpeed: 460/3.6 })`, reading `jumps[].landings`.

Results:
- **Gap:** the arc's D equals the validator's gap in every case.
- **Clear / not clear:** agree for all 20 falls.
- **Touchdown x:** the arc's and the validator's agree to **0.003–0.031 m**. The validator interpolates on the 2 m sampled ramp; the arc uses `landingRamp`'s exact root.
- **Red:** `landing-misses-zone` is red exactly in the cases where the arc draws a fall that does not reach the landing:
  - 30 m on a flat take-off: 6.3 g misses;
  - 120 m / 3 m / −3°: 6.3 g misses.

  It is never red otherwise, including 30 m off a 0.002 climb.
- **Default 20/1/−2:** 3.2 g comes down at 43.53 m (validator 43.52 m), 6.3 g at 24.86 m (24.83 m). Both are caught, with no red. This confirms A's reason for moving the default from 30 to 20.

Limit: the arc is drawn at 460 km/h whatever the speed box says. At another validation speed the check can go red while the arc stays cyan. A's words say so ("Validation is using N km/h…"); I did not probe that case.

## The F3 nit: "SCULPT_MOVES_CENTRELINE:" at the start of the Sculpt message
**This is not Sculpt-specific, so don't drop it alone on this land.**

The prefix comes from `CoreError` itself: `document.js:48`, `super(\`${code}: ${message}\`)`. The shell's `attempt` shows `e.message` as it is. So **every** core refusal the page shows starts with its code. I saw `CLOSE_WINDOW: close: can't close…` in my own real window on 2026-10-06. Line `:327`'s end-of-drag message also writes the prefix as a literal.

The jump refusals are the one place that strips it, because `jumpWords` rewrites the whole sentence.

Dropping it from Sculpt alone would make a third style. The clean fix is a separate small lap:
- strip `^[A-Z_]+: ` once where the shell shows a `CoreError` (`attempt`, plus the `:327` literal);
- amend by name the regexes that pin the prefix (`core-sculpt.test.js:101/:110/:115/:169`, and the CLOSE_WINDOW/close ones).

My recommendation is yes, do that lap, because the keeper reads codes as noise. But that is the chair's call, and it is not a blocker here.
