## 1 · The code path, read

- **Recording** (`heavy-run.js:74-76`): `image = path.parse(process.execPath).name` and
  `holder_start = Date.now() − process.uptime()·1000`. No spawn. `self` is computed once per `acquire` (`:126`) and does
  not drift while waiting.
- **Asking** (`:77-89`): `powershell -NoProfile -NonInteractive -Command "$p = Get-Process -Id <pid> …;
  $p.ProcessName + '|' + $p.StartTime.ToUniversalTime().ToString('o')"`. It runs with `timeout: 20000`,
  `windowsHide: true` and stderr ignored. The pid is validated as a positive integer first, so nothing but digits reaches
  the command string. On any throw, off Windows, or with no `|` in the output, it returns **null**. If only StartTime
  throws (a protected process), the start is null and the image survives.
- **Deciding** (`:92-98`, `sameHolder`): null identity → same holder. A case-insensitive image mismatch → different.
  Both starts parse and differ by more than `START_TOLERANCE_MS` = 10 s → different. Anything else → same.
- **Asked when** (`:155-161`): only if the pid is alive AND the lock has an identity field. It is cached per holder
  token and re-asked at most every `IDENTITY_RECHECK_MS` = 60 s.
- **Taking over** (`:162-184`): rename aside; a race check that puts a live lock back with `linkSync`; **unlink the
  aside file**; `took_over` in the new lock gets `{holder{pid,seat,cmd,started}, age_ms, reason, now_running}`; one
  stderr line names both identities.

**The edge the chair asked for** (F6, F7): a failed or timed-out lookup returns null, and null counts as the same holder.
The lock is held, the waiter keeps polling, and at the max wait it fails loudly naming the holder. **That is the safe
direction.** The cost is that a reused pid on a machine where PowerShell can't answer goes back to the pre-fix
behaviour: a 30-minute wait and a loud failure, never a silent double run. A slow lookup blocks the poll loop
synchronously. Worst case, the 20 s timeout, re-asked at most once a minute. That delays a waiter but never a holder.

## 3 · "Moved aside and named, never deleted": the brief's words, not A's

**The stale lock IS deleted.** In every takeover (F1, F2, F3d, F4, F5b, F8b), `readdirSync(<tmp>)` right after
`acquire` lists only the new `heavy-run.lock`. The aside file is unlinked at `:173`. Once the new holder releases, the
new lock goes too, `took_over` with it. **So on disk nothing of a takeover survives the next release.** It survives in
the stderr line, and in `took_over` while the lock is held.

**A's hand-back already says this plainly** (`p-l124-heavyrun-A_2026-09-27.md:50-52`: *"…and then unlinks the renamed
file. An existing test pins exactly that"*). "Named" holds: both the log line and `took_over` name the old holder. "Never
deleted" does not. I flag it only so the phrase doesn't travel into a later brief. Keeping the aside file would put a new
file in the data dir, which is UNPLACED at close (the design note at `:24-26`). So the deletion looks deliberate, and
right.

A small gap, not a defect: `took_over.holder` keeps pid, seat, cmd and started, but not the old lock's recorded `image`
or `holder_start`. Those appear only in the stderr line.

## 4 · Residual risks — named, not blocking

1. **A slow boot reads as reuse.** `holder_start` is node's own start, and the OS's `StartTime` is process creation.
   On this machine they differ by 16 ms against a 10 s tolerance (H0). If a node process took more than 10 s from
   creation to `acquire` (antivirus scanning `node.exe` at launch, a thrashing disk), a **genuine live holder** would
   read as `pid_reused` and be taken over. Two heavy runs would follow, which is the unsafe direction. I could not
   produce that delay; it is a stated limit, not an observation. A fix, if ever needed, is to record the OS's own
   StartTime for `process.pid` at take time (one PowerShell call, ~250 ms, once per run) instead of `uptime`.
2. **Reuse by the same image within 10 s is not caught** (F3c shows the window). A's comment at `:70-71` names this
   honestly ("named, not claimed").
