## 3 · THE WRITE — designed, not done

### 3.1 The rows that can be lost, and who writes them

`board.jsonl` has more writers than the app. A coarse grep (a file names `board.jsonl` and uses an append API; not
traced call by call) finds `main.rs`, the hooks `baton-wake-stop.js` and `blind.js`, and `lap-row.js`, `ferry.js`,
`librarian-cite.js`, `read-ledger.js`, `state-sync.js` and `board-compact.js`. **Hooks run inside live pane sessions,
so closing the app does not stop every writer.** "Rewrite with the app closed", my working plan before this
measurement, is not safe on its own. `lap.jsonl` has one writer, `lap-row.js`, through `appendFileSync`, with no lock.

### 3.2 Recommended: the swap protocol that already exists, `board-compact.js:290-366`

The repo already solved "rewrite a live-appended JSONL without losing a row." Reusing it follows the existing pattern
and adds no new mechanism:

1. **Read and remember the byte offset.** Write the union to a temp file next to the target.
2. **Catch up** (`catchUp`, `:130`): up to 8 passes from the offset to the current end, complete lines only, appending
   any row not already in the union. Stop when a pass adds nothing and the size has not moved.
3. **Freeze:** `rename(target → attic/<name>.<stamp>)`. **Refuse if that attic path exists** (`:336`). The original
   becomes the record, untouched.
4. **Re-created file:** if a writer created the target between the renames, carry its rows (`:346-350`).
5. **Swap:** `rename(tmp → target)`.
6. **Reconcile:** whatever the frozen original gained after the last read offset is appended to the new target
   (`:355-362`). It is compared against a frozen file, not raced.

**Order stays right for readers.** The union is sorted by time, and every row caught in steps 2, 4 or 6 is newer than
anything in it and lands at the end. So `board-digest`'s 2 MB tail (`board-digest.js:41`) still ends with today's rows.

**The same protocol serves `lap.jsonl`.** With one writer and a 73 KB file, the window is smaller still.

### 3.3 Rejected, with reasons

- **Board append-only (missing rows appended at the end):** 3.07 MB of old rows exceeds `board-digest`'s 2 MB tail. Every
  pane digest would lose today's board until 2 MB of new rows accumulated.
- **Lap append-only:** safe against loss, since one `appendFileSync` cannot erase a concurrent append. But file position
  would stop matching time, and two readers use position: the baton gate at `lap-row.js:862` takes `prior[prior.length-1]`,
  and `map`/`opened` take `mine.find(open)`, which is the FIRST open row in the file. Acceptable only if nobody stages
  L058–L065 again. The tripwire in §4 now refuses to mint them, but it cannot stop a hand-typed `--lap L058`. The swap
  keeps time order, so it is preferred.
- **A lock:** `lap-row` has none, and the board's writers are spread across the app, hooks and tools. A lock that only
  some writers honour protects nothing. The swap needs none.

### 3.4 What the keeper sees after the write: 8 DOUBLE-OPEN ids

The union keeps every generation as its own row under its original id. `laps()` folds by id, and
`lap-row.js:348` files an id with more than one `open` row as `DOUBLE-OPEN`. On the union file, **8 ids**: L058×8,
L059×5, L060–L065×3 each. The live ledger has 0. `map`/`opened` on those ids would bind to the first generation in the
file. **"No renaming" means this is permanent unless a later ruling adds a disambiguating field.** That is keeper-level,
so I'm stating it and leaving it alone.
