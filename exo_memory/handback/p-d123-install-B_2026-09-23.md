## 2 · WHAT EACH PART DOES, AND WHAT PINS IT

### install.js
- **It merges, never replaces.** Jev's two entries are appended as **their own groups**, at the end of `Stop` and `UserPromptSubmit`. Every other key, event and group is carried over.
  - It is written back in the file's own layout: indent, CRLF/LF, trailing newline, BOM.
  - **Pinned:** the installed file, with Jev's two groups taken out, is the original **byte for byte**. A CRLF 4-space file keeps both. A BOM is kept.
- **Exec form**, `{type:"command", command:<node's absolute path>, args:[<script>], timeout:10}`. See §3.3 for why and what is unverified.
- **Jev's entries are recognised by the script's absolute path, never by file name.**
  - Case-insensitive with either slash on win32, exact elsewhere; the test drives `platform`.
  - **Pinned:** the room's own `hooks\jev-flags.js` (same name, different file) is never touched by install or uninstall. The install prints a note that both will run.
  - **The price:** an install made from a checkout that has since moved is not recognised as Jev's.
- **Idempotent.** A second install **writes nothing**: same bytes, **same mtime**, no new backup. An entry that is Jev's but pointed at an old node is re-pointed in place, not duplicated.
- **Reversible.**
  - Before every write it copies the file to `settings.json.bak-jev-<stamp>`, the room installer's rule.
  - The first install records **which backup holds the pre-install file** in `~/.jev/install.json`. It records the path only, **never the content**, because settings.json can hold secrets and they are not copied out of `~/.claude`.
  - `--uninstall` removes Jev's entries. If what is left equals the pre-install content, it writes **the pre-install bytes**.
  - **Pinned:** a byte-exact restore of a 2-space file, a CRLF 4-space file, an `"hooks": {}` that was there before, and a **compact one-line file even after a second, writing install**. That last test proves the record keeps the *first* backup.
  - If the user changed the file since, only Jev's entries leave and the run says the restore is **not** byte-exact.
  - A settings.json that didn't exist before is removed again.
- **Refusals are loud (exit 1) and write nothing:**
  - no `~/.claude`;
  - a file that doesn't parse;
  - `hooks` or an event of the wrong shape;
  - **pinned:** file bytes unchanged, no backup, no record, both for install and uninstall.
  - A write that doesn't read back as intended is undone from the backup.
- **`home` has no default** in `install()` / `uninstall()`; only the CLI passes `os.homedir()`. A test pins that a missing home throws. The CLI test spawns with `HOME` and `USERPROFILE` pointed at a temp dir.

### jev-judge.js
- **The move comes from `last_assistant_message` when present.** It travels **on the child's stdin pipe**, never the command line (visible to process listers, length-capped on Windows) and never a file.
  - **Pinned:** the spawn's argv carries no move, and the pipe carries exactly `{last_assistant_message}`.
  - A payload with no move still closes the pipe.
  - **A real hook process delivered the move to its detached child:** the child got past the view to ask()'s key refusal, which it can only reach if the move arrived.
  - Capped at 8,000 characters, as the room's view caps it.
- **The user context** with the payload's move is the transcript's most recent user text. It skips tool-result-only rows, and it isn't the lagging row, because the prompt was written when the turn began.
  - **Pinned:** it equals A's `buildPrompt` over `{assistant_move: <payload>, user_context: 'the second prompt'}`.
- **Dedupe follows `prompt_id` when the payload has one**, and falls back to the transcript as batch 1 did.
- **`confidence` is in every row**: from what `ask()` returns, else `null`, never invented (§3.2).
- **Every row now has 11 keys:** `ts, session_id, turn_uuid, prompt_id, verdict, probabilities, confidence, reason, model, prompt_sha256, usage`. `jev.log` lines gain `prompt_id` too, so a failure can be traced to its turn even when the end row never showed.
