## 1 · ROW 4, WHAT IS BUILT

- **The app's own main window is subclassed** (`watch_session_end`, installed in `.setup()` on the UI thread, which is
  the thread that created that window). `SetWindowSubclass` chains, so tao still sees every other message.
- **`session_end_proc`** handles three messages:
  - **WM_QUERYENDSESSION** — takes the block reason, starts the fast Leave on another thread, and answers at once:
    `FALSE` ("not yet") normally, `TRUE` when `lParam` carries `ENDSESSION_CRITICAL`, which cannot be blocked at all.
    A second query starts no second Leave (`SHUTDOWN_LEAVING`).
  - **WM_LEAVE_DONE** (`WM_APP + 0x51`), posted by the Leave thread when the save is finished: it releases the block —
    on this thread, the only one allowed to — and exits the process so the session can end.
  - **WM_ENDSESSION** — the session is ending; logged, nothing blocks.
- **The reason string** is one short sentence, `"Consonance is saving this session to the stick."`, because Windows
  truncates it and the keeper reads it on the shutdown screen.

## 2 · WHAT WINDOWS GUARANTEES HERE, AND WHAT IT DOES NOT

Read at source on 2026-09-15, not from memory. Quotes are Microsoft's.

| # | The rule, quoted | What it means here |
|---|---|---|
| 1 | *"Applications can delay responding to WM_QUERYENDSESSION for 5 seconds, then the system allows the user to continue or cancel shutdown."* | **The 5 s is the ANSWER budget, not the work budget.** The proc answers immediately and does the work on another thread, so the app never reads as hung. |
| 2 | *"the system does not allow console applications or applications without a visible window to cancel shutdown. These applications are automatically terminated if they do not respond … or if they return FALSE."* | **This killed my first build** (§4). A hidden window's FALSE is not a block; it is a 5 s stay of execution. Hence the app's own visible window. |
| 3 | *"This function can only be called from the thread that created the window"* — both `ShutdownBlockReasonCreate` and `…Destroy` | Both calls live in the proc. The Leave thread cannot release the block, so it asks by posting WM_LEAVE_DONE. |
| 4 | *"If any application returns zero, the session is not ended. The system stops sending WM_QUERYENDSESSION messages as soon as one application returns zero."* | Our FALSE **cancels that shutdown attempt**, it does not pause it. After the fast Leave the app exits, and **the restart does not resume by itself** — Windows Update retries later. Named as a cost in §3. |
| 5 | *"If an application returns FALSE … it still appears in the shutdown UI"* with its reason, and the user decides | The keeper sees why, and can override. |
| 6 | *"Applications cannot rely on being able to block shutdown."* And `ENDSESSION_CRITICAL` = *"The application is forced to shut down."* | A forced end is answered TRUE at once and the Leave races the kill. **An EWX_FORCE shutdown sends no message at all** and nothing in this lap can help there. |
| 7 | — | **NONE OF THIS VETOES A WINDOWS UPDATE RESTART, and it would not have saved tonight.** The control that stops tonight's cause is a policy on the keeper's machine (active hours / NoAutoRebootWithLoggedOnUsers), and it is his to set. |

**If the fast Leave exceeds what Windows allows:** the process is killed mid-Leave. `stick-leave.started.json` is on
disk by then, so the next launch reads **case c** — "the app died mid-save" — instead of a silent hole. That is the
one guarantee this design can actually make.

## 3 · THE FAST LEAVE: WHAT IT DROPS

**It is the same Leave.** `leave_run` now takes a `LeaveBounds`, and there is exactly one of it (a test asserts that).

| bound | keeper's close | OS's end of session | what the difference costs |
|---|---|---|---|
| spawns in flight | 10 s | **1 s** | a seat still starting is NAMED in the record as NOT DONE instead of waited for |
| seat teardown | 5 s | **1.5 s** | the seats are killed either way; the wait only proves they are gone. A seat still alive is named |
| the export | 600 s | **20 s** | at the bound the export is NOT_DONE with its reason, and LEAVE_STARTED stays on disk |

**What it drops is waiting, never the save** — the packet's "prefer the stick export over completeness". A test
asserts each shutdown bound is shorter than its ordinary one and that the export keeps more than twice the two waits.

**Costs I am naming rather than hiding:**
- **The 20 s export bound is a judgment, not a measurement.** The one measured carry is 348,026,190 B in 55 s, and
  that was the FIRST carry; later ones carry a tail. A tail bigger than 20 s of writing is cut, and reads NOT_DONE.
- **After the fast Leave the app exits** (rule 4 above), even if the keeper cancels the shutdown at the blocking
  screen. I chose the record over staying alive. Seats resume on the next launch.

  on its own thread and answered FALSE from there. The documentation says an application without a visible window

  5 s with the Leave half-run. I rebuilt it on the app's own window and re-pointed the test.
  - The second, quieter half of the same error: `ShutdownBlockReasonDestroy` from the Leave thread would have failed
    with ERROR_ACCESS_DENIED, and the block would never have been released. That is why the release is posted back.
  - **Both were found by reading the docs, not by a test.** No test I can write on this machine would have caught
    either, which is exactly why they are in this section.
- **E's three pins were re-pointed, and I say so because they are E's.** They cite the literal constants that ROW 4
  parameterised (`SPAWN_FLIGHT_POLLS`, `SEAT_TEARDOWN_POLLS`, `LEAVE_EXPORT_TIMEOUT` at the call sites). Each keeps
  its guarantee and gains one: the call now reads `b.flight_polls` / `b.seat_polls` / `b.export`, and a new assertion
  beside it says `LeaveBounds::NORMAL` still carries the measured constant, so the keeper's close is unchanged.
- **The keep-awake hold was released at the start of every save, and my tests were green.** The pure decision was
  right and the pin passed; the input was wrong. Nothing in the suite compares a seat count to what the Leave does to

- **My ROW 5 string sweep had two false positives of my own making.** It read Rust generics (`OnceLock<AppHandle>`) as

  pieces. The sweep reads STRINGS, not comments — a comment explaining what Windows does is not a claim to the keeper.

## 5 · ROW 5, WHAT IS BUILT

- **One long-lived thread** (`keep_awake_thread`), because Windows drops an `ES_CONTINUOUS` state when the thread that
  set it exits. It polls every 2 s.
- **A RUNNING LEAVE COUNTS AS WORK, not just live seats.** `leave_run` drains Panes BEFORE it saves, so the seat count
  reaches zero at the moment the export starts — the longest thing this app does. Counting only seats would drop the
  hold exactly when it is most needed. Found by re-reading my own code, after the tests were green (§4).
- **The decision is pure and tested**: `sync_launch::keep_awake_transition(held, seats)` — take the hold on the first
  live seat, release it when the last ends, do nothing otherwise.
- **The hold is `ES_CONTINUOUS | ES_SYSTEM_REQUIRED`; the release is `ES_CONTINUOUS` alone.** `ES_DISPLAY_REQUIRED`
  appears nowhere in the source, and a test asserts that: **the screen still sleeps.**
- **Said plainly, in the app and here:** this prevents IDLE SLEEP and nothing else. No application can veto a Windows
  Update restart. A test sweeps every string the app can show (Rust literals, `ui/*.js`, `ui/*.html` text) and fails
  if one claims otherwise; a second test shows the sweep catches the claim and lets the true sentence through.
- **It would not have saved tonight**, and the two sleeps at 20:12 and 21:39 both resumed cleanly and killed nothing.
  It is built because the keeper asked for it at 22:17, and because an idle sleep during a long carry is a real risk.

## 7 · WHAT I DID NOT VERIFY

- **No shutdown, no restart, no logoff was ever run against this code.** No rebuild and no relaunch, as ruled. So:
  - no WM_QUERYENDSESSION has ever reached `session_end_proc`;
  - the blocking screen and its reason string have never been seen by any eye;
  - WM_LEAVE_DONE has never been posted or handled;
  - the `ENDSESSION_CRITICAL` branch has never run.
- **Whether the block is honoured on this machine is unknown**, and the documentation says it may not be.
  **The ROW 4 falsifier — a Windows restart with the stick in, after which no LEAVE record exists — cannot be scored
  until the keeper rebuilds.** Until then, D-6 is closed on paper only.
- **Whether subclassing tao's window is safe in practice.** It chains through `DefSubclassProc`, and `cargo test`
  compiles it, but no run has proved the chain is intact, and a tauri or tao upgrade could move that window.
- **The keep-awake hold has never been observed to hold anything.** `SetThreadExecutionState`'s return value is
  checked and logged, but no idle-sleep test was run, and no machine was left idle with a seat open to see whether it
  stayed awake.
- **The 2 s poll means the hold can lag a seat by up to 2 s**, at both ends. Not measured against anything.
- **The 20 s export bound is unmeasured** against a real shutdown-time carry (§3).
- **The exit-after-Leave choice** (§3) has not been tried against a cancelled shutdown.
- **Windows Update's own behaviour** — whether it re-queries, and how soon it retries after a cancelled attempt — is
  from documentation and the event log, not from a run.
- **dev/stick-waiter.js is unchanged this lap**; the waiter still dies with the machine, and nothing here changes what
  happens to a waiter that is killed with no app left to watch.
