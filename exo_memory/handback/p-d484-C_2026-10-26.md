## 1. The answer first

- **Nothing slow and nothing new.** Each Turn change costs, at most, one display frame of **3.7 to 4.0 ms at the 95th percentile**. That holds on every release from 0.4.19 to 0.4.22, 14 runs, with no change between them (§3).
- **Row 4 misses because of how it adds up.** It sums the input handler and *every* animation frame over 0.5 ms for up to 120 ms after a change. The exact ghost is built a slice a frame (D407), so the row adds the slices back together. That sum then has a p95 of 5.2 to 7.7 ms, which swings either side of 6.0 run to run, on 0.4.19 just as on 0.4.22.
- **The bar is right; the measure is not.** The rule is per frame (ARCHITECTURE.md §9b: "as smooth as the user's refresh rate", 6.06 ms a frame at 165 Hz). The row's own header gives rows 1–3 the per-frame rule: "the cost of an action is the LONGEST piece of main-thread work it causes".
- **The per-frame measure still catches what the row was written for.** On b306309 (0.4.8, before D407 sliced the ghost) it reads **10.4 / 11.8 ms**, red. The summed measure reads 11.1 / 12.2 there.

- **The sum's spread is noise.** Its p95 over 32 changes is about the second-largest change, and that one is a change where a handles relayout or a slice lands inside the window. It passes or fails at random: 0.4.19 and 0.4.21 each have a run under 6.0 and a run at 7.7. "Red at 0.4.21 and 0.4.22" is two unlucky draws, not a regression. inferred: it was as marginal when D407 measured it green.
- **The per-frame measure is steady** (3.7 to 4.0 ms on every post-D407 run) and clearly separates b306309 from everything after.

Why "handler + the first frame" counts as one display frame: with a real refresh rate, Chrome dispatches input aligned to the frame and runs the animation-frame callbacks after it in the same frame. Later slices each get a frame of their own, one per refresh. inferred: from Chrome's input alignment, not measured here. Headless with the frame-rate limit off runs frames back to back, so it can only show the frames separately, never one display frame's real span.

## 4. Could the sum be made green by a code fix instead?

Yes, by doing less per change. Two candidates:
- (a) `assemble` (mesh.js) builds the scene of the new pieces only, not every piece.
- (b) The handles layer keeps its layout when a typed field moves only the ghost.

inferred: together about 1 to 1.5 ms a change, enough to bring the sum's p95 near 5. But it would fix the reading, not the feel: no frame the user sees is over 4.5 ms now. I recommend fixing the measure, and leaving (a) and (b) as optional speed work.

## 5. The proposed change to the bar (for the librarian, before anyone edits the row)

Row 4 keeps its bar of 6.0 ms and its case, and changes its measure. Each Turn change costs **the worst display frame it causes**: max(handler + the first animation frame after it, each later animation frame alone), within the same window as now (until the next change, at most 120 ms). The row asserts the p95 of that over the 32 changes is at most 6.0 ms.
- The header's "handler and frames together" becomes "the longest frame it causes, the handler counted with the first frame after it", in line with rows 1–3.
- **What it reads:** 3.7 to 4.0 ms on 0.4.19 to 0.4.22; 10.4 / 11.8 ms on b306309, red there (§3).
- **Falsifier, registered here:** if the per-frame measure on 0.4.22 ever reads over 6.0 ms on a quiet machine, or if it reads green on b306309, this proposal is wrong.

The code for it is one line in the row: `cost = evs.map(...)` becomes the max described above. It is in `_evidence/probe.js` as `largest` with the handler added to the first frame (`perframe.out` computes it from the probe's JSON). I have not edited `release-frame.test.js`.
