## 1 · THE FALSE CLAIMS, WITH THE EVIDENCE AND THE TRUTH

### Claim 1 — "299 lines" · FALSE, and the wrong number is reproducible

**Truth: 298 lines.**

    wc -l  < consonance/tools/boundary-check.js     298
    sed -n '$=' consonance/tools/boundary-check.js  298
    awk 'END{print NR}' …                           298
    grep -c '' …                                    299

**Where 299 comes from, because it is worth knowing rather than just correcting.** The file contains
**one NUL byte, at byte offset 8653**, on **line 155**:

    const key = o.pane + '\0' + o.text;

— a join delimiter written as a raw NUL rather than an escape. `grep` splits a line at a NUL, so
`grep -c ''` counts that one line twice. Demonstrated on a control:

    printf 'a\nb\nc\n'      | grep -c ''   ->  3
    printf 'a\nb\000x\nc\n' | grep -c ''   ->  4      (wc -l on the same: 3)

So **299 is what you get from `grep -c ''`, and it is wrong here for a reason specific to this file.**
The NUL is deliberate code, not corruption; nothing needs fixing but the note. **One practical consequence
worth knowing, since it bit me while checking the other claims:** `grep -n "..." boundary-check.js`
prints `Binary file … matches` instead of the matching line, for every search. Anyone reading this file
with grep needs `-a`, or they get no line numbers at all.
