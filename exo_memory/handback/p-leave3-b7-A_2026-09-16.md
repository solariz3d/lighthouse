## 1 · B7, AND WHY A DROP GUARD RATHER THAN `catch_unwind`

**The hole B found:** `shutdown_leave` posts `WM_LEAVE_DONE` on every *return*, but not on an *unwind*. A panic in the
Leave thread therefore leaves the block reason held by a dead thread, and the shutdown hangs until Windows forces it —
B2's exact sentence through a different door. `leave_run` had a real panic site on that path: `main.rs:10994`
unwrapped the `Panes` mutex that **row 5 already treats as poisonable**.

**Built, both halves:**

1. **`sync_launch::OnDrop<F>`** — a guard whose `Drop` runs the closure. `shutdown_leave` installs it BEFORE any work,
   and the post moved inside it. The exit decision travels in a `Cell<bool>` the guard reads *on the way out*, so
   R4-1's "exit only if that Leave finished" still holds.
2. **`harvest_guard::recover(app.state::<Panes>().0.lock())`** replaces the `unwrap()`. One mutex, one policy — the
   same recovery the capture watcher uses, and the same one row 5 uses two hundred lines away.

**Why the guard, since the chair asked me to say if I took it:**
- It fires on **every** exit, so *"the post happens on every return path"* stops being a property a reader has to
  re-verify by eye. **B had to read every return to close B1; nobody should have to do that twice.**
- `catch_unwind` would need `AssertUnwindSafe` around a closure holding the `AppHandle` — a claim about that handle's
  state after a panic that nobody here can make. The guard needs no such claim.
- A later edit that adds a `return` cannot skip it. That is how this hole would otherwise come back.
- It does **not** swallow the panic: the thread still dies. The guard's job is the block, not the Leave.

**Tests, red first.** Both were red against a stub guard whose `Drop` did nothing:
- `an_on_drop_guard_runs_once_on_a_normal_return_and_on_an_unwind` — runs the guard in a normal scope, then inside
  `catch_unwind` with a real `panic!`, and counts. **This is the deliberate-panic test the ruling asked for.**
- `a_poisoned_panes_style_lock_is_recovered_rather_than_unwrapped` — poisons a real `Mutex<HashMap<..>>` from a thread
  that panics while holding it, asserts `lock()` is `Err`, then drains it through `harvest_guard::recover`.
  **This one passed before the fix** (the helper already existed and works); its partner pin — that `leave_run` uses
  it instead of `unwrap` — was the red one. I am naming that rather than counting it as a catch.
- `the_shutdown_path_releases_the_block_even_if_the_leave_panics` — the wiring: the guard is installed before the
  work, exactly one `PostMessageW` exists and it is inside the guard, and `leave_run` no longer contains
  `.0.lock().unwrap()`.

**Two older pins had to be re-pointed, and this is the weaker kind of change:** the ROW 4 pin asserted the post came
*textually after* `leave_run`, and R4-1's asserted the literal `u32::from(exit_after)`. The post is now a guard at the
top of the function, so textual order no longer expresses the guarantee. They now assert the **structure**: the guard
is installed before the Leave, there is exactly one post and it is inside the guard, and the wparam reads
`exit_after.get()`. The guarantee — the block is released after the Leave, on every path — is unchanged and is now
carried by `Drop` rather than by line order.
