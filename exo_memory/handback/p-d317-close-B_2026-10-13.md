## What changed (main.rs at 7bc89502)
- **`close_needs_confirm(&[(String, PaneGate)]) -> Option<Vec<(String, PaneGate)>>` (:13934):** the seats whose gate is not Ready,
  in the order given, or None. All Ready → None; empty → None; Working, Stale, Unstamped or Contradicted → Some, naming each.
- **`close_route(leave_idle, checking, since_asked) -> CloseRoute` (:13956):** the X's decision, pure.
  - Leave: a Leave is under way, so today's path answers "busy", or "use-button" once the Leave screen is up.
  - Swallow: a check is in flight, or the question went out under `CLOSE_ASK_HOLD` ago (2 s, :13953).
  - Check: otherwise.
- **`close_seat_gates(app)` (:13973):** every seat in `Panes`, its gate read through `pane_state` exactly as the inbox and
  keep-warm read it. The label is the seat's name from `PaneNames` when it has one, else its short id; the list is sorted.
- **`close_on_x(app)` (:13991):**
  - Routes as above.
  - For Check, it sets `CLOSE_CHECKING` with a compare-exchange, so two quick X presses start one check.
  - It reads the gates on a spawned thread, then either emits `close-confirm { working: [{ label, gate }] }` (gate words
    `working`, `stale`, `unstamped`, `contradicted`, from `gate_word`, :14032) or calls today's `leave_close_requested`.
  - Each outcome is written to the log (`CLOSE X — asked: …`, `CLOSE X — … none working`, `CLOSE X — swallowed`).
- **`#[tauri::command] leave_confirmed(app)` (:14026):** in the handler list (:15112); calls `leave_close_requested(&app)`. A second
  call meets the Leave already running and gets today's "busy".
- **`on_window_event` (:15121):** `CloseRequested` on main → `api.prevent_close(); close_on_x(…)`. It was `leave_close_requested`.
- **Unchanged:** `leave_close_requested`, `leave_run`, the Leave button (`leave_exit`, `app.exit`) and the applier's exit. Neither
  raises CloseRequested, so neither reaches `close_on_x`.

## Where the plan does not hold as written
- **The pending guard cannot be "until answered".** The fixed contract has no signal for [Keep working], which "does nothing at
  all", so the app can never learn the question was dismissed. A guard held until an answer would swallow every X after one
  [Keep working], for the rest of the session.
  - So the guard stops stacking: a check in flight, a double click, a held key (`CLOSE_ASK_HOLD`, 2 s, a judgement).
  - After that, a further X asks again.
  - **For E (part 2):** a `close-confirm` may arrive while the modal is already up. Treat it as a refresh of the list, not a second
    modal.
  - The clean fix is a `close_dismissed` command from [Keep working] that clears the guard, for a later revision of the contract.
    I did not add it, because the contract is fixed and E is building against it.
- **pane_gate from the window-event thread: safe, and not done there.** `pane_state` takes the `PaneEmus` map lock, then one
  emulator's lock, which the PTY reader holds while it parses. Both are short, but they are on the event loop.
  - So `close_on_x` reads the gates on a spawned thread, as `leave_close_requested` already spawns the Leave. The event handler
    itself only reads two atomics and a mutex-held `Option<Instant>`.
  - inferred: no lock is held across the spawn.
- **`consonance/CHANGELOG.md` did not exist.** The plan names it, and the packet asks for the line there, so I started it in Keep a
  Changelog form with one Added entry. Say if the room's record should stay in exo_memory only.
- **An exited child still counts.** A seat whose process has exited keeps whatever stamp it last wrote, so it may read Stale or
  Unstamped, and then it asks. That is the plan's fail-safe ("unknown counts as working").
  - Leaving exited seats out, as keep-warm does with `pane_exit::liveness`, is a small follow-up if the question proves noisy. Not
    done: it is outside the plan's rule.
- **"Ask always":** the one-line change the plan mentions is `close_needs_confirm` returning `Some(seats.to_vec())` when the list
  is non-empty.
