## THE CORRECTION — `m_updateCoverTimer` does not accumulate seconds

`WearNTearUpdater.Update()` reads `Time.deltaTime` — **one frame** — and hands it down. But the
cover `foreach` runs at most **once per second** (`m_sleepUntil` gate). So the timer gains one
FRAME of time per SECOND of wall clock.

    WearNTearUpdater.cs:19-23   deltaTime = Time.deltaTime;  if (time < m_sleepUntil) return;
    WearNTearUpdater.cs:31-45   the cover pass runs on the branch where m_sleepUntilNext == m_sleepUntil,
                                sets m_sleepUntilNext = time + 1f, and RETURNS  ->  once per ~1 s
    WearNTear.cs:626-627        m_updateCoverTimer += dt;  if (<= 4f) return;
    WearNTear.cs:51             m_updateCoverTimer = Random.Range(0f, 4f)   // phase-spread at Awake
    WearNTear.cs:1287           private const float c_UpdateCoverFrequency = 4f;   // named as seconds

**The 4f constant is not four seconds. It is four seconds' worth of FRAMES, delivered one frame per
second.** Effective period per piece = `4 x fps` seconds: **~4 min at 60 fps, ~9.3 min at 140 fps,
~20 min at 300 fps.** Steady-state cast rate is `N * dt / 4` per second — an **upper** bound, since
a wear sweep longer than one second makes the cover pass rarer still.

The identical pattern done **correctly** is thirty files away: `Player.UpdateCover`
(`Player.cs:3646`) accumulates `fixedDeltaTime` from `FixedUpdate` (`Player.cs:231`), where the call
rate is fixed and `+= dt` really is seconds. WearNTear copied the shape into a once-per-second
`Update` loop, where it is not.

## MY OWN INSTRUMENT'S BROKEN ORACLE, reported rather than deleted

`rate.js` prints `ratio intended/actual = 112.2x` against my analytic prediction of `140x`. **The
control arm is wrong, not the measurement.** With `dt = 1.0` exactly, `<= 4f` plus reset-to-zero
gives a period of five passes, not four, so the INTENDED arm reads `N/5` where the analytic form
says `N/4`. `1000 / 8.91 = 112`; `1250 / 8.91 = 140`. The ACTUAL arm — the one the verdict rests on
— matches its closed form to three significant figures (8.91 vs 8.93) and is unaffected. Left in
the output rather than papered over; the discretisation artifact is in the arm that does no work.

## WHAT THIS DOES NOT ESTABLISH

- **It is a source read, the same class as the finding it corrects.** No stopwatch ran, no frame was
  timed, nothing in Valheim executed. The difference is that this one makes a falsifiable
  quantitative prediction (`N * dt / 4` casts/s) with a ~1000x margin, where the finding asserted a
  rate it never derived.
- **Duhem-Quine, named:** the refutation bundles one auxiliary I did not test — that
  `Time.deltaTime` inside `Update()` is the frame delta. That is Unity's documented semantics and
  the IL shows no other source, but I did not observe it at runtime.
- **It does not touch defect 1 or 2 as MECHANISMS.** Both are real. They are worth ~0 because of the
  rate, not because they were misread.
- **The other unbudgeted pass, examined and cleared:** `UpdateAshlandsMaterialValues`
  (`WearNTear.cs:70-83`) is `N` cheap calls per second — no physics, and its one expensive call
  (`MaterialMan.SetValue`) is guarded by an equality check against the previous value. It is not a
  hidden cost centre.
- **NOT machine-bound, and this is the one place that helps.** `machine_bound_class_2026-08-25.md`
  does not bite here: the result is a function of framerate and piece count, not of his box, and it
  gets **cheaper as framerate rises**. It holds on a stranger's install without a second base. The
  scripted 2,000-piece world is not needed.

## THE ONE THING THAT SURVIVES, and it is not a performance mod

The same defect is a **correctness** bug with the sign reversed. `m_haveRoof` initialises to `true`
(`WearNTear.cs:1281`) and is written **only** at `:633`, inside the timer gate; `UpdateWear` reads
it at `:279` (`m_rainWet = !flag && !m_haveRoof && EnvMan.IsWet()`). So a piece standing in the open
in rain does not begin taking rain damage until its first cover pass — a mean of `2 x fps` seconds,
**~4.7 minutes at 140 fps** — and **the higher your framerate, the longer the delay**.

I am not proposing it. Rain damage is 5 points per 60 s of continuous wetness (`:290-295`), so a few
minutes of lag is small and invisible in play, and a correctness mod for an invisible effect is a
solution with no reader — the exact failure class `memory/split-the-work-with-the-panes.md:28`
records against the last Valheim build. **Named so the next lap does not rediscover it and mistake
it for a rescue.**
