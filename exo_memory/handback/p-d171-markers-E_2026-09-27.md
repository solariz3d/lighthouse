## 2 · Decisions

- **Anchored to words** (§5c: "markers stay on the road when the words around them are edited").
  - The start line and the pits are `{ word, along }`; the grid and the hotlap hang off the line.
  - Edit a word upstream and they move with their word.
  - Edit the anchor word and they keep their distance into it, clamped to its length.
  - Remove the word and **`anchors` is red**, never silent.
- **Race direction is +s**, the order the words are placed. AC_START_0 is nearest the line, and every marker faces +s.
- **The paint is geometry, not a §5b texture layer.** There is no texture system yet: no road textures, no layer
  compositor, no DDS writer.
  - Each mark is a patch in (s, u) mapped through the same `surfaceAt` the markers use. So it bends with bank and walls
    as a road-space texture would, and "paint and marker can never disagree" holds by construction; the tests check it.
  - It is lifted 2 cm along the normal (inferred).
  - It is exported as **visual meshes**. The names do not start with a digit, so AC does not read them as physics
    (ARCHITECTURE §6).
  - When §5b lands, the same (s, u) rectangles become the layer's rectangles.
  - **Not painted:** grid numbers (glyphs needed), the pit lane's entry and exit lines (no lane yet), sector lines
    (§5c paints only start/finish).
- **The gates:** at the cross-section's edges, inset 0.5 m (inferred) so the gate stands on the road. On a half-pipe
  that is up the walls, standing off the wall along its normal.
- **The hotlap run-up is the design speed's run-up.** `runUpM(v) = ∫₀ᵛ v / a(v) dv` with a(v) from D169's measured
  table (FINDINGS.md:494); 352 m at 460 km/h (`node -e` probe of `runUpM`).
  - On an open track too short for it, the hotlap sits at the start, and an **amber** says the speed it will reach
    (344 km/h on the sample, the same probe).
  - A hotlap on a curve is checked along its own road. T1's grid-direction heading test is narrowed to the grid and
    the start gate (`raceHeading`).
- **Default distances** (inferred, from D167): the line 15 m before the longest straight's end; the pole 10 m back;
  staggered rows 16 m (one slot every 8 m); ±3 m across; 2 pit boxes every 8 m; 1.5 m up. The car slot is ±1.0 m ×
  ±2.4 m (T1's, inferred there).

## 3 · Proposed interfaces and mounts (for A, C and B: none of their files touched)

**The pit lane, for C (geometry) and A (the document).** §5c: "a side road leaving and rejoining the loop".
- **The marker half is built and tested.** `placeAll(layout, path, segs, { lane: { path, segments } })` places,
  checks and paints the boxes along a given lane: from `layout.pits.lane.along`, backwards by `spacingM`, on the lane's
  own surface. `test/markers_lane.test.js` uses a hand-built lane 20 m beside the road.
- **What the lane needs:**
  - **A, the document:**
    `doc.pitLane = { leave: { word, along }, rejoin: { word, along }, side: 'L' | 'R', offsetM, width, speedKmh? }`,
    serialised with the track.
  - **C, the geometry:** `buildPitLane(mainPath, mainSegments, pitLane) -> { path, segments }`. It is a road branch
    leaving the main path at `leave` and joining it again at `rejoin`, `offsetM` to the given side, with the lane's own
    flat profile. It must be closed-form enough to mesh with `buildMesh` (its own cells, named `1ROAD_PIT_n`).
  - **E, validation:** stacked and self-intersection must exempt the two merge zones, where the lane meets the main
    road by design.
  - **A, the export:** `exportTrack` would pass the lane to `placeAll` (`{ lane }`) and add its mesh to the scene.
- **Paint still to do with the lane:** the entry and exit lines.

**The layout in the document, for A.** The layout belongs with the track (`doc.markers = layout`), serialised with the
words, so it is saved and shared and survives a reload. Until then it lives in the markers panel for the session, and
**the export uses the default layout.**

**The export, for A** (`app/export/export.js`): pass the panel's layout, i.e.
`fromwords.exportTrack(doc, { outDir, selfCheck, variant, markers: layout })`. `layout` arrives on the `t180:markers`
event (below), or from `doc.markers` once that exists. Nothing else changes: without it, the export is as today.

**The mount, for A** (`app/index.html`): a `<section id="markers">` in the side panel, and `['markers', 'markers']`
added to the list of panels loaded through `app/lib/cjs.js`. Tested: `app/markers/index.js` loads through A's loader
and exports `mount`.

**The preview, for C.** After every update, `#markers` dispatches a bubbling `t180:markers` CustomEvent with
`{ layout, placed, paint, check }`:
- `paint.meshes` are scene-shape arrays (world positions, normals, uvs, u16 indices), ready to draw;
- `placed[i].pos` / `.fwd` / `.up` give a gizmo per marker.

It follows C's own DOM-event pattern (`t180-camera`). This is proposed, not agreed.

**For B, the INTERFACES.md lines.** "§5c markers: `src/markers` `placeAll(layout, path, segments, { lane })` →
`{ placed, paint, check, nodes }`. A layout is word-anchored track coordinates (`src/markers/layout.js` header).
`exportTrack` takes it as `opts.markers`."
