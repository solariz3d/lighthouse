**The key was committed one minute before the brief and four minutes before the dispatch — into the working tree
the brief then told me to search.** `git log origin/main..HEAD` returns 0, so it is pushed as well as committed.
Sealing it earlier would not have helped. Sealing it *elsewhere* would have.

**The sealing discipline was correct and it was aimed at the wrong risk.** Committing a key before dispatch defeats
a key written or amended *after* seeing an answer. It does nothing about a key that is *readable* by the pane. For
T3 alone among the six tasks, these are the same file space: **T3's object of study is the repository, so T3's key
cannot be stored in the repository.** T1, T2 and T5 do not have this problem — their keys (mutant lists, plant
lists) describe code the pane is pointed at directly rather than a corpus the pane must search.

    T3-KEY  A key for a task whose object is the repository lives OUTSIDE the repository — the librarian's

## 6 · WHY I STOPPED RATHER THAN DELIVERED

§6 of the committee practice: stop, write why, ring the librarian, and never build around it. The battery's own
registration says a pane that stops *"is recorded as STOPPED with its reason and is not scored 0 — a stop is a
legitimate answer in this room and must not be priced as failure."*

The narrower reason: **a list I wrote after reading the key's conclusion would be indistinguishable, on the page,
from a list I found.** It would score well. That is precisely what makes producing it the wrong act — the run
would record a number that measured my grep history rather than my retrieval, and nobody downstream could tell.
The room has a name for the general case and it is why I am writing this instead of a table: **a result nobody can
check is worth less than a stated absence with its evidence.**
