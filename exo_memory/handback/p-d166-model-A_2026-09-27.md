## 2. The model, per §2

- **Words:** the §2 set `straight, sweep, turn, tight, wall-ride, inversion, jump`.
  - Their radius bands are the track reader's own (`tools/read_track.cjs` `word()`): straight > 1,500 m, sweep
    500–1,500, turn 180–500, tight < 180. Default peaks: sweep 1,000, turn 300, tight 120, wall-ride 30.
  - Climbing and dropping are the `climb` handle on any word.
- **Fonts:** one data type, `flat, half-pipe, bowl, wall-ride, tube`. Each is a floor of `width` plus a wall of arc
  `wall` each side, with ψ rising linearly to ψL/ψR. That is C's `profile.js` convention: rise from the floor,
  positive on both sides, past 90° legal. A bowl's and a wall-ride's outside wall goes on the outside of the turn.
- **Tempo:** `scale` on every default radius, and `ease` as the default ramp share.
  - `aurora` sweeps at 1,200 m, as §2's Aurora figure.
  - `serpents` turns at 135 m, inside the 100–170 m §2 cites.
  - `standard` is 1.0 / 0.3.
- **Handles:** INTERFACES §4b's set.
- **Stable ids:** `w<n>` from a counter that only grows, so a removed head's id is never reused.
- **Defaults are written into the document at append time,** so resolve never depends on a default a later builder
  might change.
- **Phrases:** inline in the document, resolved as `<id>/<n>`.
- **Canonical serialisation:**
  - The text is written by `serial.js` itself: fixed key order, one word per line, numbers printed from quantised
    integers.
  - Quanta: 1 mm, 0.001°, 1e-4 for ease, 0.01 km/h.
  - It carries `schema: 1` and `generator: "t180-track-builder/doc 0.1.0"`.
  - In memory every number is already quantised, so a document is its own serialisation.
- **Schema versions:** §2 says a document carries one, and **says nothing about migration**. There is no older schema
  (this is the first). So **any other schema is refused**:
  - `SCHEMA_TOO_NEW` for newer;
  - `SCHEMA_UNKNOWN` for older or malformed ("no migration to it exists").
  - `MIGRATIONS` is the empty table a future step goes in.
- **Undo:** snapshots of frozen documents. A drag is one entry, and a drag that changes nothing adds none.
- **resolve:** each road word opens its curvature from what it arrives with, holds, and closes to 0. The peak is solved
  so the word turns by exactly `turn` and climbs by exactly `climb`. A jump is one `gap` segment whose pitch clothoid is
  solved (Newton, Gauss–Legendre) to cover `gap`, come down `drop`, and land at `land`.

## 3. SHAPE NOTES for B's `docs/INTERFACES.md` — where my part differs from, or adds to, the file (not silent)

1. **A word resolves to up to THREE segments**: parts `in`, `body` and `out`, each linear in curvature, all with the
   word's id, plus a new field **`part`**. INTERFACES §1 says "one entry per resolved word". A single linear k0→k1
   cannot express open–hold–close, and §4b's `easeIn`/`easeOut` needs it. Consumers group by `id`.
2. **Jump handles are `gap`, `drop` (+ = lands lower) and `land` (landing pitch, rad).** INTERFACES §4b lists only
   `gap`. Without the other two, the landing's height and pitch are undefined. The gap segment has `profile: null` and
   `k0 = k1 = 0` (no yaw in the air), and carries the solved `kp0`/`kp1`.
3. **Roll across parts is piecewise smoothstep.** C's path smoothsteps within each segment, so a word's one smoothstep
   becomes three pieces, each level at its ends. It is continuous, but not identical to one smoothstep. A per-segment
   `rollShape` or linear option would fix this, and it is C's and B's call.
4. **Heartline has one field per segment, so there is no heartline ramp.** A step between words is refused
   (`HEARTLINE_STEP`), because the road position would jump. The same holds for roll (`ROLL_STEP`).
5. **Fonts step at word boundaries.** Nothing blends a profile across a join (the platform test blended ±10 m). If the
   mesh should blend, it needs a field or a rule, and it is C's and B's to place.
6. **`width` is the FLOOR width,** and walls extend by the font's `wall` arc (a font constant, not a handle).
7. **A closed document is refused** (`CLOSE_NOT_BUILT`). §2's connector needs the path's end frame and is not built.
8. `resolve` also returns `head: { id, word, k, kp, pitch, roll }`, the curvatures and angles the next word opens from.
9. **The library (INTERFACES §4b `library` / `piece`) is NOT built,** and neither is a phrase's `exposed` list.
   Phrases exist only inline.
