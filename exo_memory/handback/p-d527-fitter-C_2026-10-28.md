## 1. What it does, and whose code it runs

    checked: tools/xsecfit.cjs at 6a3f496

- **Input.** One JSON object per section: `{ left: { u, psi }, right: { u, psi } }`.
  - `psi` is the surface's angle above the horizontal, in degrees, going outward from the centre, at arc length `u` in metres.
  - A side may give `y` (heights above the centre's) instead of `psi`, which is a cut's own points with nothing re-integrated.
  - `psiFromPoints(points, centre)` turns a polyline of world points `[lateral (+ left), height]`, edge to edge, into both forms. It is for O's cuts in Part 2.
- **The model is the builder's own code, not a copy of it:**
  - `src/core/adapter.js` `cupProfile` (the base: flat at c = 0, the family's floor shape above it) and `edgeProfile` (ψ_mid + e·G(t), with G the smoothstep, from the start s);
  - the edge zone's knot count as `xsecSegments` sizes it (`max(EDGE_MIN_N, ceil(1.5·max|e|))`);
  - `src/geom/profile.js` `offsetAt` for the integration;
  - the bank applied as the path applies it. checked, on a real road banked +10°: `m.L = [0.985, 0.174, 0]` and `m.U = [−0.174, 0.985, 0]`, so a positive phi raises the left side, u > 0, and height = X·sin φ + Y·cos φ.
- **Bounds:** the builder's own. s in [0.5, 0.95] (document.js S_MIN, S_MAX); c in [0, 150] (CUP_MAX); each side's total rim angle, c + e, in [−30, 150] (EDGE_FLOOR, CUP_MAX); phi within ±89°.
- **Three families:**
  - `one-s`: phi, c, e, er, s. What the builder makes today.
  - `two-s`: phi, c, e, er, sl, sr. The edge start free per side.
  - `cup-per-side`: phi, cl, cr, e, er, s.
  - A two-sided family takes each half of the road from the builder's profile made with that side's value. That is the builder's own code for each half, joined at u = 0, where both are 0.
- **The fit:** least squares on height, compared at equal arc length from the centre, with one free vertical offset (a measured centre's height is not trusted).
  - When the two measured sides differ in length, the centre is put halfway along the whole width, because the builder's road is symmetric in width.
  - The search is Nelder–Mead from 12 starts (3 edge starts × 2 cups × 2 edge scales, the bank and rim angles read from the data), each polished until it stops improving.
- **Output, per family:** the channels, `rmsCm`, `maxCm`, `maxAt` (side, metres from the centre, share of the half-width), `offsetM`, the point count and the evaluations.
- **Command line:** `node tools/xsecfit.cjs <section.json> [family]` prints the three fits, one JSON line each.

## 4. What this means for the plan's falsifier (Part 2), registered before any reference section is fitted

- **The plan's test is "under about 2 cm RMS across the width".** On the two-start section, one-s scores 3.27 cm RMS, close to that bar, while it is 22.6 cm off at the right rim.
  - inferred: an RMS over the whole width under-weights the rims, because the floor is most of the width and fits well. So a section could pass the 2 cm RMS bar and still be visibly wrong where a car rides the wall.
  - Proposed for Part 2, before the numbers are in: report the max and where it sits beside the RMS, and read the falsifier on both. Under 2 cm RMS and under about 5 cm max would say the shape across the road is not the lesson. This is a proposal; the bar is the plan's, so the chair or the librarian sets it.
- **The fit is a local search:** 12 starts, no proof of a global minimum. A misfit on a reference section should be checked by refitting from the other families' answers before it is believed. Part 2 can do that cheaply: the two-s answer is a start for one-s with sl = sr.
- The model has no tube base and no legacy-rate (`r`) base. It fits banked bends' floors and edges on the cup base, which is flat at c = 0. A reference section that needs neither will not notice; one that does would show as a misfit in every family.
