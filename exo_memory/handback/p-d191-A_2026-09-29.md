**Why `-text`, not `eol=lf`.** Both give a fresh Windows checkout the committed LF bytes. They differ only when a CRLF file gets committed: `eol=lf` would silently normalise it to LF on `git add`, hiding an edit the digest test exists to catch, whereas `-text` commits the bytes as they are, and the raw-byte check then goes red where it should. The fixtures are hashed as raw bytes, so "never convert" is the accurate statement.
**What else in the tree hashes raw repo-file bytes** (searched: `createHash`/`sha256` in `test/`, `app/test/`, `src/`, `tools/`): only `test/core_cup_fixtures.test.js`, which reads `test/fixtures/fixtures.js` and `test/fixtures/manifest.json` raw, and `fixtures.js --check`, which hashes each `F*.core2.json` raw. All eleven are under `test/fixtures/`, so the one rule covers them. The other hashers (`test/texmaker.test.js`, `app/test/export.test.js`, `src/export/fromwords.js`, `src/export/layouts.js`) hash GENERATED bytes (texture pixels, kn5 output, an sha256 shim self-test), not files read from the repo, so autocrlf cannot change them. `app/test/export.test.js` also reads repo text files (`fromDisk`, the shader and licence text) with `utf8` but does not hash them. Every other text file in the tree is CRLF on a Windows checkout and nothing raw-hashes it (that is what "not verified beyond a grep" means below).
