## 2 · (2) FOLD BY (id, GENERATION): the definition

- **A generation starts at each `open` row of an id**, sorted by `at`, with ledger order breaking ties.
- **Every other row** belongs to the latest open of that id with `open.at ≤ row.at`. A row before the first open belongs
  to generation 1.
- **By time, not by file position.** After the union interleave, and in the live file before it (the 09-21 generation
  came first), file order and time order can disagree. A test pins exactly that case.
- **THE RACE stays DOUBLE-OPEN.** Two opens of one id **within 60 s** are one generation with two opens. That is the
  double-mint `open()` guards against, and it must still be flagged. **Why 60 s:** measured on L's ledger over all 23
  successive-open gaps of one id: **min 4,867 s** (L058), median about 88,865 s, max about 346,916 s. The race is an
  append followed by a re-read, seconds at most. The window sits 80× below the shortest real reissue.
- **Nothing is written:** no row is rewritten, renamed or reordered. A test hashes the ledger around `laps()` and
  `report()`.

**Read paths:** `laps()` (and so every `--report` table and count); the late-map check in `report()` (it now reads the
lap's own generation rows instead of the whole ledger by id); every place the report prints an id (9 sites), which now
print the label. **`chain-status.js` does not share this fold.** It has its own reader, the newest chain row per id by
`at` (`chain-status.js:488-490`), which for a reissued id is already the newest generation. It was not changed; it
isn't in my files and isn't wrong.

**Writers bound to the latest generation:** `map()` (its open row, its guess seal, "already has a map"), `opened()`
("no map yet"), `chain()` (the opened-row gate, the baton's prior holder, the window start), and `voidLap()` ("already
void"). **`open()` is unchanged.** It mints a fresh id and still refuses below the record (L070).

**Printing:** `label` = `L058 (2026-09-14 07:30Z, gen 1/8)` when `gens > 1`, else the bare id. In the per-lap table the
label is padded as `(label + ' ').padEnd(6)`, so **every single-generation row prints byte-for-byte as before** (a
4-character id plus 2 spaces), and a long label no longer runs into the next column (§5.3).
