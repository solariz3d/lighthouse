## What HTML windows would cost in the builder

**Frame cost of a blur over the 60 fps WebGL view: none measurable on this machine.**
- checked, `evidence/measure_blur_cost.js` → `blur_cost.txt`:
  - Headless Chrome on this machine's GPU (`ANGLE (NVIDIA, NVIDIA GeForce RTX 5070 Ti Laptop GPU … Direct3D11)`).
  - A 1500 × 900 WebGL canvas redraws 40,000 moving triangles every frame.
  - Five overlays, each run 5 s, twice, in the order A-E then E-A: none; a 260 × 856 blurred panel; that panel plus 1 blurred
    label; the panel plus 4 blurred labels; the panel plus 1 plain label.
  - Every run held 240 fps: mean 4.17 ms a frame, p95 4.3 ms, 0% of frames over 20 ms.
  - The measure is rAF to rAF, not GPU time. It says no frame was missed at 4× the 60 fps budget; it does not give the blur's
    own milliseconds.
- **The app already pays for it.** checked: `#stage` spans every column (`app/index.html:242`, `grid-column: 1 / -1`), so the 3D
  view runs under `#left`, and every one of the five looks puts a `backdrop-filter` on `#left` (the table above).
  - So today, each frame already blurs a 260 × ~850 px panel over the WebGL canvas.
  - A label window, about 204 × 44 px, is about 4% of that area.
  - inferred: WebView2 is the same Chromium compositor as the Chrome measured here, so the app would cost the same.

**The placement code that would move:**
- checked, `app/core/secondtick.js`:
  - `placeLabel` (`:108`) and its caller (`:199-200`). The caller reads `hooks.avoid()`, the labels already placed this draw,

  - It works in stage css px and returns `{ x, y, w, h }`. That part needs no change for an element.
  - inferred: what changes is that `w` comes from `measureText` today (`:196`), so an element would have to be measured, or
