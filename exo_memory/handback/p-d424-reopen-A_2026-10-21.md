## §2 What changed

### Item 1: a committee pane is reopened once

**`pane_exit::decide` now takes a `Seat`**, one of Fixed, Committee or Human:
- Fixed and Committee get `ReopenOnce` the first time, then `ExitedAgain`. The once is per pane per app run, in the same set as before.
- Human gets `Prompt`, unchanged.

**`main.rs` `reopen_seat` decides the seat and its folder:**
- a fixed seat resumes in its own folder;
- a committee pane resumes in the folder its kept-pane record holds (`read_kept()`, the record `resume_pane` restores it from at launch);
- a committee pane with no record, or an empty folder, is left to the ↻, and so is every human pane.

The reopen goes through the existing `on_pane_exit` → `spawn_claude_pane(…, resume=true, …)` → `insert_pane` path. That is still one spawn, behind the `ReopenOnce` guard. The board rows say which case applied.

### Item 2: refuse, don't force

**`pane_exit::exit_gate`** reads the exit record, the reopens under way and the pid the map holds now. It returns one of:
- `Open`;
- `AwaitReopen`: exited, and its one reopen is running;
- `Refuse(exit)`.

**The door, `gate_or_queue`, asks it first:**
- On a refusal it writes `REFUSED NOT DELIVERED -> <id8> (at the door; …exit code N) at HH:MM:SSZ…): <label>` to the board and the log. The same text is returned to the sender as the tool's reply.
- On `AwaitReopen` it queues the message.

**The drain, `drain_inboxes`, asks it before any reading:**
- On `Refuse` it takes every queued message for that pane. Each gets its own `REFUSED NOT DELIVERED -> … (queued Ns ago; …)` row.
- Each is also told to its sender, through a note queued to the sender's own pane. The sender is read from the provenance label the app writes: `[chair:MAIN]`, `[librarian:LIB]` or `[pane:X]`.
  - The note carries no sender of its own, so a refused note is never refused back.
  - A keep-warm, a pull or a dyad line has no sender, so only the board hears.
- On anything that is not `Open`, nothing is taken that tick.

**After a reopen, the message waits for the new child's own ready signal.** Two parts:
- The held messages' bound restarts when the reopen lands (`Inbox::restart_wait`; `Queued.wait_from`, kept apart from `queued_at`, which the rows still use). It restarts before the new pid is inserted, so no tick sees the new child with the old clock.
- A ready stamp written before the reopen is the dead child's, so it reads as no stamp (`gate_stamp`, `pane_exit::stamp_predates_reopen`). The screen gate then decides on the reopened child's screen.
  - **This is a choice of mine.** The stamp's own `pid` field is the hook's node process, not claude's, so "the new pid's ready signal" cannot be keyed by pid. A resumed claude runs no turn, so it fires no Stop until something is delivered. Waiting for a fresh Stop would deadlock. So the reopened child's ready signal is its own screen reading ready: quiet, empty composer, no spinner, and bounded again from the reopen.

**Order in `on_pane_exit`:**
1. The reopen is marked under way before the exit is recorded, so no tick refuses what should wait.
2. On success, the mark is cleared after `insert_pane`. On failure it is cleared too, so the next tick refuses by name.

**`chain-status.js` pairs the new row.** It adds `REFUSED NOT DELIVERED` to `QUEUE_ROW_RE` beside `WITHDRAWN NOT DELIVERED`. Unpaired, a refused ring read as `QUEUED A 99m` for ever.
