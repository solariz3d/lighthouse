## 2. Findings

- **The chair's correction holds.** checked: `git show 1526a59:src-tauri/tauri.conf.json` → `app.windows[0]` has `"maximized": true`, and no
  `visible` or `backgroundColor`.
- **A window created hidden with `maximized: true` comes up maximized when it is shown.**
  checked, from source: `tao-0.37.1/src/platform_impl/windows/window_state.rs:360-374`. The maximize block skips `ShowWindow(SW_MAXIMIZE)` while
  the window is hidden ("This is to avoid the window from flashing"). When the window becomes visible the same block runs and calls `SW_MAXIMIZE`
  before the `SW_SHOW` at `:460`. `window.rs:1405-1412` applies `maximized` after `CreateWindowEx`, as `set_maximized(true)`.
  inferred: from reading the source; the app was not launched (no window may be opened by a seat).
- **So the remembered state is skipped**, as the packet allows. The window opens maximized on every start, and an un-maximized window is not
  remembered. Why: "The builder opens maximized" (0.4.25, 7dc5917) is the behaviour that was asked for, and remembering would add stored state
  for a case nobody asked about. The page still calls `maximize()` before `show()`, so the order holds even if the config changes.
  What would change my mind: the keeper wanting the builder to come back as he left it.
- **The shortcut's own Run setting.** checked, from the ShowWindow documentation (learn.microsoft.com, ShowWindow): "This parameter is ignored
  the first time an application calls ShowWindow, if the program that launched the application provides a STARTUPINFO structure."
  - With the window hidden, the app's first ShowWindow is now the page's show: tao's `SW_MAXIMIZE`, then `SW_SHOW`.
  - inferred: a shortcut set to Run: Maximized still opens it maximized (its SW_SHOWMAXIMIZED takes the first call), and Run: Minimized would
    still start it minimized, as before.
  - inferred, NOT checked: a shortcut at Run: Normal would, by that rule, turn the first call into a normal show. The old window, created
    visible, went through the same first-call rule and still came up full screen for the keeper, so that suggests it does not. Only a real
    launch from a shortcut can say. It is the first thing to look at if the installed build opens un-maximized.
- **A page in a hidden window may get no animation frames.** Chromium pauses them for hidden pages, and WebView2 in a hidden window is likely
  treated as hidden. inferred: not observed here. So each frame is "an animation frame or 100 ms": at worst the window appears about 200 ms
  after the reveal, not after the 3 s fallback.
