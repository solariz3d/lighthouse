## 1 · THE FIVE GAPS, EACH DECIDED: post-registration choices, made BEFORE any label or Jev call

**The registration fixes the question texts (§2 `:148`, `:149`) and the answer set (`:167`, `yes | no | cannot-say`).
It does not fix the call shape.** v1 said the schema carries the question "unchanged" (`tj1_registration:77–80`). The
rest is decided here, with the reasons. **The rule I decided by: Jev gets exactly what the keeper gets** (§4: *"the
class question, and the unit's three lines, as plain text. Nothing else"*), because the keeper is the truth, and any
difference between what he answers and what Jev answers is a second instrument.

- **(a) The criteria text.** Every choice gets a gloss of the same form, `yes: the answer to the question is yes`,
  `no: … is no`, and `cannot-say: the text does not let the question be answered yes or no`.
  - **Deliberately contentless.** jev-ask requires a gloss for every option (`:115–118`), and the gateway decides by
    them. A gloss that defined the question's own terms ("a number", "as fact", "beside it") would hand Jev a sharper
    question than the one the keeper answered with no glosses at all.
  - **B was right that any wording is a new instrument.** This is the smallest one that `validateSchema` accepts.
  - `cannot-say` is glossed to match the keeper's `can't tell` (`:167`), not to invite abstention.
  - **What this costs:** Jev may interpret the question differently from the keeper. **That is exactly what the backtest
    measures**, so it is not a defect to engineer away.
- **(b) The keys.** One question per file, keyed `answer`. **The key is sent** (jev-ask `outgoingTexts` `:76` lists it),
  so a name like `c1_figure_without_command` would be extra words the model reads. The option keys are the
  registration's answer set exactly (`yes`, `no`, `cannot-say`), so scoring needs no mapping.
- **(c) The instructions.** The §2 question, verbatim, **with no frame around it**. jev-shadow frames its state because
  its state is a whole prompt (`jev-shadow.js:56`, `const INSTRUCTIONS`, at HEAD plus A's uncommitted L105 edit). Here the question already names what the state is ("this text",
  "this transcript"), and the keeper gets no frame either. **Checked byte-identical** against §2 by extracting the
  quoted text from `:148` and `:149`, not by retyping it. The K text also matches v1's AMEND-1 once v1's blockquote
  wrapping is undone.
- **(d) Two files, not one.** K and C1 are asked about **different units**, a rendered transcript and three lines. One
  file with two questions would ask both of every unit: K about three lines of prose, and C1 about a transcript.
  That wastes calls and exposes each answer to the other question. Path: `consonance/jev/schemas/`, the directory v1
  named (`tj1_registration:79`), created here.
- **(e) The state.**
  - **C1:** `units[i].three_lines.join('\n')` from the member file: the three lines as held, joined by one LF, with no
    path, line number, heading or trailing newline. That is what the keeper sees, minus the question, which Jev gets as
    `instructions`. **It blinds Jev exactly as §4 blinds him:** no file or seat, no stratum.
  - **K:** the pinned renderer's `renderFile(<transcript>).text`, which is §13 item 2's renderer, sha `5fa7a56d…`.
  - **Found while checking, and fixed before any sha was recorded:** my first K note said *"its stdout"*. The CLI
    writes `text + '\n'`, one byte more than the `bytes` the renderer records (`tj1-k-render.js:63–64`, `:88`). The
    state is now `.text`, matching the recorded size and the C1 rule.

**Every choice is written into each file's `what`/`state` fields.** jev-ask sends only `questions` (`buildRequest`,
`:195–196`), so those fields reach no model. They are covered by the sha.

## 4 · FOR A, NOT CHANGED: a risk this lap cannot check without the network

**The option key `cannot-say` has a hyphen.** Every choice option in a live Jev schema so far is an identifier
(`quiet_spiral`, `refer_to_human`; `jev-shadow.js:62–84`, the `JUDGES` table). jev-ask checks question names with an identifier rule
(`:106`) and option names with none, so a hyphen passes here. **Whether the live gateway accepts a hyphenated option
name is unverified.** I kept it because it is the registration's answer set verbatim (`:167`).
- **If the gateway refuses it,** the first call fails with an HTTP error and returns no answer, so no output exists.
- **The fix would be a schema change, re-hashed and appended**, made before any answer is seen. That is allowed under
  §5, which voids only edits made after output.
- **Cheaper:** A, or whoever holds the gateway docs, can check whether choice option names must be identifiers, before
  the run.
