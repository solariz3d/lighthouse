## 1 · THE DEFECTS

### D1 — `:118` the usable-row filter is INVERTED — `length <= MIN_SHA` (repo: `>=`)
**What it does.** `joinRows()` keeps only ledger rows whose sha is *at most* `MIN_SHA` characters. Real rows carry
7–40 character shas, so **the usable set is empty in normal operation.**
**Consequence when it runs:** every artifact commit reads `ferry: null`. Nothing is ever ferried, `--due` lists work
that was ferried days ago, and the miss rate reads 100%.
**Measured** (same planted ledger, same commits, both tools):

| | since the ledger | ferried | miss rate | median | `--due` |
|---|---|---|---|---|---|
| repo | 39 | **4** | 89.7% | 30.0 min | 805 owed |
| copy | 38 | **0** | 100.0% | n/a | **809 owed** |

**This is the defect that matters most**, because it fails in the direction that looks like diligence: a tool whose
job is to make un-ferried work visible now reports *everything* as un-ferried, and the four real ferries disappear.
**Found by reading; proved by running.**

### D2 — `:43` `MIN_SHA = 4` (repo: `7`)
**What it does.** Lowers the floor `record()` enforces. The comment three lines above still says *"at 6 characters
collisions stop being hypothetical"*, so the constant now contradicts its own stated reason.
**Consequence:** `--record a1b2 B` **succeeds and writes a row** (repo: exits 2, writes nothing), and per the tool's
own comment at `:151-155` that phantom then blocks the real sha. Measured, in the copy:

    --record a1b2 B                     exit 0   {"sha":"a1b2",...,"already":false}   <- row written
    --record a1b2c3d4…a9b0 B            "already recorded … nothing added"           <- the FULL sha can never be recorded
    ledger holds only                   {"sha":"a1b2","panes":["B"],...}

**The commit is now unferryable without hand-editing the ledger** — exactly the failure the refusal exists to
prevent. **Found by reading; the blocking interaction proved by running.**

### D3 — `:160` `if (prior.length || !added.length)` (repo: `&&`)
**What it does.** Takes the no-op branch whenever *any* prior row exists, regardless of whether this call adds a new
pane.
**Consequence: a second pane on an already-ferried sha is silently dropped.** Measured at the CLI:

| | 1st `--record SHA B` | 2nd `--record SHA C` | rows written | panes the ledger knows |
|---|---|---|---|---|
| repo | added B | **added C** | 2 | `["B","C"]` |
| copy | added B | **"already recorded … nothing added"** | 1 | `["B"]` — **pane C is not in the ledger** |

This reinstates the precise incident the tool was built after — a dropped second pane, invisible because the output
looked the same as a duplicate. **Found by reading; proved by running.**

### D4 — `:201` latency divided by `1000` (repo: `60000`)
**What it does.** Computes latency in **seconds** while `:220` still prints `median.toFixed(1) + ' min'`.
**Consequence: every latency figure is 60× too large and carries the wrong unit.** Measured with three ferries at
5 / 30 / 120 minutes: repo prints `30.0 min`; copy prints `7200.0 min`. **Found by reading the diff; the mislabelled
unit only shows when you run it**, because the divisor and the label are twenty lines apart.

### D5 — `:202` the `n >= 0` filter is gone
**What it does.** Keeps latencies where the ferry timestamp precedes the commit (clock skew, a back-dated row).
**Consequence:** impossible negative latencies enter the median. Measured with 5 / 30 / 120 and one at **−45 min**:
repo drops it and still prints `30.0 min`; the copy keeps it.
**Found by reading; proved by running.**

### D6 — `:204` `lat[Math.ceil(lat.length / 2)]` (repo: `Math.floor`)
**What it does.** For an odd count, indexes one past the middle.
**Consequence: with three samples the "median" is the MAXIMUM.** Measured, 5 / 30 / 120 minutes → repo `30.0`, copy
`7200.0` seconds = 120 minutes, the largest of the three. With an even count it also risks `lat[length]` →
`undefined` at the top end of the index range.
**Found by reading; the "it is the max, not the median" consequence proved by running** — the two arithmetic defects
D4 and D6 are indistinguishable in a single printed number, and only separate when you vary the sample.

### D7 — `:215` `RATE_FLOOR = 1` (repo: `10`)
**What it does.** Removes the denominator floor. The comment directly above still explains why the floor exists
(*"printed 97.2% off a denominator the instrument could not have observed … immediately produced 0.0% off n=3"*).
**Consequence: a percentage is printed off any n ≥ 1.** Measured with two commits in the window: repo prints
`n/a - only 2 in window, need 10 before a rate means anything`; copy prints **`100.0%`**.
**Found by reading; proved by running.**

### D8 — `:196` window filter `r.at > ep` (repo: `>=`)
**What it does.** Excludes a commit whose timestamp equals the epoch exactly.
**Consequence:** the denominator silently loses one commit. Measured by setting the epoch to a commit's own
timestamp: repo `since the ledger 13`, copy `12`. In every mixed run above the copy's window is exactly one smaller
than the repo's.
**This one I would not have caught by reading alone** — I read `>` vs `>=` as cosmetic until the harness printed
39 vs 38 on the same data, and the same off-by-one then appeared in every run.

## 2 · READING VERSUS RUNNING — the split the packet asked for

| found by | what |
|---|---|
| **reading** (the diff, plus the comments the changed lines contradict) | all eight changed lines; D2's contradiction with its own comment; D7's contradiction with the paragraph above it; that D1 empties the usable set |
| **only by running** | that the `' min'` label survived D4, so latencies are mislabelled as well as wrong (D4); that D6 returns the **maximum** rather than "some other element" (D6); that D8 is a real off-by-one in the denominator rather than a stylistic choice (D8); that D2 and D3 **compound** — a short row is written and then permanently blocks the full sha; and that the shipped test file, unmodified, already fails 7 of 13 |

**The test run is the cheapest evidence and nobody had done it:** `node ferry.test.js` in that directory →
**6 passed, 7 failed**, including *"a SHORT sha in the ledger matches the FULL sha of its commit"*, *"record()
REFUSES a short sha"*, *"a SECOND pane on the same sha MERGES into the set — the defect this fixes"*, and *"the merge
does NOT change what counts as ferried"*. Three of the failures are `Cannot read properties of null` — that is D1
cascading, not four separate bugs.

## 3 · WHAT I DID NOT FIND WRONG

The artifact-directory rule, the prefix-match logic itself, `panesOf`, the malformed-line tolerance, the epoch
derivation and the `--due` output format are unchanged from the repo version and behave identically in my runs.

## 4 · HOW IT WAS CHECKED

- `diff -u` repo vs copy; `diff -q` on the test files (identical).
- `node ferry.test.js` in the copy's directory.
- Three harnesses in my own scratchpad, each running **both** tools against the **same** planted ledger and the same
  real artifact commits, with `FERRY_LEDGER` pointed at a scratch file and `FERRY_NOW` fixed for reproducibility:
  a mixed run, an isolation run (median / negative latency / epoch boundary / rate floor, one at a time), and a
  CLI write-path run.
- Because D1 inverts *which* rows are usable, each side was given a ledger whose sha length that side counts, so the
  arithmetic defects (D4–D7) were compared on equal matching — otherwise the copy reports `n/a` for everything and
  the numbers cannot be compared at all.
