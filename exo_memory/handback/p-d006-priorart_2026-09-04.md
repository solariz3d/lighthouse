## THE THING NOBODY ASKED FOR — THE FINDING'S CADENCE IS WRONG BY A FACTOR OF THE FRAMERATE

The finding's headline is **"One 100-metre spherecast per building piece, every 4 seconds, whenever
it is raining."** Re-deriving the call chain to check "unclaimed" surfaced that this is not what the
code does.

    $ grep -rn "UpdateCover" <full>    -> WearNTear.UpdateCover has EXACTLY ONE caller:
      WearNTearUpdater.cs:38   wearNTear.UpdateCover(deltaTime);
      WearNTearUpdater.cs:18   float deltaTime = Time.deltaTime;      // ONE FRAME's delta

`UpdateCover` accumulates `m_updateCoverTimer += dt` and acts at `> 4f` (`WearNTear.cs:626-627`).
The pass that feeds it runs **once per sleep cycle**, not once per frame: `UpdateWearNTear` takes the
cover branch only when `m_sleepUntilNext.Equals(m_sleepUntil)`, and **returns immediately after**;
`m_sleepUntil` is advanced only once the budgeted `UpdateWear` sweep wraps (`WearNTearUpdater.cs:97`),
with `c_WearNTearTime = 1f`.

**So the timer accrues one frame's deltaTime per ~1 second of wall clock — not one second per second.**

    $ node -e '...'
    fps= 60  dt=0.01667  cycles to 4.0 =  240  -> per-piece roof-cast period =  4.0 min
    fps=140  dt=0.00714  cycles to 4.0 =  560  -> per-piece roof-cast period =  9.3 min
    fps=300  dt=0.00333  cycles to 4.0 = 1200  -> per-piece roof-cast period = 20.0 min

    steady state, pieces staggered by Random.Range(0f,4f) at Awake (WearNTear.cs:51):
      N= 5000 @ 140 fps ->   8.93 spherecasts/sec       FINDING IMPLIES  1,250/sec
      N=20000 @  60 fps ->  83.33 spherecasts/sec       FINDING IMPLIES  5,000/sec
    OVERSTATEMENT FACTOR = the framerate (~140x on the keeper's box).

And the sign is inverted from the finding's story: **the higher the framerate, the rarer the cast.**
The `Random.Range(0f, 4f)` stagger and `c_UpdateCoverFrequency = 4f` say Iron Gate intended seconds;
passing a frame delta into a once-per-second pass is the bug. Either way the *behaviour* is the above.

**FALSIFIER FOR THIS CLAIM, registered before anyone acts on it:** a Harmony **postfix on
`WearNTear.RoofCheck`** incrementing a counter, logged once a minute, during 60 s of in-game rain on
a base of known piece count N. **If it returns ~N/4 per second, I am wrong and the finding is right.
If it returns ~N*dt/4, this holds.** That is one counter and no stopwatch — cheaper than packet 1's
attribution instrument, and it should run first, because it decides whether packet 1 is worth running
at all. Packet 1 owns the build; this is its cheapest first move.

## THE REFUSAL — the answer the packet said would be worth most

**Do not build the roof-cache mod as scoped.** Three reasons, in the order they bind:

1. **The bypass is claimed and shipping.** `RockBreaker/ValheimBuildOptimization`, live, updated ten
   weeks ago, config-toggled, with its own profiler. Anyone whose base is slow in rain can install it
   today.
2. **The magnitude is ~fps-times smaller than the finding states.** ~9 spherecasts/second on a
   5,000-piece base at the keeper's framerate is not a performance problem. The finding's own
   registered falsifier ("no measurable share of frame time -> no mod should be built") is very likely
   to fire, and this is the arithmetic that says so before the instrument is built.
3. **The finding's own load-bearing sentence already conceded the magnitude was unmeasured.** It was
   right to. The correction is that the mechanism was mis-read too, in the direction that made the
   problem look bigger.

**What is worth doing instead, if anything is** — and it is a different, smaller thing: the
114,213-download `NoRainDamage` adds a reflected `HaveRoof()` call per `UpdateWear`. That is a real
regression in a widely-installed mod, it is one line to fix, and its consumer is a stranger who has
already installed something. **Not proposed. Named, so the next lap can rule on it.**
