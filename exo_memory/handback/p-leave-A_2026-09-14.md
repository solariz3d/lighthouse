## 1 · WHAT §2.3 AND §2.7 BECAME (dev/stick-waiter.js)

At the app's exit, in this order:

    a  stick-apply.started.json names a live applier   -> last = STOOD_DOWN; then step 4 — no longer a return (D-9)
    b  stick-leave.result.json for THIS app pid          -> last = STOOD_DOWN_LEAVE, whatever its outcome: no find, no
                                                            notice, no export. Remove it, and a same-pid
                                                            stick-leave.started.json beside it (the app died between its
                                                            two writes), then step 4 (D-4, D-9)
    c  stick-leave.started.json for THIS pid, no result  -> waitForLeaveCarry (D-3), then today's findStick + export with
                                                            fallback notices, then remove LEAVE_STARTED (D-4), then step 4
    d  neither file for this pid                         -> today's path, whose notices now name the fallback; then step 4

- **"For this pid" (D-7), `leaveFor`.** `rec.pid === the watched app pid` decides first. The image is a second check:
  `imageName(rec.image) === imageName(argv --app-image)`, lower-cased with `.exe` stripped on both sides by the same
  normaliser the waiter already used (pidImage's shape). The record's `"consonance.exe"` matches an argv of
  `consonance.exe`, `CONSONANCE.exe` or `consonance`. The right pid under `node` does not match.
- **Stale.** A LEAVE file naming any other pid is not this waiter's. It is ignored (case d runs) and NOT removed; the
  app's launch-time cleanup owns stale files.
- **D-4, `removeLeave`.** Removes only after acting, and only if the file still names the pid acted on. A newer app's
  LEAVE file written during a long fallback export is left alone (tested).
- **D-3, `waitForLeaveCarry`.** It reads `<stick>/consonance-tails/ledger.lock`, where `<stick>` is
  `LEAVE_STARTED.stick`, or the stick found now if that field is missing.
  - It waits while the lock names a live holder. Live means the pid answers (the kernel's `kill(pid, 0)`, which starts
    no process) AND `carry.holderLive(rec)` agrees on the image, with "cannot tell" counting as live.
  - It does not wait when there is no lock, an unreadable lock, a dead holder, or a live pid under another image.
  - Every wait poll spends the same `maxPolls` budget as the app wait (the CLI's is Infinity). Out of budget →
    `GAVE_UP`, LEAVE_STARTED kept.
  - Then comes **today's export, unchanged**, LEDGER_LOCKED retry included. By then the orphan is gone, so the retry
    can only meet an unrelated writer.
  - The status file names the wait: "waited N s for the close window's own carry (pid P, tail-carry.js) to let go of the
    stick's ledger before saving".
- **Fallback notices.** Every save this waiter makes is the fallback now.
  - Both notice titles read "Consonance — fallback save to the stick".
  - The first notice's body and the status file say why. Case c: "Consonance stopped during its own save to the stick
    (pid P, started <at>), so this is the fallback save." Case d: "Consonance closed without saving to the stick itself
    (it was stopped before its close window could run), so this is the fallback save."
  - Nothing else about the export changed: the same tail-carry call, the same DONE / NOT DONE text, the same tag.
- **D-9.** Cases a and b set `last` and fall through to the existing step 4 (adoption) instead of returning. A new app
  pid is adopted and watched, and at its own exit the rules run again for that pid.
- **Also:** the header's "In order" block is rewritten to a-d, and `LEAVE_STARTED` / `LEAVE_RESULT` are exported.

## 5 · FOR B AND THE CHAIR — four edges, built as ruled and named rather than built around

1. **Case c's wait has no bound.** The ruling says "waits until that pid is not live", and that is exactly what was built.
   - **Where it can hang:** an orphan tail-carry that never exits (a hung read on a failing stick), or a holder whose
     image cannot be read while its pid answers, keeps this waiter waiting indefinitely.
   - **What the wait holds up:** it holds `stick-waiter.lock` the whole time. So a relaunched app's own waiter exits
     ALREADY_WAITING, adoption (step 4) waits for the wait to end, and E's launch cleanup leaves the LEAVE files alone
     (by D-4).
   - **The race it opens:** if the orphan then finishes during the relaunched session, the fallback export runs while
     that session's seats are writing. That is B's §8 race through case c; §2.5 scopes the fix to the Leave, not the
     fallback.
   - **What would close it:** a bound (for example LEAVE_EXPORT_TIMEOUT plus a margin, then NOT DONE naming the
     holder), or an adoption check inside the wait. Neither was ruled, so neither was built.
2. **Each wait poll starts a hidden tasklist** (holderLive's image check), every 2 s, for as long as the orphan lives.
   That happens only at exit, only in case c, and always with `windowsHide` (the P-NO-CONSOLE sweep test still passes).
   The app wait confirms the image once a minute, and the lock wait could do the same. I left it unchanged because the
   ruling says "not live", and `holderLive` is the tool's own definition of that.
3. **Case c with the stick unplugged** after the app died reads NO_STICK and stays quiet (today's path). LEAVE_STARTED
   is removed. The keeper's last sight was the app's "Saving to the stick" screen, and no notice says NOT DONE. Built as
   ruled ("today's export path").
4. **B's D-8 (the relaunched app reusing the pid) touches the waiter too, and is unruled.**
   - The case: a LEAVE_RESULT from session 1 survives, because the app's cleanup found its pid live under consonance —
     session 2 was given the same pid.
   - The effect: if session 2 is then hard-killed, this waiter reads case b and stands down, exporting nothing.
   - Pid and image cannot tell those sessions apart. Comparing the file's `at` with the watched session's start time
     would, but nothing records that start time today.

## 8.1 · WHAT CHANGED

- **`LEAVE_CARRY_WAIT_MS = 660 * 1000`**, a waiter constant. The reason beside it: LEAVE_EXPORT_TIMEOUT's 600 s (the
  app's own bound on that carry) plus a 60 s margin; a carry still holding the ledger past the app's own timeout is
  hung, not slow. It is injectable as `leaveCarryWaitMs`, the same pattern as `lockedRetryForMs`, and exported.
- **`waitForLeaveCarry`** stamps `began = k.now()` before its loop. While the holder is live, it checks
  `waitedMs >= k.leaveCarryWaitMs` before sleeping, and at the bound returns `{ timedOut, holder, stick, waitedMs }`.
  The bound counts from the start of the wait, not from the first live sighting. The poll budget (`maxPolls`, `GAVE_UP`)
  still applies.
- **Case c at the bound, via `leaveCarryTimedOut`:**
  - no export
  - the status file is written fresh:
    `NOT DONE — the stick's ledger is still held by pid P (tail-carry.js, since <at>) after N s. Nothing was saved.`
  - the next status line says it was the fallback and that it did not run over a live writer; a third names the stick
    and says not to unplug while pid P is running
  - ONE fallback notice (title "Consonance — fallback save to the stick") carries the first two lines. Nothing was saved,
    so there is no "don't pull it yet" notice.
  - the status file ends `@@END 2 NOT DONE LEAVE_CARRY_TIMEOUT`, and the outcome is `LEAVE_CARRY_TIMEOUT`, code 2
  - **LEAVE_STARTED is left in place**, because nothing was acted on
  - `last` is set and control **falls through to the adoption check (D-9)** before returning
- The header's case-c line now names the bound.
