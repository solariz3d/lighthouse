## 2. The fix
`free.move(fwd, right, up)` used to add `d·fwd + r·right + U·up`. Forward `d` follows the view's pitch and `U` is the world's up, so they are not perpendicular, and that sum's length is not the request's. Now the sum's DIRECTION is kept and its length is set to `hypot(fwd, right, up)`:
`v = d·fwd + r·right + U·up`, `L = hypot(fwd, right, up)`, `eye += v · L / |v|`.
- A single-axis move is unchanged (|v| = L). The wheel's free dolly (`free.move(steps·4, 0, 0)`) is unchanged, backward too.
- Shift's ramp still multiplies: `preview.js` asks for `k = sprint · flySpeed · dt` metres, and now gets `k` metres whatever the keys.

## 6. The rule at an exact cancel: the case, named
The plan says "move along the non-cancelled part, not stop". Normalising the sum does exactly that, and I checked whether an EXACT cancel can occur:
- **It cannot, inside the camera's own limits.** The pitch is clamped to ±89°, so the view direction, the right vector and world-up stay independent; the sum is never shorter than 0.0123 of the request (the smallest singular value, `√(1 − sin 89°)`). A true zero needs a pitch of exactly ±90°, which the clamp forbids.
- **The nearest case, tested:** W+E at −89° goes 3.000 m along the horizontal heading (direction dot the heading > 0.999), instead of 0.037 m. The direction swings continuously as the pitch changes; the speed does not.
- **A guard remains for a sum that is nothing at all** (`n > 0 && n > 1e-12·L`, else the old plain sum, which is zero). It is not reachable through the keys; I did not test it beyond `move(0,0,0)` being a no-op.
- **The one thing to decide:** at −89° with W+E the eye slides horizontally and does not rise, which is what "the non-cancelled part" means. If the keeper wants W+E looking down to still climb, that is a different rule (say so).
