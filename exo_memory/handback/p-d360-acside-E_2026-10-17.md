## 0. The answer

1. **Per layout:** `models_<L>.ini`, `<L>/data/*`, `<L>/ai/*`, `<L>/map.png`, and `ui/<L>/{ui_track.json, preview.png, outline.png}`.
   - **Shared:** the kn5 files that every layout's `models_<L>.ini` names, plus `extension/ext_config.ini`.
   - A layout is nothing more than a models file listing kn5s, plus its own data and ui folders. (§1)
2. **Yes, shared road can sit in one common kn5, and Kunos does exactly that.** Every Kunos multi-layout track here loads one or more common kn5s in all layouts, plus small per-layout kn5s.
   - Measured saving against shipping each layout as a whole copy: 48–61% of the kn5 bytes.
   - **Aurora does not share its road.** It shares only `environment.kn5` (128 MB, 17.5% saved). Its two track kn5s share all 17 of medium's textures byte for byte (151.7 MB), and almost no geometry. (§2)
3. **Content Manager:**
   - It shows one track with a count, using the longest common prefix of the layout names: "Aurora Cryopticon (2)".
   - It finds layouts by scanning `ui/*/ui_track.json`.
   - It picks the main layout by a `priority` field, then by name rules.
   - It remembers the picked layout per track. (§3)
4. **Our exporter already writes multi-layout folders, as whole copies.**
   - `src/export/layouts.js` `exportProject` is the code, over `src/doc/project.js`.
   - The app never calls it: only `test/export-layouts.test.js` does.
   - It writes one whole kn5 per layout, with nothing shared, by an explicit design choice (ARCHITECTURE §11.1, quoted at `layouts.js:1-2`).
   - Four gaps against what the keeper's ask needs are in §4.

- **What the Kunos pattern shows:** a layout is a set of kn5s that AC loads together at the same origin.
  - Each layout's own pieces sit in kn5s that only its models file names. Silverstone national loads `2.kn5`, `6.kn5` and `101.kn5`; gp loads `3.kn5`, `4.kn5` and `100.kn5`.
  - So "only the differing pieces per layout" is the established form, not a hack.
  - inferred: the small per-layout kn5s (Silverstone `100.kn5` and `101.kn5`, about 7.3 MB each) hold each layout's own pieces, such as start or pit markers. I did not open their node names, so this is not checked.
- **Aurora, inside its two track kn5s.** checked: `scratchpad/d360/kn5overlap.js long.kn5 medium.kn5` (sha256 `0c27a3b6…`). It parses the textures, materials and node tree to the end of each file, and hashes each texture blob and each mesh's vertex+index blob in memory:
  - long: kn5 v6, 21 textures (190.8 MB), 130 meshes (76.6 MB of geometry);
  - medium: kn5 v6, 17 textures (151.7 MB), 120 meshes (58.5 MB of geometry);
  - **all 17 of medium's textures are byte-identical to one in long: 151.7 MB,** which is 72% of medium's kn5;
  - only 71 of medium's 120 meshes are byte-identical to one in long, and **together they are 10,366 bytes**. The road geometry is not shared byte for byte.
  - So Aurora as shipped has no shared road. Its download repeats about 152 MB of textures. inferred: medium was exported separately from the same scene, so the same road reads as different bytes. A road could also sit in a different place or vertex order; this compare cannot tell those apart.
- **Our own kn5s weigh differently from Aurora's.** checked: the same script on our largest export here, `t180b_elysium.kn5`: 203.8 MB, kn5 v5, 3 textures (22.4 MB), 182 meshes (181.4 MB of geometry, 89%).
  - So for a T-180 track, sharing **geometry** is what saves bytes. Textures are small, and repeating them per kn5 costs about 22 MB.
  - inferred, as a formula, not measured on a real two-layout T-180 track:
    - whole copies cost Σ (each layout's whole kn5);
    - shared costs (pieces in every layout) + Σ (each layout's own pieces and markers).
    - Example: a medium that reuses half of a 200 MB long, plus a short connector, costs about 310 MB as whole copies against about 210 MB shared.
- **What a split has to respect:** each layout's own kn5 has to carry its own `AC_START_n`, `AC_PIT_n` and `AC_TIME_n` markers. Any piece cut away in a layout must not be in the common kn5, or that layout would still draw it, and still drive it if it has physics.
  - inferred from how AC loads every kn5 a models file names. It is not stated in any document I found.
  - Unknown, not checked: whether AC or CSP resolves a texture across two kn5s of one layout (so textures could live once), and how two kn5s holding nodes of the same name behave. Until that is measured, the safe form keeps each kn5's textures inside it, as Kunos's do.

## 3. How Content Manager shows layouts (from its source)

Source: `gro-ove/actools` at master `e5e5c94b`, `AcManager.Tools/Objects/TrackObject.cs` (sha256 `3b209649…`), `TrackObjectBase.cs` (`80b5f6ff…`) and `TrackExtraConfigurationObject.cs` (`a64adf3b…`). They are kept in `scratchpad/d360/cm/`.

- **Finding layouts** (`TrackObject.cs:129-153`):
  - A layout is any `ui/<dir>/` holding a `ui_track.json`.
  - If `ui/ui_track.json` also exists at the root, the root is the main layout (the "simple main layout": root `models.ini`, root `data/`).
  - Otherwise CM picks a main from the subfolders.
- **Choosing the main layout** (`:193-237`):
  - Kunos tracks use CM's list of Kunos layouts.
  - Anything else is scored. The ui_track.json **`priority` field counts ×1e8** (`:210`), so it decides.
  - Below that, the name's distance from the folder name counts, and the name rules: `circuit|international|full|gp|…` raise a layout, and `drift|mini|oval|reverse|…` lower it (`:180-183`).
  - Extra layouts are ordered by `priority`, then by id (`:46-52`).
- **The name in the list:** the longest common prefix of the layout names, trimmed of a trailing `-`, `—`, `/` or `(`, plus the count (`:339-355`, `:410-411`).
  - So Aurora shows as "Aurora Cryopticon (2)". Ours, named `"<name> (<L>)"` at `layouts.js:48`, would show as "<name> (2)".
- **The picked layout is remembered per track** (`SelectedLayout`, `:73-91`).
- **Per-layout paths CM reads** (`TrackObjectBase.cs:453-460`, `:497`; `TrackExtraConfigurationObject.cs:44-49`):
  - `<L>/data/`, `<L>/map.png`, `<L>/ai/fast_lane.ai`, `<L>/ai/pit_lane.ai`;
  - `models_<L>.ini` at the folder root;
  - `ui/<L>/ui_track.json`, `preview.png` and `outline.png`.
  - A missing `outline.png` or `preview.png` is flagged as an error (`TrackObjectBase.cs:93-98`).
