    P2  rule ONLY on the incoming branch (D's real position)    -> merge exit 1, markers 2  — the rule did nothing

N1 is the concrete warning: union turns a real disagreement into two silent lines. There is also a cosmetic effect,
visible in P1: both appends began with the same blank line, and union keeps one, so the two new entries sit with no
blank line between them. Nothing is lost.

**Run 2, the runbook dry run: `runbook_dry.sh`** (sha256 `cabf2a1e…`). The runbook's steps 2–6 were run verbatim in a

**Run 3: `runbook_dry2.sh`** (sha256 `9c1c2f89…`) is the same with `MSYS_NO_PATHCONV=1`. Rule count 3. `check-attr`: M.md

The runbook now prefixes the three `<ref>:<path>` commands for Git Bash and says to drop the prefix in PowerShell.

## 4 · The runbook

`exo_memory/loop/runbook_D_merge_and_push_2026-09-27.md`. It holds no machine paths
(`grep -nE "[A-Z]:[\\/]|/c/Users|zackn|nname"` → none). The steps:

0. The keeper is present; no seat is writing.
1. Record D's state and HEAD sha.
2. Fetch, and check that origin carries the rule (count 3, **else stop**).
3. Put the rule in `.git/info/attributes` and verify with `check-attr`.
4. Make a backup branch.
5. `git merge --no-ff origin/main`, with the seat named in the body.
6. The conflict check: a union file in conflict → abort and redo step 3; non-union dated notes → both sections in time
   order; LEDGER → by hand, row by row; code, JSON or the brief → abort and bring it to the librarian. Then no markers left.
7. Read what union did (N1 duplicates, the cosmetic blank line), and let the recovered table yield to D's masters.
8. Remove the local rule lines, then the suite: js-suite, carrier-drift compared with D's own before-count, portable-paths
   and text-census, plus cargo if `src-tauri/src` changed. Compare each red against the backup.
9. Push **only at the keeper's word**, quoted on the board. After it, `origin/main..HEAD` = 0.

Recovery for each stage: abort during the merge; the backup branch before the push; fix forward, never a force-push,
after it.

## 5 · What was NOT verified

- **Nothing has been merged against D's real commits.** `4a00947`, `b214e3a`, `cc1135d` and `79e3c01` are not objects on
  L (`git cat-file -t` → not a valid object name). I do not know which files D changed. If D edited a union file in
  place, and not only appended, the result is N1: two silent lines. Step 7 is the only guard.
- **D's git version and shell** are unknown. The P2 and MSYS findings were measured with git 2.53.0.windows.2 on L.
- The classification covers **L's first-parent history** only. D's own history since 5ced140 is not in it.
- `.gitattributes` must be **committed before L's push** (L122) for step 2's check to pass. Until then, origin has 0 rules
  and the runbook tells D to stop.
- The suite was not run over the `.gitattributes` change. Attributes affect only merges and eol here; portable-paths
  and text-census were run.
- **Union ordering:** it puts the merging side's lines first in a conflicted hunk (P3: D's entry before L's). On D's
  merge that means D's 09-26 entries come before L's 09-27 ones, which is chronological by luck, not by rule.
