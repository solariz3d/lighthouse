## The answer
**It is a native crash of the child `node.exe`, exit code `3221225477` = `0xC0000005` (STATUS_ACCESS_VIOLATION).** It is not a test failure, not an out-of-memory death, and not a kill. **It cannot be reproduced on demand, and the evidence points at this machine's instability, not at our code** (inferred, not proven; below).
- Not reproduced: 50 runs of the file alone, plus one full suite run exactly as the librarian ran it.
- **What would settle it is the keeper's:** check the BIOS memory setting, and run a memory test.
- No code was changed.

## Evidence, each with its command or source
1. **The crash is native, not a kill.** In the librarian's `full1ff.tap` (main 1ff9963, `--max-old-space-size=4096 --test --test-concurrency=1 --test-reporter=tap`), `app\test\core-textures.test.js` is `not ok 11` with `failureType: 'testCodeFailure'`, `exitCode: 3221225477`, `signal: ~`, `error: 'test failed'` (`full1ff.tap:1520-1531`).
   - It is the ONLY non-zero child exit in the whole run (`grep -c exitCode:` → 1).
   - There is no crash text anywhere in the TAP (`FATAL ERROR`, `out of memory`, `access violation`: 0 real hits).

## Correction of my own earlier reading
On 09-27 (d181) I wrote that "the process that died is node/V8 itself". Taken alone that fit, but the machine-wide picture above (Defender, Vanguard, the kernel, all `c0000005`) makes **the machine the more likely common factor, not node.** The 09-27 note's other conclusions stand: not fixable in our code; not the op sequence; not memory pressure.

## Proposals (nothing built)
1. **For the keeper:**
   - Look in the BIOS: is EXPO (or a manual 6000 MT/s) on? If so, try its JEDEC default, or EXPO with more SoC/VDD voltage per the board's guide.
   - Run a memory test: Windows Memory Diagnostic, or MemTest86 overnight.
   - If it stays, have the 6 kernel dumps read with WinDbg `!analyze -v` (administrator).
2. **For the suite runners (small, tooling only):**
