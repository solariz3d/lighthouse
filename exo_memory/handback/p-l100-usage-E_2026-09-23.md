## 1 · HOW IT READS, AND WHY: measured on L's transcripts BEFORE any key was chosen

The probe (`scratchpad/l100/probe.js`, `probe2.js`) read all **2,707** transcript files, 312,774 rows, and 78,350
usage rows:
- **One response is several rows sharing `message.id`.** 39,203 repeats have identical usage. **In 1,603, the
  usage differs**, and in every sampled case only `output_tokens` differed, growing (5 → 231). Some rows are written
  mid-stream. **So each response is counted once, with each field at its MAXIMUM across its rows.**
- **The key is `message.id`, not `requestId`:** every usage row has a message id, **92 have no `requestId`**, and no
  message id spans two request ids.
- **Dedup works across files:** 114 responses sit in two files (a resumed session copies earlier rows), and **391
  exist ONLY in a `.jsonl.orphaned` file**, so orphaned files are read. Subagent transcripts
  (`<session>/subagents/agent-*.jsonl`) are read too, under the seat whose session spawned them.
- **`modelUsage` exists only in `cost-state` rows** (645 on L). Those are running SESSION totals (`totalCostUSD`,
  `startTime`), so adding them would count the same tokens twice. **They are counted and reported, never added.**
  `<synthetic>` rows (the client's own messages, e.g. an expired login) are skipped and counted.
- **The four fields are the ones `main.rs` already reads** (`extract_usage`, `main.rs:2189`). The packet pointed at a
  precompact hook that prints "read from message.usage"; that phrase is in no file under `~/.claude/shell`, `dev`, or
  `consonance/hooks`/`tools` (grep). The live readers are `main.rs:2189`, `:10865` and `bin/jsonl_tap.rs:72`. I
  followed `main.rs`. Its own test fixture (`:19440–19441`) shows the same request written twice.

**Seats.** The project dir is the cwd with every non-alphanumeric character turned into `-` (`main.rs` `encode_cwd`).
The instances dir resolves the way board-digest.js does it (`CONSONANCE_INSTANCES`, then `instances_dir`).
- `<instances>/main` → MAIN, `/librarian` → LIBRARIAN, `/third-place` → THIRD-PLACE.
- A sibling is named `pane <letter>`: `panes.json` maps cwd → pane, and `letters.json` maps pane → letter (L096's
  mapping).
- A retired sibling not in `panes.json` is still named if one of its session files is a pane id in `letters.json`.
- Everything else is shown under its own dir name, never dropped.

**Keep-warm share** (the registration asks for it, `:124`). A response counts as keep-warm when the last real prompt
before it is the chair's ping (`KEEP_WARM_TEXT`, `main.rs:10776`, matched on its opening words). A `tool_result` does
not end the turn; the next real prompt does.

**Days and the week** use the zone from `--tz`, else `~/.consonance.json` `ambient_tz` (America/Regina on L), else the
machine's. The week is `[reset − 7 days, next reset)`. The reset is strictly after now, so at the reset instant the new
week begins.

## 3 · THE LIMIT: typed, never guessed, and what it COUNTS is part of it

**Both a flag and a config key, and the flag wins:**
- `--limit N --limit-counts <all|no-cache-read|output>` for one run;
- `usage.weekly_limit` + `usage.limit_counts` in `~/.consonance.json` for every run (`usage.reset` likewise).

**Why both:** the config lets the keeper type it once, so every report, including the librarian's at each machine
switch, uses it. The flag lets a single run test a different number without editing his file. **I did not edit the
config.** Until both keys are set, the report prints `limit: not set`, or `set to N, but WHAT IT COUNTS is not set`,
and **no percentage**.

**Why "what it counts" is required and not defaulted:** on L this week, **cache reads are 4,989,326,085 of
5,085,273,506 tokens (98.1%)**. So whether a limit counts cache reads changes the answer about fiftyfold, and picking
one silently would be a guess about the account. **I have not checked how the keeper's weekly limit is measured.** As
far as I know, Claude Code's own usage view shows a PERCENTAGE, not tokens. If so, the number he can actually type may
be a percent at a moment. That would make the useful input a calibration ("the app said X% at time T"), and this tool
does not build that. **Named, not built.**
