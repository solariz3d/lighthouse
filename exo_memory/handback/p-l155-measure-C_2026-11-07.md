## The first thing to say: the logs have NO per-file times
- All six logs are node 24 `--test` output: spec (A's, B's) or TAP (mine). Both reporters print each **test's** duration, never its **file's**, and never which file a test came from.
- So, by the packet, I **stop before running anything** and ask (the ring).
- What I could do without running anything:
  - each top-level test's title is matched to the one test file that declares it, at the sha that log was run on (`git show <sha>:<file>`);
  - a template-literal title's `${…}` matches anything;
  - each file then gets **the sum of its top-level tests' durations**.
- **That figure is in-test time, not a file's wall time.** It leaves out module load, a browser launched in a `before` hook outside a test, and the gaps between tests. All runs were at concurrency 4 under load, so every figure is inflated alike by contention.
- **How well it attributes (checked):**
  - in the four test-fast logs, 3,439–3,479 of 3,463–3,503 top-level tests match one file, with 0 ambiguous. The 24 unmatched (titles built at run time) are 2.9–3.1 s per log;
  - in the two killed full-suite logs, 512 titles match several files. **Every such set is mutation harnesses only** (checked: `pertest.js` prints the sets), so that time is mutation-group time whose file can't be split out.
- inferred: the sums track worker time well. Mine is 4,345 s of in-test time over 1,178 s of wall at concurrency 4 (3.7 of 4 workers busy).
