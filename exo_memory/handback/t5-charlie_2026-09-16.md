## 1 · THE DEFECTS

Line numbers are the copy's. "Caught" = the unmodified `ferry.test.js` goes red on that edit alone.

| # | line | the edit | caught |
|---|---|---|---|
| D1 | 43 | `MIN_SHA = 7` → `4` | **yes** (11 pass, 2 fail) |
| D2 | 118 | `r.sha.length >= MIN_SHA` → `<= MIN_SHA` | **yes** (8 pass, 5 fail) |
| D3 | 160 | `if (prior.length && !added.length)` → `\|\|` | **yes** (11 pass, 2 fail) |
| D4 | 196 | `r.at >= ep` → `r.at > ep` | **no — 13/13 green** |
| D5 | 201 | `/ 60000` → `/ 1000` | **no — 13/13 green** |
| D6 | 202 | drops `&& n >= 0` from the latency filter | **no — 13/13 green** |
| D7 | 204 | `lat[Math.floor(len/2)]` → `Math.ceil` | **no — 13/13 green** |
| D8 | 215 | `RATE_FLOOR = 10` → `1` | **no — 13/13 green** |

Baseline: the original against the same suite is **13 passed, 0 failed**. The copy as delivered is
**6 passed, 7 failed** — so the suite does fire, which is exactly why the five it cannot see are the
dangerous ones. **The suite never calls `report()`** (`grep -c "report(" ferry.test.js` → **0**), and
D4–D8 all live in `report()`.

### D1 — `MIN_SHA = 4` (line 43)

**What it does.** Lowers the floor `record()` refuses below. The copy accepts a 4-character sha and
exits 0 where the original refuses and exits 2:

    COPY:     {"sha":"fc27","panes":["A"],…,"already":false}     exit=0
    ORIGINAL: refusing sha "fc27": need >= 7 chars — …           exit=2

**Consequence.** The original's own comment at `:39-42` and `:127-130` says why 7: *"at 6 characters
collisions stop being hypothetical"*, and a short row *"writes as success but is never counted, and
its prefix then blocks recording the full sha"*. At 4 characters a ledger row matches by prefix
against **any** commit sharing those 4 hex digits — roughly 1 in 65,536 per pair, which over a
multi-hundred-commit history is a matter of when, not whether. A collision marks an artifact ferried
that was never ferried, and the miss it hides is invisible by construction.

### D2 — the join filter is inverted (line 118)

**What it does.** `usable` becomes rows whose sha is **at most** `MIN_SHA` long instead of at least.
Combined with D1 it means: **only shas of 4 characters or fewer are counted, and every real 40-character
row is discarded.**

**Consequence, and this is the worst of the eight.** The copy accepts a full-sha write and then denies
it happened. Measured end to end:

    COPY: --record fc27b03a…c50e A   ->  {"…","added":["A"],"already":false}   (a successful write)
          ledger now holds that row
    COPY: --due                      ->  fc27b03  2026-08-20 07:00  artifact 1
                                         5 artifact commit(s) never ferried

**The row is in the ledger and the tool says the commit was never ferried.** The header at `:19-22`
says this tool exists so that *"a miss is a visible line rather than an absence"*; `:176-181` records
that an earlier version doing precisely this — *"accepts a write and then silently omits it from its
own count"* — was *"the failure this whole tool exists to make visible, reproduced inside the tool on
its first use."* D2 reintroduces it.

And the inversion is complete, not partial. With a ledger holding **only** a 4-char row:

    COPY:     4 artifact commit(s) never ferried   (the short row counts)
    ORIGINAL: 5 artifact commit(s) never ferried   (the short row is refused)

### D3 — `&&` becomes `||` in `record()` (line 160)

**What it does.** The no-op branch now fires whenever *any* prior row exists, regardless of whether
new panes were supplied. A genuinely new pane on a known sha is silently discarded.

**Consequence, measured — record pane A then pane B on one sha:**

    ORIGINAL   row 1: {"panes":["A"]…}   row 2: {"panes":["B"]…}     both written
    COPY       row 1: {"panes":["A"]…}   row 2: {"…","added":[],"already":true}
               stderr: already recorded: fc27b03a… -> A — nothing added
               ledger: ONE row

This is a verbatim regression to the defect the surrounding comment (`:136-152`) says it repairs:
*"the second `--record <sha> <pane>` wrote nothing, returned null and exited 0 … so the pane list
silently under-reported every multi-routed commit and no operator could see it happen."* The same
comment records the measurement that motivated the fix — *"of 43 countable ledger rows, 6 have a
chair dispatch naming a pane the row lacks within ten minutes"*. **Multi-pane reach becomes
unrecordable**, which is the one thing the `panes` field was ever for.

### D4 — the epoch boundary (line 196) — SHIPS GREEN

**What it does.** `at >= ep` → `at > ep` drops a commit whose timestamp equals the epoch exactly.

**Consequence, and it is not merely an off-by-one: the accounting stops summing.** `before` is
`r.at < ep` and `inWindow` is now `r.at > ep`, so a commit landing exactly on the epoch falls out of
**both** buckets. Measured on a fixture where commit 1's timestamp equals the epoch:

    ORIGINAL   artifact commits 5 · before 0 · since 5      (0 + 5 = 5)
    COPY       artifact commits 5 · before 0 · since 4      (0 + 4 ≠ 5)

The dropped commit is a **ferried** one, so `ferried` falls 3 → 2 while `missed` stays 2: the miss
rate moves from 2/5 to 2/4, **40% → 50%, in the pessimistic direction**, off a denominator that has
quietly lost a row. The epoch is frequently the first ferry's own timestamp (`epoch()`, `:95-96`
falls back to `Math.min(...ferried_at)`), so a commit sitting on that boundary is a normal case, not
a contrived one.

### D5 — latency divided by 1000, not 60000 (line 201) — SHIPS GREEN

**What it does.** Milliseconds become seconds while the label still says `min`.

**Consequence.** A 60× inflation printed under the wrong unit. Measured on the same fixture:

    ORIGINAL   median latency         40.0 min
    COPY       median latency         2400.0 min

40 minutes reported as 40 hours. Nothing in the output hints at a unit change, and the figure is
plausible enough to be quoted — which is how a wrong number survives.

### D6 — the negative-latency filter is dropped (line 202) — SHIPS GREEN

**What it does.** `.filter(n => Number.isFinite(n) && n >= 0)` → `Number.isFinite(n)`, so a row whose
`ferried_at` precedes its commit — clock skew, a hand-typed stamp, a back-dated row — is kept.

**Consequence.** Measured with three latencies of −10, +30 and +40 minutes:

    ORIGINAL   median latency         40.0 min     (negative dropped, median of [30,40])
    COPY       median latency         30.0 min     (median of [-10,30,40])

A nonsense sample silently drags the central statistic down. Note the direction: it makes the ferry
practice look **faster** than it is, so the error flatters.

### D7 — `Math.ceil` for the median index (line 204) — SHIPS GREEN, AND CRASHES

**What it does.** Indexes one position higher.

**Consequence — a hard crash, and reading the diff would not show it.** With exactly one latency
sample, `Math.ceil(1/2) = 1` indexes past the end of a length-1 array; `median` becomes `undefined`,
which is not `null`, so `median.toFixed(1)` at `:220` throws:

    TypeError: Cannot read properties of undefined (reading 'toFixed')
        at Object.report (…/ferry.js:220:74)

`node ferry.js` with no arguments runs `report()`, so **the tool's default invocation dies with a
stack trace and exit 1 the first time exactly one artifact has been ferried** — i.e. on the first
day the ledger is used. For odd n > 1 it does not crash but returns the wrong element (at n = 3 it
returns the **maximum**, not the median); for even n it is identical to the original. **Intermittent
by array length**, which is why no single run would convict it.

### D8 — `RATE_FLOOR = 1` (line 215) — SHIPS GREEN

**What it does.** Removes the n-threshold guarding the percentage.

**Consequence.** Measured with 5 commits in window:

    ORIGINAL   miss rate   n/a - only 5 in window, need 10 before a rate means anything
    COPY       miss rate   40.0%

The comment three lines above it (`:210-213`) is the record of this exact harm happening twice:
*"The first version printed 97.2% off a denominator the instrument could not have observed; the fix
made the window honest and immediately produced 0.0% off n=3, which is the same defect pointing the
other way and reads as a clean bill of health."* At a floor of 1, a single in-window commit yields
`0.0%` or `100.0%`. **D8 is what converts the other defects from wrong counts into a confident wrong
percentage** — it is why the full copy prints `100.0%` rather than an honest `n/a`.

## 2 · WHICH FINDINGS CAME FROM READING AND WHICH FROM RUNNING

**From reading** (`diff -u` against the repo copy, plus the surrounding comments, which state the
intended invariant beside almost every line that was altered):

- All eight edits, their locations, and what each was *meant* to be. The file is unusually
  self-documenting, so for D1, D3 and D8 the comment sitting directly above the changed line
  describes the harm the change reintroduces. Reading alone was enough to call these wrong.
- D2's inversion and D4's boundary shift are legible as inversions on sight.

**From running** — and none of the following is available by reading:

1. **That five of the eight pass the entire test suite.** Only by building eight single-edit variants
   and running the unmodified suite against each (`13/13` green for D4–D8) can you know which
   defects the room's own guard cannot see. This is the finding I would put in front of whoever
   proposed the rewrite.
2. **That D7 crashes.** `Math.ceil` versus `Math.floor` reads as a rounding preference. It is an
   out-of-bounds index that makes `report()` throw a TypeError at n = 1, and be silently wrong at
   other odd n. I found this only by running `report()` against a one-sample ledger.
3. **The magnitudes.** 40.0 → 2400.0 min (D5); 40.0 → 30.0 min (D6); `n/a` → `40.0%` (D8). Reading
   gives you "the unit is wrong"; running gives you the number a person would actually read and quote.
4. **That D4 breaks the accounting identity.** `before + inWindow ≠ total` is derivable on paper, but
   I only trusted it after seeing `5 · 0 · 4` printed.
5. **The write-then-deny behaviour.** That `--record` reports `"already":false` with `"added":["A"]`
   — an unambiguous success — and `--due` then lists the same commit as never ferried, is a two-command
   sequence, not a line.
6. **The D3 no-op text.** That the copy prints `already recorded: … — nothing added` when a *new*
   pane was supplied, i.e. it actively asserts the correct-looking thing while dropping information.
7. **The compound result** in §0: 3 ferried reported as 0, with `100.0%`. The individual diffs do not
   predict how they stack.

**The honest asymmetry:** reading found *what* changed, and did it faster and more completely.
Running found *what happens*, and it is the only thing that separated "five edits in `report()`" from
"five edits no test in this repository can see, one of which crashes the default invocation."
