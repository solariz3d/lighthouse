## 3 · THE SPLIT — and the readers, counted

**209 tracked files name `board.jsonl`**, of which **59 are code** (`*.js`, `*.rs`, `*.ps1`) and the rest prose
(59 hand-backs, 57 `loop/`, 17 `librarian/`). The chair's "about 56" matches the code count. Excluding tests,
**26 distinct sites resolve the board path**, and **there is no shared resolver** — at least six mechanisms:
`CONSONANCE_BOARD` (board-audit.js:33, chain-status.js:370), `BOARD_LEDGER` (boundary-check.js:91), `LAP_BOARD`
(lap-row.js:739), `CONSONANCE_DATA` (residue.js:532), `~/.consonance.json` `data_dir` (deference-unit.js:157), and
**four hard-coded literals** (agreement-spread.js:252, balance-check.js:196, board-audit.js:33, residue.js:532) —
which is the exact thing `board-compact.js`'s own header warns about: *"a tool that guesses a data dir reports about a
disk nobody asked about."*

**THE INSIGHT THAT SIZES THE WHOLE JOB: the 100 MiB limit is a TRANSPORT constraint, not a storage one.** The local
file can be any size; GitHub only ever sees what `state-sync` puts in the `consonance-state` repo. **Only 4 files
cross that boundary** — `state-sync.js`, `ledger-union.js`, `sync_launch.rs`, `chain-status.js` — and **no tool reads
the state repo's board copy** (chain-status.js:971's `store` is `path.dirname(LEDGER)`, the *data* dir, not the state
repo). So:

**THE SMALLEST CHANGE THAT WORKS — split at the transport boundary, leave the local file whole.**

1. **`C:\Consonance\data\board.jsonl` stays one whole file.** **All 26 reader sites change: zero.** This is the whole
   point of the design and it is why I recommend it over an archive split.
2. **`state-sync` pushes `data/board/000.jsonl`, `001.jsonl`, …** — fixed slices of the board **in file-position
   order**, capped by **bytes** (40 MiB suggested), not by rows.
3. **Shard by POSITION, never by timestamp, and this is measured, not stylistic:** **15,696 of 61,820 parseable rows
   = 25.4% land behind the running `ts` maximum**, and the four calendar months **re-open 12 times** in file order.
   A month-keyed shard is therefore **not contiguous**, and concatenating month shards **would not reproduce the
   file**. Position-keyed shards reproduce it by construction. Today's shape at 20,000 rows per shard:
   **29.4 · 23.8 · 18.5 · 1.5 MiB** — largest 29.4 MiB, a 3.4× margin under the limit.
4. **Only the last shard is ever rewritten.** Every earlier shard is frozen after its first push, so git stores and
   transfers each once. This also addresses a second problem nobody named: the state repo's `.git` is already **61 MB**
   with **16 board objects** across 4 commits, and every future push of a whole board adds another ~50–70 MB blob.
5. **The manifest gets one glob, `board/*.jsonl`, `install: "fast-forward"`.** **No new machinery**: the fast-forward
   mode is already generic and manifest-driven (`state-sync.js:1150` `INSTALL_MODES`, `:1351` the per-file check).
   On install the arriving shards concatenate in name order and the existing fast-forward check runs on the result.

**WHAT WOULD MAKE THIS WRONG TO SHIP:**

1. **If a shard is ever rewritten, the freeze dies** and with it the only reason this is cheap. The board carries
   **260 torn/unparseable lines**; repairing them — which `board-compact.js` deliberately refuses to do — would
   rewrite every shard holding one. **Ship the split only with the rule that shards are append-only and torn lines
   stay torn.**
2. **If the concatenation is not byte-exact, the sha256 index is meaningless** — `.gitattributes` in the state repo
   carries `* -text` for exactly this reason. A shard boundary must fall on a newline, and a torn line must never be
   split across two shards.
3. **If any future reader reads the state-repo copy directly.** None does today. The moment one does, the split
   becomes visible and the 26-site cost returns.
4. **If one shard can exceed the limit.** Cap by bytes, not rows; 20,000 rows is 29.4 MiB today but row size is not
   fixed.
5. **If the keeper wants the board readable as one file in GitHub's web UI.** The split removes that, and it is his
   call, not mine.

**The alternative I did NOT recommend**, and why: an *archive split* (`board.archive.jsonl` + a small live
`board.jsonl`) is the obvious move, but it is visible to readers, so its cost is the 26 sites and six resolution
mechanisms — and I could not measure how many of those readers need full history, so I cannot price it. The transport
split needs no such measurement to be safe.

## 4 · WHAT I COULD NOT MEASURE

- **Whether L has written rows since its 13:44Z push.** I read L's board as the pushed git blob; anything L wrote
  after that is invisible from here, so "L holds 0 unique rows" is true **of the pushed copy**, not of L's disk now.
- **Which readers need FULL history versus recent rows.** I classified all 26 sites by how they *resolve* the path,
  not by what they *need*. That number is what prices the archive design, and I do not have it. My recommendation is
  the one that does not depend on it.
- **How git deltas successive board blobs.** I measured `.git` at 61 MB and 16 board objects; I did not measure the
  push or clone cost, so "each push adds another 50–70 MB blob" is an upper bound, not a measurement.
- **Whether D's next push would succeed.** At 73.2 MiB it is under 100 MiB, so it should — I did not attempt it, and
  attempting it is not mine.
- **Nothing was applied.** No `--apply`, no compaction, no deletion, no write to any stored file.
