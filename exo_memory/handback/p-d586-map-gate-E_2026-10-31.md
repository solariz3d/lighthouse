## 2. The decisions the order left to me

**How the gate learns the repository and the base: from the ring.** Each repository the lap changed gets one line in the ring, written above the `SOURCES:` line:

    BASE: <checkout path> <base commit sha>

Why the ring and nowhere else:
- The packet names the base ("branch … off e80b2af7").
- Only the pane knows which checkout it worked in.
- Nothing else that reaches `call_librarian` carries either of those.

The rules for the line:
- A lap that touches two repositories writes two lines, and each is checked.
- The checkout path is everything before the last word, so a path keeps its spaces. Backticks and quotes are trimmed.
- The commit must be a sha of 7 to 40 hex characters, never a ref, because a ref moves after the packet is sent.
- Placing the line above SOURCES matters: the SOURCES slot runs until a blank line or NEXT, so a BASE line below it would be read as one of its sources.

**What it reads.** It runs `git -c core.quotePath=false diff --no-renames --name-status <base> HEAD` in the named checkout.
- A rename or a split therefore counts as the files it deleted and created.
- Rows marked A or D under `src/`, `app/`, `consonance/src-tauri/src/` or `consonance/tools/` are gated.
- Any file named `MAP.md` in the diff counts as the map change. That covers t180's root `MAP.md` and lighthouse's `consonance/src-tauri/src/MAP.md`.
- A MAP.md is never itself counted as a gated file.
- Files changed in place are not gated, as Part 3 says.
- The list in a warning is capped at 40 files, with "+N more".

**What each case does:**

| case | gates_mode light | gates_mode strict |
|---|---|---|
| nothing created or deleted | delivered, `[map gate: <checkout> b..h — no source file created or deleted]` | same |
| created or deleted, and MAP.md changed | delivered, `[map gate: … — N source file(s) created or deleted, and MAP.md changed]`, posted | same |
| created or deleted, no MAP.md | delivered with `[MAP NOT UPDATED — <checkout> b..h: N … : A path, D path …; gates_mode light, strict would refuse]`, posted | **refused**. The reply names the files and the recovery, and the attempt is kept on the board (`call_librarian REFUSED (map)`). |
| the gate cannot run (see below) | delivered with `[MAP GATE COULD NOT RUN — <checkout> <base>: <why>; gates_mode light, strict would refuse]`, posted | **refused**, same as above |
| no BASE line | delivered with `[NO map check — this ring names no BASE: line …]`, posted | same |

The gate cannot run when:
- the line names no commit or no checkout;
- the commit is not a sha;
- git cannot open the folder as a checkout;
- the base is not a commit there;
- git itself does not run;
- the diff fails;
- the gate's blocking task does not finish.

**Failures are never silent.** Every failure is a line in the delivered ring and a row on the board. Strict refuses on a failure, as the order asks.

**A ring with no BASE line is not refused, in either mode.** Laps that change no repository (research, docs-only work, collations) have nothing to name. The skip is marked in the ring and counted on the board, so how many rings skip the gate is measurable. This is also the gate's open evasion: a pane can omit the line. See §5.

The mode is read on the calling thread, before the blocking task starts. Under `cargo test` it is thread-local, and the task runs on another thread.
