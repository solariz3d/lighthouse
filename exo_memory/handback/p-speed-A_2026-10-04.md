## What was built
1. **Coarser preview while a brush drag is open.** `app/preview/coarse.js` thins a core segment's precomputed row grid (`seg.fractions`) to every 6th fraction, both road edges kept, memoised so neighbouring segments still share one grid. `preview.js` sets detail 6 while `st.brush` is open and schedules ONE full-detail rebuild 250 ms after release (cancelled by a new drag, cleared on dispose). The model returns the REAL segments, never the coarse ones.
2. **Pointer moves coalesced** in `app/core/panel.js`: at most one `shell.brushTo` per animation frame with the latest position; release applies the one still waiting.
3. **A state change that is not an edit** no longer rebuilds a closed loop (same resolved document and same detail returns `how: 'same'`).
4. **Segment change key hashed** (`app/preview/segkey.js`, 64-bit, replaces `JSON.stringify`) and `ghostFor` builds batches only from the new pieces (`batchesOf(mesh, fromPiece)`).

## What this does NOT do, stated plainly
- **Coalescing cannot meet a per-step 2x bar.** It stops steps queueing behind each other (felt lag) but does not shorten one step. The 3.0x is the detail mode; the bar's number is E's re-measure, not mine.
- **Not helped:** the cup oval (no `fractions`, about 640 ms/step, unchanged 642 -> 639); `toSegments` of the whole document on every keystroke (about 78 ms; a per-piece memo would touch the adapter and so the export's code: not done); validation stays full on a closed loop (about 275 ms; the panel already coalesces it).
- **Plan item 4 (rebuild only the brush-radius cells) not built:** my own bar was met without it, and it is the riskiest of the lot.
- **Not verified:** real WebView/GPU time (node numbers are a floor); the keeper's felt result; the rate of full-detail snap-back (a visible change of section step, about 6 degrees where it was 1, while dragging, back to full 250 ms after release).
- `maxSeamDeg: 4` does nothing on core segments (they use `seg.fractions`), so the plan's mesh-option route does not work.
- Fast key risk: a 64-bit hash, a false "unchanged" would show a stale mesh with a chance of about 2^-64 per comparison; equality was tested against JSON on real segments (the same segments differ).
