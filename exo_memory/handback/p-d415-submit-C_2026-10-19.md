## §1 What it does (main.rs line numbers at 143e1612)

- `deliver` (:11509) is the one delivery, run over a writer and a screen reader so it needs no PTY:
  - the paste, its `submit_delay_ms` wait and the first `\r` go out exactly as before, in ONE call under
    the pane's lock;
  - then the composer is read at 200, 300, 600 and 1,200 ms (`SUBMIT_CHECK_GAPS_MS`, :11424). Its
    doc gives the numbers' reasons: doubling because a busy TUI needs longer, not more often; 2.3 s in
    all, 2.5× the 900 ms ceiling that failed on 2026-08-25; inside the MCP caller's 15 s;
  - each retried Enter is a lone `\r` in its own lock call, so the lock isn't held while it waits.
- `submit_step` (:11455), pure:
  - Empty → Submitted. This is the composer rule's Empty, so a dim suggestion reads empty.
  - Unreadable → Unknown. No key is pressed and it's never called submitted.
  - HasText that isn't ours → NotOurs. No key is pressed.
  - HasText that is ours → RetryEnter, up to 3 times, then NotSubmitted.
- `ours_in_box` (:11471): the composer row and the rows under it, down to the next separator rule. It
  counts as ours if those rows hold the receipt's head or tail needle, or a collapsed
  `[Pasted text #k +n lines]` whose n is the message's newline count.
  - **That last case is beyond the plan's rule 1, and it's needed.** A long ring sits in the box as
    that placeholder, not as its words, so a needle-only rule would read it as not ours and never
    retry it. That is exactly the 14:53 case.
  - checked (my pane's capture, `C:/Consonance/data/captures/0845a868-….log`, `grep -ao "Pasted.\{0,40\}"`):
    the D415 packet (14 newlines) showed `#88 +14 lines`, and the 12:59 heads-up (5) showed `#87 +5 lines`.
- `inject_to_pane` (:11391) now takes `&PaneEmus` and returns `Result<Submit, String>`, for all seven call
  sites (the arch test's derived list): dyad_spot, drain_inboxes, deliver_pull, keep_warm_send,
  chair_inject_exec, librarian_call_exec, pane_call_librarian_exec.
- `Receipt` gains `NotSubmitted`. `delivery_receipt` (:11571) gives `Received` only for a render AND a
  submit; text still in the box is `NotSubmitted`; anything else is `Unconfirmed`.
- What each sender is told:
  - `ring_reply` (:12710): "delivered to X and submitted (…)", "NOT SUBMITTED — the text is in X's
