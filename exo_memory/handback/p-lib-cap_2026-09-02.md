## 5 · ITEM A — THE CHARS-VS-BYTES DERIVATION, STATED AS A DERIVATION

The source states this in a comment; the packet is right that a derivation living only in a comment
is not a hand-back. Re-derived here independently rather than copied.

**The only measurement of the host's cap anyone has is its own refusal:**

    CLAUDE.md is over the 150.0k-char limit (906.3k chars)

printed against a file measured at **915,994 bytes**.

**Step 1 — `k` is 1000, forced by arithmetic rather than chosen.** In UTF-8 a Unicode scalar costs
1–4 bytes, so scalars ≤ bytes. A UTF-16 code unit costs ≥1 byte too (BMP: 1–3 bytes per unit;
astral: 4 bytes per 2 units, so 2 bytes per unit). **Under every counting convention the host could
be using, chars ≤ bytes.** Then:

    k=1000: 906.3k = 906,300 chars  <=  915,994 bytes   POSSIBLE
    k=1024: 906.3k = 928,051 chars  >   915,994 bytes   IMPOSSIBLE

**And it is robust to the rounding**, which the source does not say and should: at k=1024, `906.3k`
is at minimum 906.25 × 1024 = **928,000**, still greater than 915,994. So 1024 is ruled out for every
value the display could have rounded from. **The cap is 150.0k = 150,000 characters.**

**Step 2 — bounding in BYTES is the conservative side of the same inequality.** Because chars ≤
bytes, `intake ≤ 150,000 bytes ⟹ intake ≤ 150,000 chars`, whatever "char" means to the harness. The
converse fails: a 150,000-char bound admits a 600,000-byte file. **The direction is right, and right
for a stated reason rather than by luck.**

**Step 3 — what the conservatism costs, measured twice.**

    the harness's own two figures:  915,994 / 906,300 = 1.010696
    tonight's shipped shell:        141,242 / 139,770 = 1.010532

**~1% of the shelf** — and the second figure is an independent confirmation of the first. The source
predicted 1.0107 from the harness's two numbers *before* any test printed a ratio, and the shipped
artifact came back 1.0105. **The derivation made a prediction in advance and the prediction held.**

**WHAT THIS DOES NOT ESTABLISH, and here the source overstates slightly.** `150.0k` is displayed to
one decimal, so the true cap lies in **[149,950, 150,050)**. A byte bound of exactly 150,000
therefore does *not* strictly guarantee compliance if the real cap is 149,950 — a 150,000-byte intake
could be 149,999 chars. It is moot at a 10,230-char margin, and `INTAKE_HEADROOM` (8,000) covers the
50-char band forty times over. **But the guarantee is "conservative by ~1%, minus a 50-char display
uncertainty", not "conservative, full stop."** Nothing needs changing. The claim needs saying at its
real strength.
