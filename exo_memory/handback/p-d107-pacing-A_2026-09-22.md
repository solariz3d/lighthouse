## 0 · THE LIMIT — none is published, so the numbers are DEFAULTS

**Vercel publishes no rate-limit number for the AI Gateway.** Source: https://vercel.com/docs/ai-gateway/rate-limits,
"last updated 2026-09-08", read 2026-09-22. What the page says, verbatim:
- *"Limits can change, so this page describes behavior rather than fixed numbers."*
- *"AI Gateway does not rate limit paid-tier requests. The free tier applies lower per-model limits…"* No RPM, RPS or
  concurrency figure appears, and nothing per key.
- *"Some `429` responses include a `retry-after` header with the number of seconds to wait. Honor it when it is
  present."*
- *"…back off exponentially otherwise."* · *"Keep retries bounded."*
- *"…a `429` on either tier may come from the upstream provider"*, possibly with the provider's own body. So this
  code keys on the STATUS, never the body.

The pricing page (https://vercel.com/docs/ai-gateway/pricing) adds only that free-tier requests *"are also rate limited
per model"*. The lookup was a researcher sub-agent's, and I did not open the pages myself.

**The defaults, stated as defaults.** They are in the code comment, which cites the page:
- **gap 2 s**, from the END of one call to the start of the next;
- **backoff 5 s doubling, capped at 60 s**, reset by any non-429 answer;
- **no in-pass wait longer than 120 s.**

**What the 2 s is argued from (measured on D):**
- **Real call length.** `jev_judge.jsonl` has 88 ok rows: median `ms` 336, max 1,231. So a 25-call pass takes about
  60 s, far inside the 10-minute cadence.
- **The failures.** `runner.log` had 60 lines at 10:3x, including **13 `failed (429)` beside 20 `failed (503)`**
  (`grep -oE "failed \([0-9a-z]+\)" runner.log | sort | uniq -c`).

2 s is a guess at "slow enough to stop tripping a per-model limit nobody will name". **The falsifier:** if 429s persist
at a 2 s gap, the gap is too small, or the limit is per day, or it is the other machine.

## 1 · THE DESIGN

**Where it lives: ONE shared call path.** `jev-judge.js:225` and `jev-shadow.js:212` both call `jev.ask({…, fetchImpl})`.
In the runner `cfg.fetchImpl` is undefined (`jev-shadow-runner.js:246/:272`), so both default to `globalThis.fetch`. So
`ask()` looks up `defaultPacerFor(fetchImpl)`, which is **one module-level `SHARED_PACER` when fetchImpl is the real
fetch, and null for a stub.** The judge and the shadow run in one runner process, so they share one spacing. **This
needed no change to C's shadow logic.** judgePass gains one optional `pacer` pass-through, for its test only.

**The pacer (`createPacer`)**, with `now` and `sleep` injectable:
- `before()` waits until `max(lastEnd + gap, notBefore)`.
- `after(status, headers)` stamps `lastEnd`. On a 429 it sets `notBefore` from `Retry-After` (delta-seconds or an
  HTTP-date), else from the backoff.
- A network failure counts as a call ended, with no backoff.
- A 5xx gets the gap, not a backoff: it is not a rate limit.
- **The first call of a process does not wait.** The gap is **not counted in `ms`**, which stays the call.

**A 429 is NOT retried inside `ask()`.** The header's rule, *"surfaced once, never retried silently"*, is kept. The item
stays skip-and-retry in both callers (L078/L079). Only the NEXT call waits.

**A wait over 120 s is not slept on.** For example `Retry-After: 3600`: the next call is refused UNSENT with *"gateway
returned HTTP 429 earlier: the next call is deferred N s … not sent, retried next cadence"*. Both callers'
`transientStatus` read `HTTP (\d{3})` as a 429 skip, so the rest of the pass is deferred rather than stalling the
runner. That message holds no key or body; it goes through `scrub()` like every other.

**The daily cap is unchanged.** `callsToday` counts `ok` rows, and a 429 or deferred item writes no row. The per-pass
`maxCalls` is unchanged too. A deferred call does take a slot in the batch; it is retried next pass.

## 3 · WHAT I DID NOT VERIFY, AND WHAT THIS CANNOT DO

- **The other machine.** L and D share one key, and **each process paces only itself.** Two runners at 2 s each are one
  call per second on the key. If L's runner is also live and 429s persist, the fix is a longer gap on one machine or a
  schedule offset, not this file.
- **That the shadow's live path is paced.** This is read from source, not run: `shadow()` defaults `fetchImpl` to
  `globalThis.fetch` (`jev-shadow.js:176`) and passes it to `ask()` (`:212`), so it gets the shared pacer. No test makes a
  real-fetch shadow call, because that would need the network or a real sleep. **If C ever passes a WRAPPED fetch, the
  pacing silently switches off for it:** the identity check sees a stub. The exact line for C, if that is wanted: pass
  `pacer: require('./jev-ask.js').defaultPacerFor(globalThis.fetch)` into the `jev.ask` call at `:212`.
- **The live effect.** No restart by me. After the librarian restarts the runner, the check is runner.log's `failed (429)`
  count per pass going to about 0 while `asked` holds. **Not yet measured.**
- **Whether the 429s are per-minute, per-day, or the provider's.** The page does not say, and the body shape does not
  tell them apart reliably. **The falsifier:** if a day's first pass still 429s at a 2 s gap, the limit is not a rate.
- **The key.** It is not in any new message. The deferral text carries no key or body and goes through `scrub()` like
  every error.
