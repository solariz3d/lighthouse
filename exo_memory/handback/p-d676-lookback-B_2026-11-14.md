## 2. What CAN change the run while he looks back (for the ruling; nothing built)

**(a) The mouse still steers the run during a glance. This is the likeliest cause of "sometimes".**
- inferred, by the code: `view()` turns the picture by `aim_yaw + kGlanceTurn * look_back` (`game/shell.cpp:185-186`), and
  `aim_yaw` is `mapper_.yaw()`, the same yaw `sample()` gives the run (`game/input.cpp:71`).
- `on_mouse` keeps feeding the mapper while V is held (`game/shell.cpp:76-78`).
- So if he moves the mouse while looking back, to look around behind him, his run turns by the same amount. At top speed a turn costs
  speed and can put him into a wall: "messes with my sprint speed", "hitch on something".
- It happens only when the mouse moves during the glance, which would be his "sometimes".
- The game's comment, "the view only: the run carries on ahead", is broken by this one path.
- **Not shown on his play.** A kept run records the input, not the glance, so no kept run says where he held V. I cannot name a run
  and ticks, which is the packet's fallback.

**(b) A long frame while the view is turned. Not measured.**
- A frame over 100 ms counts as 100 ms (`game/loop.h`, `FixedStep::advance`), so the run loses the rest of that time in real seconds.
- That happens only if drawing the view behind stalls a frame by more than 100 ms. Nothing here measures it.
