**Additive to the contract, and needed for parity:** `readDiscipline(file = DEFAULT_RUBRIC)` and `DEFAULT_RUBRIC`
(`jev/METHOD.md`).
- A provenance line on top of the rubric would otherwise become part of the discipline, and the module's prompt would stop
  being byte-identical to the room's.
- `readDiscipline` drops exactly a line-1 `<!-- jev: … -->` and nothing else, so a swapped-in rubric (config `rubricPath`)
  is used whole.
- **Whoever builds the prompt (the judge) should read the rubric through `readDiscipline`, not `fs.readFileSync`.** That is a
  note for B/C/E's judge.

## 2 · THE CONTRACT, CORRECTED: `narrowedView(transcriptPath)` returns `{ user_context, assistant_move }` or `null`, not a string

- The contract says `→ string`. The room's function returns the two fields, and **`buildPrompt` puts them in two different
  places in the prompt.** A string would have to be parsed back apart, and parity would be lost.
- **Consumers should pass it straight through:** `buildPrompt({ view: narrowedView(p), discipline })`. `null` means "no
  judgeable move" (skip the call).
- The correction is written in `prompt.js`'s header too. **Nothing under `jev/` depended on the string form when I checked**
  (`grep -rn narrowedView jev/` found only mine).
