# P-D119-GAPS · ALPHA — the 42 gaps are numbers the OTHER machine spent, not laps that lost their rows. Nothing is missing, and the ledger's counts are not floors for this reason. The cause is one line: `mintId` shares the NUMBER across machines and makes only the LETTER local

**Pane A, machine D, 2026-09-22 16:2x–17:0x. Read-only:** no ledger write, no `--void`, nothing committed. HEAD `9273064`
(C's floor-guard repair). The chair's question was the right one to ask — *did these laps RUN and lose their rows, in
which case the room has lost work it does not know about?* **No. They were never minted.** Every figure below comes from
one command against D's live ledger, the board, the attic and git.

## 3 · THE CAUSE, IN ONE FUNCTION

`consonance/tools/lap-row.js:474-481`:

    function mintId(all) {
      const max = all.map(r => Number(String(r.lap || '').replace(/^[A-Za-z]/, '')))
        .filter(Number.isFinite).reduce((a, b) => Math.max(a, b), 0);
      return machineTag() + String(max + 1).padStart(3, '0');
    }

**It strips ANY letter prefix and takes the maximum NUMBER over every row on the ledger, then prefixes the local
machine's tag.** The number space is shared between the machines; only the letter is local. That is deliberate — the
comment above it says a parse that knew only `L` would re-mint an id that already exists — and the gap is its
consequence, not a defect in it.

**Proved, not inferred:**

    the 09-09 migrate stamp (attic)          2026-09-09T14:59:05.515Z
    D055's first row                          2026-09-09T15:10:41.323Z     — 11 min 36 s later
    highest lap NUMBER on the ledger
      at that instant                         54, held by L054   (54 distinct L ids present)
    so mintId returns                         D055

The migrate brought the laptop's record, whose highest number was 54. The desktop's next mint was therefore D055, and
**the numbers 13–54 were never available to it to mint.**

## 6 · THE ANSWER TO WHAT WAS ASKED

**Case two: ids that were never used — and more precisely, never minted.** Nothing ran under D013–D054, so **no work is
missing and the ledger's lap count is not a floor on this account.** The room has not lost laps it does not know about.

**What this does NOT establish**, because the chair's framing deserves the limit stated:
- **It is about ROWS, not about work.** It says no lap ran under these ids. Work done with no lap open at all is
  invisible to every instrument used here, and this says nothing about it.
- **It is this machine's ledger.** L's own copy was not read. The prefix-stripping mint means L has the mirror shape, and
  the reissue file — not this one — is the master for what happened to L055–L065.
- **The union could still hide a loss** by a different mechanism, and my D113 §-ATTACK names two; this account rests on
  the attic copy being intact, which I checked by reading it, not by verifying it against a second source.

## 7 · WHAT I WOULD DO WITH IT, AND WHAT I WOULD NOT

**Worth one line somewhere a future seat will meet it** — `lap-row.js`'s header, beside the mint: *a gap in one machine's
id range is the normal shape of a shared number space, and is not evidence of a missing lap.* Three seats have now spent
time on these gaps (C's guard, the reissue file, this). The fourth should meet the answer instead of the puzzle.

**What I would NOT do: make the ids per-machine to close the gaps.** The shared number space is what stops two machines
minting the same id, which is the failure the reissue file documents and which costs real confusion. **The gaps are the
price of that guarantee, and they are the cheap half of the trade.** Tidying them would be tidying away a guard.
