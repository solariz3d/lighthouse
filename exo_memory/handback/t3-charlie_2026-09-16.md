## 1 · THE ANSWER, BEFORE THE LIST

**The question is well-formed on one side and has no referent on the other.**

- **"Is the corpus bloated"** is asked here repeatedly, measured at least four separate times, given a
  registered claim with a falsifier, given two purpose-built instruments, and ruled on in the binary
  with a constant. It has a **unit** (bytes against the seat's intake cap), a **budget** (150,000),

## 4 · THE PART THAT HAS NEVER BEEN ASKED, WITH ITS EVIDENCE

**Nowhere on disk does anything ask, measure or rule on whether the code is too large for what it
does.** Stated as absences with the command that shows each:

- **No budget.** `grep -n "const.*CAP.*usize\|SOFT_CEILING\|INTAKE_LIMIT"` over `main.rs` returns
  ceilings for the **shell** (140,000), the **librarian intake** (150,000) and the **Third Place
  intake** (150,000). There is no constant anywhere bounding lines, files, functions or binary size.
- **No gauge.** `ls consonance/tools/` has `corpus-age.js` and `forget-rate.js` for the corpus. It has
  **no counterpart** — no `code-age`, no size report, no complexity or duplication measure. The one
  code-facing census, `tool_audit_tally.js`, counts *test coverage of the shelf* (its own header,
  `:13-15`: instruments, tests, untested, orphan).
- **No registered claim.** The journal's numbered registrations carry #44 on corpus deletion and #45
  on instruments reaching outside the machine (*"zero network calls across 44 instruments"*) — a
  **direction** claim, not a size one. `grep -rn` for a registration about code size returns nothing.
- **No retirement rule.** `SOURCE.md` ends with one for the deck — *"give it a trigger in SOURCE.md, or
  retire it"* — and `BOOT.md:155` is one for the corpus. There is no sentence anywhere saying an
  instrument should be retired for being unused.
- **And one real asymmetry that cuts the other way, in the code's favour:** the Rust tree carries
  exactly **one** `#[allow(dead_code)]` (`capture_audio.rs:236`, `grep -rn` across `src/*.rs`), so the
  compiler is not muted and dead code surfaces as a warning on every build. **The code has a
  continuous, un-silenced check for the thing nobody asks about; the corpus has no such thing and
  needs an instrument run by hand.** That is why the corpus question got instrumented and the code
  question did not — and it is a decent reason, not an oversight.

## 5 · IS THE QUESTION MALFORMED? PARTLY — AND HERE IS WHAT WOULD HAVE TO BE DEFINED

The corpus half is **not** malformed: "bloated" has a referent, a unit and a threshold — bytes against
`LIBRARIAN_INTAKE_LIMIT`, and the room has both a number (16.8x) and a death (1,305,657 B) to anchor it.

The code half **is** malformed as asked, and in a specific way: **"too large for what it does" has no
denominator here.** 29,142 lines is not a verdict against anything. Before it could be one, three
things would have to be fixed, and I name them rather than supply them:

1. **A cost.** The corpus's cost is that a seat stops answering. The code's cost is not stated
   anywhere: is it compile time, is it the surface a pane must read before editing, is it the number
   of places a rule can hide? Each gives a different measurement and they do not rank the same files.
2. **A unit that is not lines.** `forget-rate.js:12-16` already settled this exact error once, on the
   corpus: `git log --numstat` "counts LINES INSIDE FILES, so it moves when somebody fixes a typo",
   which is how a registered falsifier "got satisfied by noise within four hours." A line count of
   `main.rs` is the same unit and would fail the same way. **The room has already paid for this lesson
   on one side and would be buying it again on the other.**
3. **A separation the raw figure hides.** `main.rs` is 16,671 lines of a 29,142-line tree, but a large
   share of it is `#[test]` bodies and doc comments like `:6780-6845` — 65 lines of reasoning carried
   beside one constant. **A line count cannot tell load-bearing prose from dead weight, and this room's
   whole practice is to put the reasoning next to the code.** Any honest code-size measure here must
   first decide whether the documentation it deliberately carries counts as bloat. I think that is the
   question actually worth asking, and it has never been put.

**What I would not do:** answer "the corpus, at 16.8x" as though it settled the keeper's *or*. It is
the only side with a number, which is a fact about the instruments, not about where the weight is.
