## 2 · THE GUARD, AND THE ONE DECISION INSIDE IT

Placed beside each file's existing dream gate, in that gate's idiom (`process.exit(0)`, no output):

    if (process.env.CLAUDE_OVERSEER_RUN) process.exit(0);

- **Truthy, not `=== '1'`.** The overseers test `=== '1'` (`l2-overseer.js:109`, `l3-overseer.js:120`) and set exactly
  `'1'` when spawning (`l2-overseer.js:132`, `l3-overseer.js:142` — measured, not quoted from the packet). I diverged
  deliberately: a guard whose failure mode is *machine text read as the keeper's* should fail CLOSED, and any non-empty
  value means an overseer set it. **Mutant #4 pins it** — `=== '1'` goes red against `CLAUDE_OVERSEER_RUN=true`.
- **Silent exit, not `{}`.** The guarded overseers write `{}` (`l3-overseer.js:121`); these two files' dream gate exits
  with no output, and has done so in production since 2026-08-17. I matched the file I am in rather than the file next
  door. If the room prefers one shape everywhere, that is a one-line change in four places and is not mine to pick.

## 3 · THE FINDING THIS TURNED UP — it corrects my own D093-A

**The leak was not only "machine text scored as the keeper's". It was also feeding the judge its own prior verdicts.**
Both hooks surface recent NON-STABLE L3 verdicts, WITH their `specific_observations` text. An overseer's child inherits
`CLAUDE_OVERSEER_RUN=1`, fires these hooks, and — before this edit — received them. The probe shows it directly: the
seeded `quiet_spiral` verdict was surfaced into the overseer-child run, both hooks, both times.

**So D093-A §1's answer was true of the prompt and false of the child's context.** Yesterday I measured three channels
into the L3 prompt (template, job file, WELFARE.md) and a fourth (the transcript extractor) and reported the invocation
*blind*. The channel I did not test was the judge's OWN session hooks. ASK-001 item (1) — "blind L3 invocations to prior
L3 verdicts" — was therefore **not** already satisfied; it is satisfied by this packet's edit, once installed.
