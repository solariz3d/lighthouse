## 2. The rule as built
- Each of forward/back (W S), right/left (D A) and down/up (E Q) resolves on its own. `held` is already in the order pressed (a repeat keeps its place), so on each axis the LAST key seen wins; a key-up removes that key and the other takes over.
- The three axes combine into one direction, which is normalised (`if (n) move(dir / n · k)`), so W+D moves `(W + D)/√2`: 3 m a frame, the same as W alone.
- Shift's ramp still multiplies `k` (W+D with Shift at the press: 12 m a frame, not 12·√2). The arrow keys still all turn, at the same time.
- No other file was touched. `cameras.js` is not mine and was not edited.

## 5. The case I name (the rule is ambiguous here)
**W or S together with Q or E, on a pitched view, is not 1.0× in metres.** The rule as written normalises the INPUT direction, and I did exactly that. But forward follows the view's pitch while up is the world's up, so those two are not perpendicular: looking 45° down, W+E gives about 0.54× a straight line's distance (`inferred:` from `|d + up|/√2` with `d` at −45°; not run). W+D, S+A, D+E and every pair of the horizontal-and-perpendicular kind ARE 1.0× (tested, D+E and W+D). Making it exactly 1.0× in metres needs the frame's view vectors, which are in `cameras.js` (`free.move`), not mine. **Decide whether the keeper's "1.0×" includes that pair; if it does, it is a `cameras.js` change.**
