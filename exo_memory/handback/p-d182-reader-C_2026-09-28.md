## 1 · What was found first: the losses are NOT the heading lag
**Reproduced before any change,** with the current reader (a copy, sha256 ea4fb383b742b333) on B's own control exports
(`…sibling-5bf9d657/…/scratchpad/d182/control/<track>-rebuild/`), with B's exact arguments and then two others:

| export | length arg | width `NaN` (what the runner passes) | width `0` | width `34` |
|---|---|---|---|---|
| sakura_speedway rebuild | 4073 | **LOST at 640 m** (162 stations) | CLOSED, 3,440 m, 861 stations | CLOSED, 3,440 m |
| centrifuge rebuild | 5230 | **LOST at 348 m** (90 stations) | CLOSED, 4,216 m, 1,055 stations | CLOSED, 4,216 m |

**The cause, in the source:**
- The builder's `ui_track.json` has `"width": ""` (`src/export/trackfiles.js` `uiTrack`: `width: m(desc.width) || ''`,
  and the P-LIKE export passes no width).
- B's runner passes `String(parseFloat(''))` = `"NaN"`, and the reader's `+("NaN" || 0)` is `NaN` (line 9).
- **A NaN hint switches off the reader's heading correction for the whole walk:**
  - `usual = Math.max(<recent median>, widthHint)` is `NaN`;
  - so `W_(cs) > usual * 1.3 + 4` is false at every step;
  - so the narrowest-cut search, the reader's only correction for a heading that lags a turn, never runs.
  - The first sustained curvature then walks the cut up the pipe's wall, which is B's "141 m ceiling and up 2° → 60°".
- `0` means "no hint" to the reader (`widthHint` falsy), and the search then runs from the eleventh station on. So the
  same walk with no hint closes.
- **So B's finding is real, and it is a reader defect, but it is not the p-d166 §3 lag.** The reader already handles these
  builder turns. It was disarmed by an argument it did not validate.

## 2 · The fix: REFUSE a hint that is not a number ≥ 0, by name (`tools/read_track.cjs` line 9 → lines 9-12)
**The chair's correction** (01:1x) narrowed route (b) to input validation: refuse a non-numeric width hint loudly, or ignore
it as absent, pick one and say why.

**REFUSE, because ignoring is how this hid.** The reader already ignored garbage in one sense: it quietly turned `"NaN"` into
a width that disarmed its own correction, and two laps were lost with no message. An argument that is not a number is a
caller's bug (here, the export's empty width). The loud answer names it at the first run and puts the fix where the bug is:
- E fixes the export;
- B's runner passes a number.

A silent "treat it as absent" would have been correct on these two tracks, and would hide the next caller's bug the same way.

**The change, every line named** (against the pinned reader, sha256 ea4fb383b742b333 → **ca45c683cf626214**). The one line
`const dir = process.argv[2], lengthHint = +(process.argv[3] || 0), widthHint = +(process.argv[4] || 0), STEP = 4;`
becomes four:
- two comment lines (why);
- `hint(x, what)`, which applies these rules:
  - an absent argument is 0 (no hint), as before;
  - a finite number ≥ 0 is taken, with `0` still meaning no hint, as `reads/readall.js` uses it;
  - anything else throws `read_track: the <length|width> hint must be a number ≥ 0 (0 = no hint), not "<value>"`: an empty
    or blank string, `NaN`, text, a negative number, or infinity;
- the `dir / lengthHint / widthHint / STEP` line, now through `hint`.

Nothing else in the reader changed. `git diff` also shows E's earlier `READ_PROFILE` block, which is in the pinned ea4fb383
already and not mine.

**Its test: `test/read_track_hints.test.js`** (new, 13 tests; the reader run as a child against a folder that does not exist,
so a refusal is seen to come BEFORE the folder is read):
- `NaN`, `""`, `" "`, `abc`, `-3` and `Infinity` as the width, and `NaN` and `""` as the length, are each refused by name,
  non-zero, with no ENOENT;

- **Fixed reader: 13/13. The OLD reader (ea4fb383): 5 pass, 8 FAIL**, the eight refusals. So the test catches the defect.
