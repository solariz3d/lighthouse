# T5 — what is wrong with the ferry.js copy

**ECHO, on D, 2026-09-16 ~05:0x.** Copy under review: `…/scratchpad/t5/ferry.js`. Baseline: the untouched
`consonance/tools/ferry.js` in the repository. Nothing in the repository was edited; nothing installed. My own
harnesses live in my scratchpad (`t5harness.js`, `t5lat.js`, `t5edge.js`, `t5neg.js`, `t5floor2.js`).

**Eight defects, all on single lines. Seven of thirteen unmodified tests fail (exit 1); the repo passes 13/13
(exit 0).** But the count understates it in one direction and overstates it in another, and both are the point:

- **One defect hides three others.** D2 empties the ledger before the latency code is reached, so D5, D6 and D7 are
  *unobservable* in any live run — including a run against the real ledger, which looks merely wrong rather than
  broken. I only found them by crafting a ledger that gets past D2.
- **One defect is covered by a test that passes anyway.** The guard D2 inverts has a test, and that test is green
  on the copy — for the wrong reason (§4).

**The single worst consequence, measured against the live ledger:** the copy erases every ferry the room has ever
recorded and reports the miss rate as total.

    node consonance/tools/ferry.js          (repo)   ferried 63 · missed 640 · miss rate  91.0% · median 15.2 min
    node …/t5/ferry.js                      (copy)   ferried  0 · missed 703 · miss rate 100.0% · median n/a

`ferry.js` is the instrument for *"a finding nobody reads is indistinguishable from a finding nobody made."* The
copy makes every finding read as never-ferried, which is precisely the reading the room has pre-committed to
treating as grounds for calling the committee decorative.

## 1 · THE DEFECTS

### D1 · line 43 — `const MIN_SHA = 4;` (was `7`)
**What it does.** Lowers the floor below which a sha is refused. It is used in two places: the reader filter
(line 118) and the `record()` write guard (line 131).
**Consequence.** `record()` now accepts 4-, 5- and 6-character shas. Measured (`t5harness.js`):

    record() sha len 4/5/6:   REPO refused · refused · refused        COPY ACCEPTED · ACCEPTED · ACCEPTED

The file's own header (lines 38-42) states the invariant this breaks: *"record() enforces the SAME floor the
readers filter on, so a short sha can never be written as a phantom the counts ignore."* **Combined with D2 the
two floors no longer agree, and a 5- or 6-char sha is now writable by `record()` and invisible to every reader —
the exact phantom the comment says is impossible.** It blocks nothing and is counted by nothing.
*Found by reading; confirmed by running.*

### D2 · line 118 — `rows.filter(r => r.sha && r.sha.length <= MIN_SHA)` (was `>=`)
**What it does.** Inverts the usability test in `joinRows`: instead of keeping ledger rows whose sha is long enough
to match safely, it keeps only rows too short to be trusted.
**Consequence — this is the one that matters.** Every sha in the live ledger is 7 or 9 characters:

    sha length histogram in C:\Consonance\data\ferry.jsonl:  {"7":135,"9":1}
    rows with length <= 4: 0        rows with length >= 7: 136

So `usable` is **empty**, every commit joins to `ferry: null`, and all 63 recorded ferries vanish. Isolated
(`t5harness.js`):

    7-char ledger sha matches its commit:      REPO YES          COPY NO — row discarded
    4-char ledger sha matches (must refuse):   REPO no           COPY YES — matched loosely

Both halves fail at once: real entries are dropped, and the unsafe short shas the floor exists to refuse are the
only ones accepted. `--due` consequently lists every artifact commit as never ferried.
*The inversion is visible by reading. **That it discards the entire real ledger is only visible by running** —
reading tells you the comparison is backwards, not that no row on disk survives it.*

### D3 · line 160 — `if (prior.length || !added.length)` (was `&&`)
**What it does.** Takes the no-op branch whenever the sha has *any* prior ledger row, regardless of whether the
call brings new panes.
**Consequence.** A second pane's ferry is silently discarded. Measured (`t5harness.js`): ledger holds
`cb0df2d → [B]`, then `record('cb0df2d', ['E'])`:

    REPO  {"sha":"cb0df2d","panes":["E"],"ferried_at":2000,"added":["E"],"already":false}   ledger: 2 rows
    COPY  {"sha":"cb0df2d","panes":["B"],"added":[],"already":true,"ferried_at":1000}       ledger: 1 row

The copy reports `already: true` and prints the "nothing added" notice on stderr — **so the operator is actively
told the ferry was redundant when in fact it was dropped.** The comment beginning on line 161 describes this as
*"precisely how the dropped second pane went unnoticed"*; the change re-creates the bug the code around it was
written to fix. Two unmodified tests name it: *"a SECOND pane on the same sha MERGES into the set — the defect
this fixes"* and *"a GENUINE duplicate is a no-op and does NOT print the same as a write"*. Both fail.
*Found by reading; the exact dropped-row output is from running.*

### D4 · line 196 — `all.filter(r => r.at > ep)` (was `>=`)
**What it does.** Excludes a commit whose timestamp is exactly the ledger epoch from the measured window.
**Consequence.** Line 197 still reads `before = all.filter(r => r.at < ep)`, so a commit landing exactly on the
epoch falls into **neither** bucket and disappears from a report that prints both. The counts stop summing to the
total. Measured (`t5edge.js`, epoch set to a real commit's timestamp):

    REPO   all=809   before=2   inWindow=807     2 + 807 = 809  ✓
    COPY   all=809   before=2   inWindow=806     2 + 806 = 808  ✗  one commit vanishes

It is a boundary of exactly one millisecond, so it will usually not fire — and when it does, the report is
internally inconsistent rather than visibly wrong, which is the worse failure.
*The off-by-one is visible by reading. **The broken invariant — that the two printed lines no longer add up — I
only established by running**, because it requires knowing line 197 was left alone.*

### D5 · line 201 — `(r.ferry.ferried_at - r.at) / 1000` (was `/ 60000`)
**What it does.** Converts latency to seconds while line 220 still labels the output `min`.
**Consequence.** Every latency reads 60× too large under a unit label that is now false. Measured end to end
(`t5lat.js`, three ferries planted at 10, 20 and 30 minutes):

    true median = 20 min       REPO  median latency 20.0 min       COPY  median latency 1800.0 min

1800 is the *30-minute* entry expressed in seconds — D5 and D7 compounding. A reader sees a plausible-looking
number in a familiar unit and has no way to tell.
*Found by reading. **The printed value, and that the label was left saying `min`, are from running.***

### D6 · line 202 — `.filter(n => Number.isFinite(n))` (was `&& n >= 0`)
**What it does.** Removes the guard that discards a ferry stamped before the commit it ferries.
**Consequence.** Negative latencies enter the median. Isolated (`t5neg.js`, two ferries stamped 5 and 9 minutes
*before* their commits — a back-dated `--record` or clock skew):

    REPO  median latency  n/a          COPY  median latency  -300.0 min

**The copy prints a negative median latency.** A negative time-to-ferry is not a slow reading, it is not a reading
at all, and the tool now reports it as the headline number.
*Found by reading; the `-300.0 min` output is from running, and it is the only form in which this defect is
obviously nonsense rather than merely arguable.*

### D7 · line 204 — `lat[Math.ceil(lat.length / 2)]` (was `Math.floor`)
**What it does.** Moves the median index up one.
**Consequence, two of them, and the second is not an off-by-one.**
1. For odd n > 1 it returns the wrong element (n=3 → index 2, the largest, not index 1).
2. **For n = 1 it indexes past the end and the tool crashes.** `Math.ceil(0.5) = 1`, `lat[1]` is `undefined`, and
   line 220 calls `.toFixed(1)` on it. The `median === null` guard does not catch `undefined`. Measured
   (`t5lat.js 1`), after five lines of report had already printed:

    ```
    TypeError: Cannot read properties of undefined (reading 'toFixed')
        at report (…/t5/ferry.js:220:74)
    ```

   The process exits non-zero with a half-written report — so a caller that reads stdout gets a truncated report
   with no median line and no error in it.
**This is the state after exactly one artifact has been ferried**, i.e. the first run of a freshly seeded ledger.
*The wrong element is visible by reading. **The crash is not** — it needs `Math.ceil(0.5) = 1` and the `null`-only
guard to be put together against a one-element list, and I found it by running the n=1 case.*

### D8 · line 215 — `const RATE_FLOOR = 1;` (was `10`)
**What it does.** Lets a percentage print off a single observation.
**Consequence.** Measured (`t5floor2.js`, epoch placed to leave exactly 1 and exactly 3 commits in window):

    n=1   REPO  n/a - only 1 in window, need 10 before a rate means anything     COPY  100.0%
    n=3   REPO  n/a - only 3 in window, need 10 before a rate means anything     COPY  100.0%

The comment immediately above (lines 209-214) records that the fixed defect *"immediately produced 0.0% off n=3,
which is the same defect pointing the other way and reads as a clean bill of health."* **The change restores that
defect**, and against the current ledger it points the harmful way: a confident `100.0%` off n=1.
*Found by reading the constant against its own comment; the printed rates are from running.*

## 3 · WHICH FINDINGS CAME FROM READING, AND WHICH FROM RUNNING

**From reading alone** — a `diff -u` against the repo shows eight changed lines, and the file's own comments state
the invariant each one breaks, so the *existence* and *direction* of all eight are readable. D1, D3 and D8 are
fully diagnosable this way: their comments describe the bug being re-introduced.

**From running only** — five things, and they are the ones that change what the defect is worth:

1. **D2 discards the whole live ledger.** Reading says "the comparison is inverted". Running says every one of the
   136 rows on disk is 7 or 9 characters, so `usable` is empty and 63 ferries become 0.
2. **D7 is a crash, not an off-by-one.** At n=1 the tool dies at line 220 with a half-printed report.
3. **Three defects are masked by a fourth.** D5, D6 and D7 all sit downstream of D2's filter. In *any* live run
   the latency list is empty, the median prints `n/a`, and the three are invisible. I reached them only by
   crafting a ledger with 4-character shas so the copy's inverted filter would admit it. **A reviewer who read the
   diff and then ran the tool to confirm would see the numbers move and reasonably stop — and would carry three
   unfound defects forward.** This is the finding I would keep if I could keep only one.
4. **D4 breaks a printed invariant.** `before + inWindow = all` holds in the repo and fails in the copy (808 ≠ 809).
5. **Which tests fail, and that one passes for the wrong reason** — §4.

## 4 · A TEST THAT IS GREEN ON A BROKEN GUARD

`ferry.test.js:55-59`, *"a sha shorter than 7 is REFUSED, not matched loosely"*, **passes on the copy.**

    withLedger([{ sha: 'cb0df', panes: ['C'], ferried_at: 1 }]);   // 5 characters
    assert.strictEqual(joined[0].ferry, null, …);

Repo: `5 >= 7` is false → filtered → `ferry` is null → passes, correctly.
Copy: `5 <= 4` is false → filtered → `ferry` is null → **passes, for the opposite reason.**

The test fixes a single sha length and asserts a single outcome, so it cannot separate the guard from its
inversion — both reject a 5-character sha, for contradictory reasons. It would take a second case (a 7-character
sha that must MATCH) to hold the guard, and that case exists as a *different* test, which does fail. **The named
guard test is not what caught D2.**

This is the same shape as a lesson already in my map from 2026-09-15: *a test whose inputs are all the same
failure cannot tell which guard held.*
