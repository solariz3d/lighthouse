## What it does
A **PostToolUse** hook on `Bash|PowerShell`. It plays a built-in Windows sound through the default output device (`System.Media.SoundPlayer`, in a detached hidden PowerShell it does not wait for; no window is involved, so minimized is irrelevant) when, and only when, the command that ran was
- a **successful `gh release create`** (not a `--draft`), or
- a **successful `git push` that updated `main`** on t180, consonance or lighthouse.

Nothing else: not lap opens, dispatches, rings, commits, tests, failed pushes, or anything that only mentions those words.
- **The sound:** `C:\Windows\Media\chimes.wav` (the classic Windows chimes, 1.23 s), found through `%SystemRoot%`. I chose it over `Windows Notify System Generic.wav` (the everyday toast sound, 1.29 s) so a ship sounds unlike a routine notification, and over `tada.wav` (1.6 s) as too fanfare for "pleasant". `"chime_sound": "<a .wav path>"` overrides; if the file is missing it tries `Windows Notify System Generic.wav`, `notify.wav`, `ding.wav`, then stays silent. **I did not listen to any of them** (no audio check was possible or wanted while the keeper may be at the PC); the real player command ran on a silent wav only.
- **Debounce:** one chime per 2 minutes, to the millisecond (at exactly 120,000 ms it chimes again); anchored at the last chime, so a debounced ship does not extend the window; a push and a release in one command, or 30 s apart, chime once. State: `<data dir>/release-chime.json`.
- **Off switch:** `"chime": false` (also `0`, `"false"`, `"off"`, `"no"`) in `~/.consonance.json`; absent, `true`, `null` or a broken config leave it ON. Also `"chime_repos"` (default `["t180","consonance","lighthouse"]`) names the repos a push to main must match.
- **Fire and forget:** prints nothing, exits 0 on every path including garbage input, an empty stdin, an unwritable data dir and a missing sound; a 3 s watchdog; the dream gate. **Measured with the real player (silent wav): 141 ms** from process start to exit.
- **A ledger:** `<data dir>/release-chime.jsonl`, one row per ship it recognised (`chimed` / `debounced` / `silenced`, with kind, repo, sound), never the command. That is where to look if a ship made no sound.

## How it decides, read from what happened and not from guesswork
- **The command** must really RUN the thing: it is split into commands by a **quote-aware** splitter (a `;` or `&&` inside quotes is text), heredoc bodies are removed, and the first real word must be `gh` with `release create`, or `git` (`-C <dir>`, `-c k=v` skipped) with `push`. `echo "gh release create v1"`, `echo 'git push origin main'`, a heredoc that contains them, a commit message that contains them, `gh release list|view|delete`, `gh pr create`, `git pull`, `git fetch` all give nothing, even when the output beside them looks like a success. `if git push …; then` works. **`--dry-run`/`-n`, `--help`/`-h` and `--delete` do not count**: a dry run prints the same `main -> main` report and sends nothing (caught by my own bait row).
- **The result** must not say it failed: any numeric `exit_code`/`exitCode`/`returncode`/`code`/`status` that is not 0, `interrupted`, `is_error`, or an `error` field vetoes.
- **A push** must show git's own report of a ref that MOVED to `main`: `To <url>` then `a..b  main -> main` (a fast-forward, a forced update, or a new branch). Rejected, `Everything up-to-date`, `= [up to date]`, a deleted ref, a tag, another branch: no. The repo is read from the `To <url>` line (so `git push` with no arguments, `HEAD:main`, `cd <repo> &&` and `-C <repo>` all work); a `main` push to another repo (`dotfiles`) does not chime unless `chime_repos` names it.
- **A release** needs `exit_code === 0`, or a `…/releases/…` URL in the output (`gh` prints it).

## What this does not establish
- **No live PostToolUse payload was observed.** The shape (`tool_response` with `stdout`, `stderr`, `exit_code`, `interrupted`) is from the Claude Code hooks documentation, read through a summariser that also said a non-zero exit "still fires PostToolUse"; I did not trust that, so the hook vetoes on any exit signal AND requires positive evidence in the output. **The PowerShell tool's `tool_response` shape is not documented in what I read**; the hook reads `stdout`/`stderr`/`output`/`content`/`text`/`result` and plain strings. If a real push produces no chime, the ledger row (or its absence) is the first thing to read: no row means the hook did not recognise the payload.
- **A release or push run inside a nested shell** (`bash -c "..."`, `node -e`, a `.ps1` file) is not caught, and a push whose report git does not print (`--quiet`) is not. Both fail to silence, never to a false chime.
- I did not listen to the sound. Whether `chimes.wav` is the pleasant one is the keeper's ear; `chime_sound` changes it.
- The hook does not distinguish a "final" product push from a mid-lap push to main of a product repo: any successful push to main of t180, consonance or lighthouse chimes (once per 2 minutes), because main is where the product ships; the keeper's phrase "not when a new lap opens" is honoured (opens are not pushes), but a push of a hand-back commit to main WOULD chime.
