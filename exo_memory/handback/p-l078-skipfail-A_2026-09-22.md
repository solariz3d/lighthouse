## 0 · THE DEFECT AND THE FIX

`judgePass` caught only the secret-scan refusal per item; **any other error was `throw err`**, ending the pass. So under
intermittent 503s, every capture queued behind the first failure waited a full 10-minute cadence: head-of-line blocking.

**Now (`jev-judge.js`, `transientStatus` + the catch in `judgePass`):**
- **Skipped, pass continues:** HTTP **5xx**, **429**, a **network** failure (`request failed before a response`), or an
  answer that does not fit the schema (`bad-answer`). Each is about one call.
- **Still ends the pass:** any **other 4xx** (401, 403, 400). Those fail every call the same way, and a bad key would
  otherwise send a batch of doomed requests every cadence.
- **A failed item gets NO row in `jev_judge.jsonl`.** The "already asked" set is built from every row, so a failed row
  would retire the item forever. With no row, it is simply eligible again, and **first**: the queue is ordered by
  capture time.
- **Never re-asked once answered:** an `ok` row puts the item in the done set, unchanged from L071.
- **The report** (`result.failed`) carries `{ key: session:turn:level, level, status }`, **never** the error body (a
  gateway error body can echo input), the prompt or the key. The runner logs one line per failed item:
  `judge: item <key> failed (<status>) — skipped, retried next cadence`, and the summary line now counts `failed N`.

### Cap accounting, stated and tested

**A failed call consumes NO daily cap.** The cap counts `ok` rows (`callsToday`), and a failed call writes none. It does
use one of the pass's `maxCalls` attempts. Whether the gateway **bills** a 503 is **not verified**; a 503 is an upstream
failure and presumably unbilled, but that is inference, not a measurement.

**A residual, named:** an item that fails on every attempt heads every batch, costing one attempt per pass. It no longer
blocks anything behind it, but nothing gives up on it either. Not built: a retry limit.
