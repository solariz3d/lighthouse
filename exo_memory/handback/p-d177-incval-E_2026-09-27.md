### 1a · The stacking check

**Before:** every surface point was hashed into a 2 m grid with string keys, and every point near a changed one was
measured.

**Now, per STATION pair:**
- Station i's points lie within r_i of its centre, in the plane normal to T_i (r_i is its largest cross-section offset).
  So every point pair is at least:
  - **the sphere bound:** |Δpos| − r_i − r_j;
  - **the plane bound:** |T_i·Δpos| − r_j·sinθ, and the same from j's side. i's points have no T_i component; j's
    have at most r_j·sinθ. This bound rejects "the same road 25 m on", which the sphere bound cannot.
- A pair is measured point by point only if both bounds are under 2 m + `SLACK` (1e-4 m, for rounding).
- The measuring uses the same arithmetic as before, so a finding is bit-identical.
- Candidates come from a grid over station centres with cell 2·r_max + 2 m, keyed by small integers.

**Proven equal to HEAD three ways:**
1. **On real tracks against `git show HEAD:src/validate/index.js`**, `deepStrictEqual` on the whole result and on the
   raw stacked map. There are 8 tracks:
   - the 40 km bench track, with CSP on and off;
   - six dense 40-word tracks that stack at 25–210 stations.
   - The command is `iv/oldnew.js`: "identical" ×8.
2. **In the test suite:** the point-by-point algorithm is kept as the reference (`referenceStacked`). It is compared
   on three seeded tracks that stack.
3. **The 91 existing validation tests** pass unchanged.

### 1b · What an edit recomputes, in metres (the packet asked for this; it is also the comment in `core`)

- **Loads, folds, seams and holes:** from the change, minus 1 station (2 m). The along-track term reads the
  neighbours' speeds; a seam or hole compares a station with the next.
- **Segment reds:** from the word before the change (the old head's gap exemption).
- **Stacking:** a changed station against every station within **r_i + r_j + 2 m in space**, at ANY s, since a new
  piece can land on road laid kilometres earlier.
  - r is at most 15.9 m with the built-in words (the bowl), so the reach is ≤ 33.8 m.
  - An old station whose deepest stack was on a changed one is re-derived.
- **Jumps:** recomputed whole. A jump's landing reads up to `landingSearchM` (150 m) after its flight, so a word placed
  within 150 m of an earlier jump can change it. There are few jumps.
- **Self-intersection:** not validation's. It is `buildMesh`'s BVH, passed in as `opts.folds`, and the controller does
  not pass it: the result's `notChecked` says so.
- **Downstream of a sculpt:** EVERY station is recomputed, per station. C's rigid re-placement moves what follows the
  edit. A full validate of the moved path reads the moved coordinates, so carrying the old figures would differ from it
  in rounding and break "exactly". Per station this is cheap now. It was never the cost: the whole-track point grid was.
- **Not strictly bounded (stated, not hidden):**
  - an append still does O(stations) bookkeeping with small constants: the speed profile, the station grid build, the
    carried-lines copy, and the result's `speed` array.
  - At 40 km that is about 10 ms of the 11–16 ms (the phase timer: `speed` 1.4–4.8, `stacked` 3.5–7, `collect` 2–4).

### 1c · ONE shared path

C exposed its path this lap as `t180:track-request` → `{ path, segments, closed, how, g, fromS }`. C's track model
now steps at 2 m, and my controller consumes it:
- **When it is used:** `sharedPath()` returns that detail. It is used only if `segments` is the very array of the
  document being validated (identity).
- **Otherwise, the fallback:** no preview, a preview one change behind, or a step that does not divide. The controller
  grows its own path as before. So an unanswered or stale path costs speed, never correctness.
- **The view:** `pathview.js` views the preview's path at 2 m. With C's 2 m path it is the identity (R = 1). With a
  0.5 m path it is every 4th station. The view claims exactness; it holds because:
  - buildPath puts each station at u = k·step on its own segment's grid;
  - a station's values depend on u alone (fixed ≤ 0.25 m substeps);
  - so every R-th station IS the 2 m station. The float identity k·0.5·4 = k·2 is checked per station, and a view
    that would differ returns null.
- **The mount:** `app/validate-ui/index.js` dispatches C's `t180:track-request`. **No change is needed in A's page or
  shell.**
- **`state.pathFrom`** says which path each update used.

### 1d · The lap, never on a drag tick

- **During a drag:** the controller validates with the lap deferred whenever `state.history.dragBase` is set (a drag is
  open). The result says `lap: { ok: null, reason: 'deferred' }`.
- **When the drag ends:** the change that ends it proves the lap with `lapOf()`. That reads the result's own speeds,
  lines and jumps: O(stations), with nothing else recomputed. It equals an undeferred validate's lap (tested).
- **Scope:** a lap exists only on a closed loop. A closed loop is still a full rebuild per change, by C's geometry: its
  closing twist spans the loop.

## 2 · What "exactly" means here, and a correction I made on the way

**My first property test compared against a fresh `buildPath`, and failed in BOTH path modes at the same drag.**
- **The cause** is C's same-lap `rebuildPathFrom`. It re-places the downstream tail by a rigid motion (a turn about
  world up plus a shift) instead of regrowing it, so the re-placed path equals a fresh build only to rounding
  (`RIGID_TOL` 1e-12).
- **"Exactly" is therefore stated for validation:**
  - the incremental result equals a full `validate` of **the same path**, bit for bit (`deepStrictEqual`);
  - separately, the path is checked against a fresh 2 m build for station count, segments and positions within 1e-6 m
    (`samePath`).
- Whether the re-placed path equals a fresh one to the bit is C's claim to state, not mine.
