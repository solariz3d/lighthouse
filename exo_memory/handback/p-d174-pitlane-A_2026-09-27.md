## 0. The design, and where it differs from E's interface

The loop stays ONE ordered list of words (§11.1). The lane is a side road ANCHORED to it, as E's markers are, so it
follows the words it runs beside when they are sculpted.

`doc.pitLane` is `null` or:

```
{ side, leave: {word, along}, rejoin: {word, along}, offsetM, width, divergeM, mergeM, speedKmh }
```

**It differs from E's proposal (`p-d171-markers-E` §3) only by adding `divergeM` and `mergeM`.** The ease is a shape
the user sets, and leaving it implicit would hide a length the geometry needs. The lane's own words are its three parts,
in order: DIVERGE, RUN and MERGE (resolved as segments `PIT` in/body/out).

**Not built, by choice: a free-form lane** (its own turns and climbs). It would have to leave the road's coordinates
and come back through a closing solve like `closeLoop`. Pit lanes run beside the road. The packet's phrase "with its own
words" is met by the three parts; if the keeper wants free-form lane words, that is a follow-up with a closing solve.

## 2. Geometry (`src/geom/pitlane.js`)

The lane is built in the main road's own coordinates:
- the main road's lane-side edge is `e(s)`, taken from the profile the mesh builds (the font, or the font-ramp blend);
- the gap is `g(s)`: 0 at the leave, then `profile.js smoothstep` (the font ramps' ease: zero slope at both ends) out to
  `offsetM`, held, and back to 0;
- the inner edge is `e + σ·L·g`, and the centre is `e + σ·L·(g + w/2)`.

At both joins `g = g' = 0`, so the inner edge IS the road's edge and runs along it (G1). The lane is flat, in the road's
plane, and never overlaps the road's surface: it shares the edge line and nothing else, so there is no stacked surface.
The rows are laid on the main road's `L` (exact joins). In a diverge they are sheared by the lane's angle; the bound is
atan(1.5·offset/diverge), 12.8° for the defaults, **inferred** from that formula. The lane's `s` is its own arc length.
Its `kvec` is scaled so `mesh.js`'s fold margin reads the lane's own rows. Cells are `1ROAD_PIT_<part>_<n>`, drivable.

Refused, by name: PIT_ANCHOR_MISSING, PIT_BACKWARDS (a lane across the loop's start is not built), PIT_TOO_SHORT,
PIT_OVER_GAP, and PIT_JOIN_NOT_FLAT (|ψ| at the joined edge > 1°).

`laneCheck` runs the self-check's own triangle and stacked tests, lane against road. It exempts ONLY a diverge/merge
triangle against road triangles within 5 m of that part's span of main road; everything else is tested, including a
diverge against any other pass.

## 3. Layouts (`src/export/layouts.js`)

The AC convention was **checked on this machine** (read only): `content/tracks/cash_auroracryopticon` has
`models_aurora_long.ini` and `models_aurora_medium.ini` at its root, then `aurora_long/{ai, data/*.ini, map.png}` and
`ui/aurora_long/{ui_track.json, preview.png, outline.png}`; `ks_nordschleife` is laid out the same way. Per layout `L`
of folder `F`:
- `F_L.kn5`, one model per layout, since Aurora's are separate model files;
- `models_L.ini`;
- `L/data/surfaces.ini`, `L/data/map.ini`, `L/map.png`, `L/ai/fast_lane.ai`;
- `ui/L/{ui_track.json, preview.png, outline.png}`.

**How `trackfiles.js` handles layouts today:** in exactly one place, `modelsIniName(layout)` → `models_<layout>.ini`
(`trackfiles.js:43`). Its `writeTrackFiles` writes the NO-layout set at the root. `layouts.js` reuses trackfiles' pure
builders (surfacesIni, modelsIni, uiTrack, mapParams, mapIni, mapPng, previewPng, outlinePng) and places them the layout
way; `trackfiles.js` is not changed. Every layout is built (every check ON) before anything is written, and NOT_OURS is
refused untouched, as in `exportTrack`.
