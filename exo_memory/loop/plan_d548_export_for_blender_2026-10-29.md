The use: build the road here, take it into Blender to tweak or to dress with an environment, then on to the game through the usual community pipeline (Blender → FBX → ksEditor → kn5).

## Facts (checked 20:33)

- A `.blend` file is Blender's own binary and only Blender writes it sensibly. Blender imports glTF 2.0 (`.glb`, built in, keeps names, normals, UVs, materials, a node tree) and OBJ natively; its FBX importer takes BINARY FBX only, and writing binary FBX ourselves is a large, under-documented job. ksEditor (AC's own, `assettocorsa\sdk\editor`) takes FBX.
- Blender 5.2 is on this machine: `C:\Program Files (x86)\Steam\steamapps\common\Blender\blender.exe` (Steam app 365670). So a pane can run Blender headless (`blender --background --python`) to import what we write and to write FBX, and the app can do the same for the user when Blender is found, the way it finds AC through Steam.
- The exporter today (`src/export/`: scene.js builds the node tree, kn5write.js writes it; acready.js merges cells into road, underskin, grip and wall chunks; markers.js the AC_ dummies; pitlane.js, pitboxes.js, catch.js, ailine.js) already holds everything a Blender file needs: positions, normals, UVs (the flow's, D543's fix included), per-chunk materials and textures, named nodes, the markers as empties. A glTF writer is a second serialiser of the same scene, not a second geometry path.

## The design

**File ▸ Export for Blender…**: a folder picker; the builder writes `<name>.glb` (glTF 2.0 binary): one node per road piece per kind, named as the kn5 names them with the piece number first (`p07_road`, `p07_wall_L`, `p07_underskin`, `pitlane_road`, `catch_…`), so a Blender user selects "piece 7" by name; the same vertex positions as the kn5 to the float (the same Float32 arrays), the same normals and UVs, Y-up and metres as AC has them (Blender's importer converts to its Z-up itself); one material per surface with its texture embedded (the made asphalt or his picture, PNG inside the glb) so it opens textured; the AC markers (AC_START_n, AC_PIT_n, AC_TIME_0_L/R, AC_HOTLAP_START_0, AC_AB_START/FINISH) as empty nodes with the same names and transforms; the AI line as a polyline node (a mesh of line primitives) named `ai_fast_lane`, optional tick on; a sidecar `README.txt` in the folder saying what each node is and the ksEditor path. Pieces or the whole track: with a run selected, "Export selected pieces for Blender…" writes only those pieces (and their markers if inside).

**FBX, when Blender is there:** a tick "also write FBX for ksEditor (uses your Blender)" shown only when blender.exe is found (Steam's folder through the same Steam lookup the AC export uses, or a saved path in Settings); on tick the builder runs Blender headless with a small bundled Python script: import the glb, export `<name>.fbx` with the settings ksEditor wants (the community's known ones: FBX binary, Y-up, apply unit scale, mesh + empties, no animation), and reports the result in the status line. No Blender: no tick, a line in the dialog saying how to get the FBX by hand (open the glb in Blender, File ▸ Export ▸ FBX). Nothing is installed or launched with a window; Blender runs background and exits.

## Parts

**Part 1 (pane E, PROVE IT: a data format):** `src/export/gltf.js` writing a valid glTF 2.0 binary from the export's scene (the same node tree the kn5 gets, after acready's merge): buffers, bufferViews, accessors with min/max, meshes with POSITION/NORMAL/TEXCOORD_0 and uint32 indices, nodes named, materials (KHR_materials_unlit or plain PBR with baseColorTexture), images embedded as PNG, empties as nodes without mesh; `src/export/blender.js` the folder write (glb + README) and the selected-pieces subset. Tests first: a glTF validator check in node (write our own strict reader of the file we wrote: chunk lengths, JSON/BIN alignment, accessor counts and byte offsets, min/max equal the data) plus BLENDER ITSELF: a test that, when blender.exe is present on the machine, runs it headless to import the glb and print object names, vertex counts and the bounds, compared to the kn5's (`tools/kn5.cjs`) for the nine fixtures and CRAZY TEST; skipped with a reason where Blender is absent. Positions equal to the float; node count equals the kn5's; markers at the same transforms; the UVs of a textured tube equal the flow's. Mutation: the export harness that reaches scene/acready (E names it) whole, with the new file's mutants (an accessor's byteOffset off by 4; a min/max dropped; a node unnamed).

**Part 2 (pane A, CHECK IT):** the File menu item and the dialog (the folder picker as the Export's; the FBX tick; the selected-pieces variant), the Blender lookup through Steam (`steamapps/common/Blender/blender.exe` across the libraryfolders, as the AC lookup does) and a Settings field to point at another Blender; the headless FBX run with its bundled Python (`src/export/blender_fbx.py`), the status line's words; a test that the item writes the files into a temp folder and, with Blender present, that the FBX appears and ksEditor's expectations hold (binary FBX header, the node names present: read the FBX header and the object names with a small reader, or re-import the FBX in Blender headless and compare names); a headless once-over of the dialog (`--mute-audio`). README and CHANGELOG lines in a player's words: "Export for Blender writes a .glb you open in Blender with every piece named; with Blender installed it can also write the FBX ksEditor takes."

Kept out: a `.blend` file (Blender writes it; the FBX step could write one too by the same headless route, a one-line addition once Part 2 stands: `bpy.ops.wm.save_as_mainfile`); importing a Blender-edited track back into the builder (a different lap, and a big one); environments and props.

Falsifier: if Blender's import of our glb and the kn5 disagree in vertex count or bounds on any fixture, the writer is wrong, not Blender; if ksEditor refuses the FBX Blender wrote from our glb, the FBX settings are wrong and the community's known export preset is the reference.
