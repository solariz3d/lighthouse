### Correction to my own last report

**My $367 session figure was wrong by ~6.7×. The real number is $54.48.**

The harness writes **one API response as several jsonl records** — one per content block (thinking / text / tool_use) — each stamped with the **same** `usage` object. Verified directly: `msg_011CeHtsebynAAGij4QZWXPJ` occupies three consecutive lines with distinct uuids chained by `parentUuid`, content types `["thinking"]`, `["text"]`, `["tool_use"]`, and byte-identical usage. **330 usage-bearing records → 80 unique `message.id`.** I summed records. My per-record medians survive (they're per-record either way); every total I gave you was inflated ~4×.

### And the same defect is shipped

**`main.rs:2235` accumulates `extract_usage` into the `Cost` state with no dedupe by `message.id`.** The `note_unseen` / `dedup_key` guard at `main.rs:1770` protects `board_push` only, and keys on `(pane, ts, text)` — turn text, not usage. So `c.usd`, the four token counters, and the **`ceiling_out` breaker at `:2249`** all count one API response once per content block. For the librarian that ratio is **330 / 80 ≈ 4.1×**.

Two consequences, and the second is the answer to your question:

1. **The cost breaker trips at roughly a quarter of the output it was configured for.**
2. **The board's cost rows cannot verify the seat's claim, because they are the same accounting, wrong in the same direction.** The only external instrument that works here is the raw transcript deduped by `message.id`.

I did not run the app — this is from source plus the file structure. It is a testable claim and whoever owns `main.rs` should confirm it before anyone acts on the number.
